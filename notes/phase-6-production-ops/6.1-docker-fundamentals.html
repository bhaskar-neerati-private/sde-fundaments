6.1 Docker Fundamentals

Objective: containerize a real application correctly - a minimal, layered, non-root, production-sane Dockerfile, not just "it runs."

6.1a Images & Containers

A Docker image is an immutable, layered filesystem snapshot (built from a Dockerfile's instructions) containing everything needed to run an application - code, runtime, libraries - built once, reused many times. A container is a running instance of an image - an isolated process (Linux namespaces + cgroups) with its own filesystem view plus a thin writable layer on top, sharing the host's kernel (unlike a VM, which virtualizes an entire separate OS).

Plain English: an image is like a class (1.1a) - a blueprint. A container is an instance of that class - an actual running thing with its own state, many of which can be spun up from the same image, independently. Unlike a VM (boots a whole separate OS, slow, heavy), a container just isolates a process using the host's existing kernel - much lighter and faster to start.

Analogy: an image is a shipping container's mold at a factory - reusable, unchanging. A running container is an actual container built from that mold, now loaded with specific cargo (the running application state) - many actual containers stamped from the same mold, each independently loaded.

Layers: each Dockerfile instruction creates a new, cached layer stacked on the previous ones - if an instruction and its inputs haven't changed since the last build, Docker reuses the cached layer instead of re-executing it. Layer order matters for caching: instructions that change rarely (installing dependencies) should come before instructions that change often (copying source code) - otherwise a source-only change invalidates the expensive dependency-install layer too, since invalidating a layer invalidates every layer after it.

FROM python:3.11-slim
WORKDIR /app

# dependencies first -- changes rarely, cached across most rebuilds
COPY requirements.txt .
RUN pip install -r requirements.txt

# source code last -- changes often, but doesn't invalidate the dependency layer above
COPY . .

CMD ["uvicorn", "main:app", "--host", "0.0.0.0"]

docker build -t myapp:latest .
docker run -p 8000:8000 myapp:latest

If COPY . . came before RUN pip install, every source change (even a one-line fix) would invalidate the cache for the pip install layer too, forcing a full dependency reinstall on every rebuild even though dependencies never changed.

6.1b Multi-Stage Builds & Docker Compose

A multi-stage build uses multiple FROM statements in one Dockerfile; later stages selectively copy artifacts from earlier stages without including those stages' full contents (build tools, intermediate files) in the final image - a much smaller, more minimal production image with only the built artifact and runtime dependencies.

Plain English: building often needs heavy tools (compilers, build-time dependencies) completely unnecessary at runtime - shipping them wastes space and increases attack surface. Multi-stage builds use a "builder" stage with all the heavy tools, then copy just the final artifact into a clean minimal stage that never sees the build tools.

Analogy: a kitchen's messy prep area (build stage) full of equipment, but only the finished plate (the artifact) gets carried to the dining room (production image) - the diner never sees the mixing bowls and half-used ingredients.

# Stage 1: builder -- has all the heavy build tools
FROM python:3.11 AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --user -r requirements.txt

# Stage 2: final -- minimal, only what's needed at runtime
FROM python:3.11-slim
WORKDIR /app
COPY --from=builder /root/.local /root/.local    # copy ONLY the installed packages
COPY . .
ENV PATH=/root/.local/bin:$PATH
USER 1000                                          # non-root -- security best practice
CMD ["uvicorn", "main:app", "--host", "0.0.0.0"]

Non-root user: a container running as root by default means that if an attacker breaks out of the container's isolation (a container escape), they'd have root on the host too - a non-root user limits that blast radius.

Docker Compose orchestrates multiple containers (app, database, cache) declaratively in one YAML file, started/stopped together, with an automatic shared network so containers reach each other by service name.

services:
  api:
    build: .
    ports: ["8000:8000"]
    depends_on: [db, redis]
  db:
    image: postgres:15
    environment: { POSTGRES_PASSWORD: secret }
  redis:
    image: redis:7

docker compose up    # brings up all 3 containers together, wired to talk by service name ("db", "redis")
