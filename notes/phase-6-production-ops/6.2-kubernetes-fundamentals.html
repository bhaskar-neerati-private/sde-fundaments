6.2 Kubernetes Fundamentals

Objective: deploy the containerized service to a local Kubernetes cluster and understand what Pods, Deployments, Services, and ConfigMaps actually do - not just copy-paste YAML.

6.2a Pods & Deployments

A Pod is the smallest deployable unit in Kubernetes - one or more tightly-coupled containers always scheduled together on the same node, sharing a network namespace (same IP/localhost) and optionally storage volumes; most commonly, one container per pod. A Deployment is a higher-level controller managing a set of identical pod replicas (via an underlying ReplicaSet), ensuring the desired number are always running (auto-replacing crashed ones) and managing rolling updates.

Plain English: you almost never create bare Pods directly - you create a Deployment, and Kubernetes creates/manages Pods for you per the Deployment's spec. If a Pod crashes, the Deployment notices the actual count doesn't match the desired count and starts a replacement automatically - this "keep actual state matching desired state" reconciliation loop is the core idea behind essentially everything in Kubernetes.

Analogy: a Pod is a single food truck at an event - self-contained. A Deployment is a franchise owner committed to always having exactly 3 trucks running - if one breaks down, a replacement is dispatched immediately to maintain the count, without anyone manually noticing and ordering a new one.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-deployment
spec:
  replicas: 3                        # desired state: always 3 pods running
  selector:
    matchLabels: { app: api }
  template:
    metadata:
      labels: { app: api }
    spec:
      containers:
      - name: api
        image: myapp:latest
        ports: [{ containerPort: 8000 }]

kubectl apply -f deployment.yaml
kubectl get pods                          # shows 3 running pods
kubectl delete pod api-deployment-xyz       # kill one manually -- Deployment automatically replaces it

Why "desired state vs. actual state reconciliation" is worth understanding as a general Kubernetes principle, not just a Deployment-specific detail: the Deployment controller runs a continuous loop, constantly comparing "how many pods matching this label selector currently exist" against "how many the spec says should exist," and takes corrective action (create or delete pods) whenever they diverge. This exact same reconciliation pattern - declare the desired end state, let a controller continuously work to make reality match it - is how nearly every Kubernetes resource type operates (Services keeping their endpoint list current, ReplicaSets maintaining pod counts, and so on), which is why understanding it once, clearly, pays off across the whole system rather than being a one-off Deployment quirk.

6.2b Services, ConfigMaps/Secrets & Rolling Updates

Pods are ephemeral (IP changes every time one is recreated), so a Service provides a stable network address (fixed virtual IP + DNS name) that automatically load-balances traffic across whichever pods currently match its label selector. Types: ClusterIP (internal-only, default), NodePort (exposes a static port on every node), LoadBalancer (provisions an external cloud load balancer - the typical production public entry point).

ConfigMaps/Secrets externalize configuration out of the image (ConfigMap: non-sensitive, e.g. a DB URL; Secret: sensitive, e.g. passwords/API keys, base64-encoded, access-restricted), injected as environment variables or mounted files at runtime.

Plain English: without a Service, a replaced Pod's new IP would break anything talking to the old IP directly - a Service gives a stable name that automatically tracks whichever pods currently exist and are healthy. ConfigMaps/Secrets exist so the same image can run in dev/staging/prod, just with different values injected at deploy time, rather than baking environment-specific values into the image itself.

Analogy: a Service is a company's single published customer-service phone number, always connecting you to whoever's currently staffing the desk, even as individual staff (pods) rotate - callers never track individual employees' numbers. ConfigMaps/Secrets are the same uniform/instructions given to any staff member regardless of branch, plus a branch-specific badge and access code handed over once they arrive - the core instructions (the image) don't change, just the environment-specific details.

apiVersion: v1
kind: Service
metadata: { name: api-service }
spec:
  selector: { app: api }              # routes to any pod with this label -- tracks the Deployment's pods
  ports: [{ port: 80, targetPort: 8000 }]
  type: ClusterIP
---
apiVersion: v1
kind: ConfigMap
metadata: { name: api-config }
data:
  DATABASE_URL: "postgres://db:5432/mydb"

Why a Service's label selector, not a fixed list of pod IPs, is what makes it stable under constant pod churn: the Service continuously watches for which currently-running pods match its selector (here, app: api) and routes to whichever set that currently is - a pod being deleted and replaced doesn't require anyone to update the Service's configuration, because the Service was never pointing at that specific pod's IP in the first place, only at "whatever currently has this label." This is the exact same "reconciliation, not a static reference" principle from 6.2a, applied to networking instead of pod count.

Rolling update:

kubectl set image deployment/api-deployment api=myapp:v2
kubectl rollout status deployment/api-deployment

What Kubernetes does during it: gradually creates new pods on the new image, waits for each to pass health checks ("ready"), then terminates a corresponding old pod - a few at a time (maxSurge/maxUnavailable), never taking the whole Deployment down at once, so the Service always has some healthy pods (old or new) to route traffic to throughout the update. This is the mechanism behind zero-downtime deploys.

Why waiting for health checks before terminating an old pod is the specific detail that makes this "zero-downtime," not just "gradual": if new pods were created and old ones torn down without confirming each new pod is actually ready to serve traffic, there could be a window where neither the (already-terminated) old pod nor the (not-yet-ready) new pod is available to handle requests routed to it - a real, if brief, outage. Explicitly gating each step on a passed health check guarantees the Service always has a pool of genuinely-ready pods (some mix of old and new) throughout the entire rollout, which is precisely what "zero-downtime" means in concrete, mechanical terms, not just a marketing phrase.

Common mistakes & misconceptions

  1. Creating bare Pods directly instead of a Deployment, losing the automatic crash-recovery and rolling-update machinery a Deployment provides - as stated above, this is almost never the right default; Deployments exist specifically because managing Pods by hand doesn't scale to real production needs.
  2. Assuming a Pod's IP address is stable and safe to reference directly. Pods are explicitly ephemeral - any component that needs to reliably reach "the API," rather than one specific, possibly-already-replaced Pod instance, must go through a Service, not a captured IP.
  3. Putting sensitive values (passwords, API keys) into a ConfigMap instead of a Secret. ConfigMaps are not access-restricted or treated with the same handling precautions Secrets receive - the distinction exists specifically to separate "fine to view/log/share freely" configuration from "must be protected" credentials.
  4. Believing base64 encoding in a Secret provides meaningful confidentiality. As with JWTs (5.6a), base64 is an encoding, not encryption - anyone with read access to the Secret object can trivially decode it; genuine protection comes from Kubernetes' access controls (RBAC) restricting who can read Secret objects in the first place, not from the encoding itself.
  5. Choosing ClusterIP for a Service that needs to be reachable from outside the cluster, or LoadBalancer for a purely internal service that never needs external exposure - each Service type exists for a specific reachability scope, and mismatching them either breaks external access entirely or unnecessarily exposes an internal-only service to the public internet.
  6. Assuming a rolling update is instantaneous or that Kubernetes tears down all old pods immediately upon kubectl set image. As explained above, the process is deliberately gradual and health-check-gated specifically to avoid any window with zero healthy pods - watching kubectl rollout status (rather than assuming the update completed the instant the command was issued) is the correct way to confirm it actually finished.
