6.4 Monitoring & Logging

Objective: instrument the service with structured logging and basic metrics, and read a dashboard to diagnose a problem - not just "add print statements to production."

6.4a Logs vs. Metrics vs. Traces

A log is a timestamped, discrete record of a specific event ("what exactly happened") - detailed, expensive to store/query at scale, not naturally aggregable. A metric is a numeric measurement tracked over time (request count, error rate, latency percentile) - cheap to store (pre-aggregated), great for "how is the system doing overall," but doesn't say why any single request behaved a certain way. A trace follows a single request's journey across multiple services, recording time spent in each step ("where did this one request spend its time") - essential for diagnosing latency in a distributed system.

Plain English: these answer three genuinely different questions. "Did this specific login attempt fail, and why?" → log. "Is our error rate trending up over the last hour, across all requests?" → metric. "This particular slow request took 2 seconds - which of the 5 services it touched caused the delay?" → trace. Using the wrong tool for the question is a common real mistake - grepping raw logs to answer "is the system healthy overall" (slow, doesn't aggregate) instead of just checking a metrics dashboard.

Analogy: a log is a detailed diary entry about one specific incident. A metric is a fitness tracker's daily step-count summary - cheap to glance at, great for spotting a trend, but doesn't say which specific steps were slow. A trace is a GPS breadcrumb trail of one specific walk, showing exactly how long you paused at each landmark - precisely which segment of this one journey took longest.

Structured (JSON) logging: instead of free-text ("User 42 failed to login"), log structured fields ({"event": "login_failed", "user_id": 42, "request_id": "abc123"}) - machine-parseable, filterable by field, and correlatable across a whole request's lifecycle via a shared request ID threaded through every log line touched by that request.

import logging, json, uuid

def log_event(event, **fields):
    print(json.dumps({"event": event, "timestamp": "...", **fields}))

request_id = str(uuid.uuid4())          # generated once per request, threaded through every log call for it
log_event("request_started", request_id=request_id, path="/checkout")
log_event("payment_charged", request_id=request_id, amount=49.99)
log_event("request_completed", request_id=request_id, status=200)
# all 3 lines share request_id -- filterable/groupable to reconstruct one request's full story

6.4b Prometheus & Grafana Hands-On

Prometheus collects metrics by pulling (scraping) from configured targets at regular intervals via an HTTP endpoint each exposes (conventionally /metrics), storing them as a time series database queryable with PromQL. Grafana queries a data source (commonly Prometheus) and renders results as charts/dashboards.

Plain English: your application exposes a /metrics endpoint reporting current counters/gauges; Prometheus periodically visits it and records what it sees, building a history over time; Grafana queries that stored history to draw graphs a human can actually reason about, instead of staring at raw numbers.

Analogy: your /metrics endpoint is a factory machine's dashboard gauge, readable at any moment. Prometheus is an inspector jotting down the gauge's reading every 15 seconds, building a logbook. Grafana is the wall-mounted screen turning that logbook into a live-updating graph the floor manager glances at to spot a trend - without reading raw logbook entries one by one.

from prometheus_client import Counter, Histogram, start_http_server

REQUEST_COUNT = Counter('http_requests_total', 'Total HTTP requests', ['endpoint', 'status'])
REQUEST_LATENCY = Histogram('http_request_duration_seconds', 'Request latency')

@REQUEST_LATENCY.time()
def handle_request(endpoint):
    # ... process the request ...
    REQUEST_COUNT.labels(endpoint=endpoint, status=200).inc()

start_http_server(8001)     # exposes metrics at :8001/metrics for Prometheus to scrape

Diagnosing elevated latency using only the dashboard (no code reading): look at the request-latency histogram/percentile panel, break it down by endpoint to identify which specific endpoint spiked (not a system-wide issue), then cross-reference when the spike started against deploy history/error-rate panels to correlate it with a specific change. This is a deliberately metrics-only diagnostic workflow - the dashboard alone should narrow down where to look before an editor is ever opened.
