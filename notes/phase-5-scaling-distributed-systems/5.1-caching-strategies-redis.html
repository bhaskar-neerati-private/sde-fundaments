5.1 Caching Strategies & Redis

Objective: choose the right caching strategy (cache-aside, write-through, write-behind) for a given access pattern, and use Redis correctly, including cache invalidation.

5.1a Caching Strategies

Cache-aside (lazy loading): application checks the cache first; on a miss, reads from the DB, then writes the result into the cache for next time - populated on demand, only for data actually requested.

Write-through: every write goes to the cache and DB synchronously, together - cache is always immediately up to date, at the cost of extra write latency.

Write-behind (write-back): writes go to the cache immediately (fast), asynchronously flushed to the DB later in batches - fastest writes, but risks data loss if the cache fails before the flush.

Plain English: cache-aside is the most common, simplest to reason about, handles read-heavy workloads well since only actually-requested data gets cached - but the first request for any given data is always slow (a cache miss, hitting the DB directly). Write-through keeps cache and DB always in sync but makes every write pay for updating both. Write-behind is fastest for writes but riskiest - there's a window where the cache has data the DB doesn't yet have.

Analogy: cache-aside is a chef preparing a dish only once a customer actually orders it, keeping it ready for the next person ordering the same thing - no wasted prep on unordered dishes. Write-through is updating your personal notebook and a shared master ledger the instant any transaction happens, together - always consistent, every transaction a bit slower. Write-behind is jotting transactions quickly in your notebook first, batching them into the ledger periodically later - fast in the moment, but if the notebook is lost before the batch update, those transactions are gone from the ledger.

def get_user(user_id, cache, db):          # cache-aside
    cached = cache.get(f"user:{user_id}")
    if cached is not None:
        return cached                        # hit -- fast path
    user = db.query(User).get(user_id)         # miss -- slow path
    cache.set(f"user:{user_id}", user, ttl=300)
    return user

Why "the first request for any given data is always slow" is an inherent, unavoidable cost of cache-aside, not a bug to fix: by definition, cache-aside only populates an entry once something actually asks for it - there's no way to serve a cache hit for data nobody has requested yet, since the cache genuinely doesn't have it. This is the direct trade-off against write-through, which pays a small cost on every write specifically to avoid ever having this "first request is slow" moment on the read side - cache-aside defers that cost to read time and only pays it for data that's actually accessed, while write-through pays it upfront for all data regardless of whether it's ever read.

Why write-behind's risk window is a genuinely different failure mode than write-through's cost, not just "a faster version of the same trade-off": write-through's cost is purely a latency trade (writes are slower, but nothing is ever lost). Write-behind's risk is a durability trade (writes are faster, but a cache failure before the batched flush means those writes are gone, not just delayed) - these are two different axes entirely (speed vs. safety), which is why the choice between them depends on whether the data can tolerate being lost in a rare failure window, not just on how much latency is acceptable.

5.1b Redis Basics & Cache Invalidation

Redis is an in-memory key-value store commonly used as a cache (also usable as a message broker, session store) - supporting simple key-value pairs plus richer structures (lists, sets, hashes, sorted sets), with optional TTL expiration per key.

Cache invalidation ensures cached data doesn't stay stale after the underlying data changes. Two dominant approaches: TTL-based expiration (entries auto-expire after a fixed time, bounding staleness but not eliminating it) and explicit invalidation (actively deleting/updating the cache entry the moment the underlying data changes).

Plain English: "there are only two hard things in computer science: cache invalidation and naming things" is an earned joke. TTL-only means data can be stale for up to the TTL duration after a write (a customer might see an old order status for up to 5 minutes if TTL=5min) - fine for some data, unacceptable for others (a stale "payment failed" after it actually succeeded). Explicit invalidation closes that gap but adds complexity: you must remember to invalidate every code path that writes the underlying data, and missing one creates a subtle, hard-to-reproduce stale-cache bug.

Analogy: TTL-only is a "best by" date - the product gets thrown out eventually regardless of whether it's actually gone bad, bounding the worst case but not preventing a mildly-stale product in the meantime. Explicit invalidation is an active recall - the moment a problem is discovered, someone actively pulls every affected unit off every shelf immediately, rather than waiting for the date to expire - more precise, but requires reliably catching and acting on every relevant change, which is the actually hard part.

import redis
r = redis.Redis()

def get_user(user_id, db):                    # cache-aside with TTL
    cached = r.get(f"user:{user_id}")
    if cached:
        return cached
    user = db.query(User).get(user_id)
    r.set(f"user:{user_id}", user, ex=300)      # expires in 300s
    return user

def update_user(user_id, new_data, db):          # explicit invalidation on write
    db.update(User, user_id, new_data)
    r.delete(f"user:{user_id}")                    # invalidate immediately -- next read repopulates fresh

Why "why naive TTL-only isn't always enough" deserves a precise answer, not just "because staleness is bad": any write path that forgets to also invalidate (or races with a concurrent read repopulating stale data right after a delete) can leave genuinely wrong data visible for the full TTL duration. For data where staleness has real consequences (payment status, near-zero inventory counts), explicit invalidation as the primary mechanism - with TTL as a safety-net backstop in case an invalidation is ever missed - is the safer default. TTL alone bounds how long staleness can last; it does nothing to bound whether staleness is acceptable for that specific piece of data in the first place.

Why update_user deletes the cache entry rather than updating it in place: deleting and letting the next get_user call naturally repopulate via the existing cache-aside path reuses the exact same "fetch from DB, write to cache" logic that already exists - there's no separate "update the cache with this new value" code path to keep in sync with the read path's population logic. This is a small but real simplicity win: one code path (the cache-aside miss handler) is responsible for ever writing into the cache, rather than two independent paths that could drift out of sync with each other over time.

Common mistakes & misconceptions

  1. Forgetting to invalidate the cache on one specific write code path, while remembering it on others - the exact "hard part" the analogy above highlights. A missed invalidation doesn't crash anything or throw an error; it silently serves stale data indefinitely (or until the TTL, if any, eventually expires) until specifically investigated.
  2. Using write-behind for data where losing a small window of writes is unacceptable (e.g. financial transactions), attracted purely by its write-speed advantage without weighing its durability risk - the speed/safety trade-off described above needs to be evaluated per data type, not applied uniformly.
  3. Believing TTL and explicit invalidation are mutually exclusive strategies to choose between. As stated above, the safer real-world pattern often combines them: explicit invalidation as the primary mechanism for correctness, with a TTL as a backstop bounding the damage of any invalidation that gets missed - not an either/or choice.
  4. Caching data that's rarely re-read, gaining little from cache-aside's "populate on demand" benefit while still paying the cache-write cost on every miss - caching is a trade specifically worthwhile for data that's read significantly more often than it changes; applying it indiscriminately to write-heavy or rarely-reread data can add overhead without a corresponding benefit.
  5. Assuming a cache hit always means correct, current data. A cache-aside hit only guarantees the data was correct as of whenever it was cached - if invalidation logic has any gap (a missed code path, a race condition), a "hit" can just as easily return confidently-wrong data as a genuine up-to-date value; the cache itself has no way to distinguish the two.
