5.5 Security: SSL/TLS

Objective: explain the TLS handshake and why HTTPS provides confidentiality, integrity, and (server) authenticity.

TLS (Transport Layer Security, the modern successor to SSL) establishes an encrypted, authenticated connection between a client and server over an otherwise-insecure network, via a "handshake" that: negotiates encryption algorithms both sides support; has the server prove its identity via a digital certificate (signed by a trusted Certificate Authority); and establishes a shared symmetric session key - used for the actual bulk data encryption for the rest of the connection - using asymmetric (public-key) cryptography specifically for this key-exchange step.

Plain English - the common confusion this answers ("why does HTTPS use both asymmetric AND symmetric crypto?"): asymmetric crypto (public/private key pairs) solves "we've never met and share no secret, yet need to establish one securely" - but it's computationally slow, unsuitable for encrypting a whole conversation's worth of data. Symmetric crypto (one shared key both sides know) is fast enough for bulk data, but requires that shared key to already exist. TLS uses asymmetric crypto only for the brief handshake moment of securely agreeing on a symmetric key, then switches entirely to the fast symmetric method for actual data transfer.

Analogy: handing a stranger a locked box and its key without an eavesdropper being able to open it. You can't shout the key across a crowded room. Asymmetric crypto is a one-way mailbox (public key) anyone can drop a locked message into, but only the intended recipient (holding the private key) can open - used exactly once, to securely hand over a regular, fast-to-use physical key (the symmetric session key). From then on, both sides just use that ordinary key directly - much faster than mailing every message through the special one-way mailbox.

TLS handshake, step by step:

  1. ClientHello: client sends supported TLS versions, cipher suites, a random number.
  2. ServerHello: server picks a cipher suite, sends its own random number and its certificate (containing its public key, signed by a trusted CA).
  3. Client verifies the certificate - signed by a trusted CA, matches the domain, not expired/revoked.
  4. Client generates a "pre-master secret," encrypts it with the server's public key, sends it - only the server's private key can decrypt it, proving the server is who it claims (asymmetric crypto used here).
  5. Both sides independently derive the same symmetric session key from the pre-master secret plus both exchanged random numbers.
  6. Both switch to symmetric encryption using that session key for everything after - fast, and secure since only the two parties who participated in the handshake could have derived that key.

Why asymmetric for the handshake, symmetric for the data: asymmetric crypto (RSA/ECDHE-style key exchange) is orders of magnitude slower per byte than symmetric crypto (AES-style). Using it for an entire HTTPS session's worth of data (potentially megabytes) would be prohibitively slow; using it only for the brief handshake (a tiny amount of data) to securely bootstrap a symmetric key is the practical sweet spot - secure key establishment with no pre-shared secret, plus fast bulk transfer afterward.

Seeing it happen locally. Generate a self-signed certificate (a certificate you sign yourself instead of a real CA - browsers will warn "not trusted," but it's enough to exercise the handshake mechanics locally):

openssl req -x509 -newkey rsa:2048 -keyout key.pem -out cert.pem -days 365 -nodes
# -x509: output a certificate directly (not a signing request)
# -newkey rsa:2048: generate a new 2048-bit RSA key pair alongside it
# -keyout / -out: where the private key and certificate get written

Serve something over it, and inspect the actual handshake from the outside:

python3 -m http.server 8443 --bind 127.0.0.1  # (a real app would wrap its socket in ssl.wrap_socket, shown below)
openssl s_client -connect localhost:8443 -showcerts   # dumps the negotiated cipher suite and the certificate chain

Wrapping a raw Python socket in TLS directly, to see where the handshake actually happens in code:

import ssl, socket

context = ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER)
context.load_cert_chain(certfile="cert.pem", keyfile="key.pem")

with socket.create_server(("localhost", 8443)) as sock:
    with context.wrap_socket(sock, server_side=True) as tls_sock:
        # everything after wrap_socket() has already been through
        # ClientHello -> ServerHello -> certificate exchange -> session key derivation --
        # by the time this line runs, the handshake from steps 1-6 above is already complete
        conn, addr = tls_sock.accept()
