5.3 Idempotency & Reliable APIs

Objective: design and implement idempotent API endpoints that behave correctly under retries and duplicate requests.

An operation is idempotent if performing it multiple times produces the same result/effect as performing it exactly once - the server-side state ends up identical regardless of how many times an identical request was actually processed. This matters because network failures make retries common and often unavoidable - a client that doesn't receive a response genuinely cannot tell whether the original request succeeded before the response was lost. By HTTP spec, GET, PUT, DELETE are idempotent; POST is not idempotent by definition - each POST conventionally creates a new resource/side effect, so naive retries create duplicates (a duplicate charge, a duplicate order).

Plain English: if a "charge payment" endpoint is called once and the response is lost in transit before the client sees it, the client cannot tell whether the charge actually succeeded server-side. Naively retrying a plain, non-idempotent POST - if the first request did succeed - charges the customer twice. Idempotency-key design fixes this: the client generates a unique key for a given logical operation (a UUID generated once per checkout attempt, reused across retries of that same attempt), sends it with the request, and the server remembers which keys it has already processed and what it returned - a repeat key returns the original result without re-executing the side effect.

Analogy: a numbered claim ticket at a dry cleaner - if you lose your receipt and ask again showing the same ticket number, the clerk checks their records, sees it was already processed, and does not process your clothes (or charge you) a second time - they just hand back the same status as before. Without a ticket number, the clerk can't distinguish "genuinely new drop-off" from "same person asking again," and might process it twice by mistake.

import uuid

processed_requests = {}   # idempotency_key -> stored result (in reality: a shared DB/Redis)

def charge_payment(idempotency_key, amount, account):
    if idempotency_key in processed_requests:
        return processed_requests[idempotency_key]    # already handled -- same result, no re-charge
    result = actually_charge(account, amount)             # the real side effect, executed exactly once
    processed_requests[idempotency_key] = result
    return result

key = str(uuid.uuid4())                       # ONE key per logical checkout attempt
charge_payment(key, 49.99, "account_123")       # first call: actually charges
charge_payment(key, 49.99, "account_123")        # retry, SAME key: returns cached result, no double-charge

Why the key must be generated once per logical attempt, not once per HTTP request: if the client generated a new key on every retry, the server would see each retry as a genuinely new, never-seen-before operation, defeating the entire mechanism - the whole point is that repeated requests representing the same underlying intent ("this one checkout") share the same key, so the server can recognize them as duplicates of each other. The key's scope is "one logical operation, however many times it's physically retried," not "one network request."

Why GET/PUT/DELETE are idempotent by HTTP's own definition, mechanically: GET never changes state, so repeating it trivially produces the same result. PUT means "replace this resource with exactly this representation" - applying the identical replacement twice leaves the resource in the identical final state both times. DELETE means "this resource should not exist" - deleting an already-deleted resource still leaves it in the same "doesn't exist" end state (even if the response differs, e.g. 200 the first time, 404 the second - the underlying server state converges to the same outcome either way). POST has no such built-in convergence guarantee - by convention it means "create a new thing," and "create a new thing" executed twice naturally produces two things, not one.

Making it safe under concurrency: the check-and-store step must be atomic (a DB unique constraint on the key, or a Redis SETNX-style atomic check) - a naive check-then-store (not atomic) has a race condition where two concurrent requests with the same key could both pass the "not yet processed" check before either has stored its result, both proceeding to charge. Testing this by firing the same request twice concurrently and asserting only one side effect occurs is specifically designed to catch this class of bug.

Why "check, then store" as two separate steps is unsafe, concretely: imagine two retries of the same request arrive at nearly the same instant. Both read processed_requests and both see the key is absent (neither has stored anything yet), so both conclude "this hasn't been processed" and both proceed to call actually_charge - resulting in exactly the double-charge idempotency was supposed to prevent, despite the code technically checking for a duplicate. An atomic "insert this key only if it doesn't already exist, and tell me whether the insert succeeded" operation (a DB unique constraint violation, or Redis's SETNX) closes this gap by making the check-and-claim a single, indivisible operation that only one of the two concurrent requests can win.

Common mistakes & misconceptions

  1. Generating a new idempotency key on every retry instead of reusing the same key across retries of the same logical operation - as explained above, this defeats the mechanism entirely, since the server has no way to recognize the retries as duplicates of each other.
  2. Implementing the check-and-store step as two separate, non-atomic operations, introducing exactly the race condition described above - this is the single most consequential subtlety in this entire lesson, and it's precisely why the checkpoint's concurrent-firing test is designed the way it is (a sequential test wouldn't catch this bug at all).
  3. Assuming POST can never be made safe to retry. POST isn't idempotent by default, but the idempotency-key pattern is exactly the standard technique for making a POST-based operation safely retryable - the HTTP method's default semantics and what a well-designed API actually guarantees are two different things.
  4. Believing idempotency means "the request has no side effects." It specifically means repeated identical requests have the same cumulative effect as one - the operation can absolutely have a real side effect (a genuine one-time charge, a genuine resource creation) the first time; idempotency is about what happens on the 2nd, 3rd, etc. identical request, not about avoiding side effects altogether.
  5. Storing idempotency keys with no expiration, letting the tracking store grow unboundedly forever - in practice, idempotency keys typically need a bounded retention window (long enough to cover realistic retry scenarios, short enough to not accumulate indefinitely), a detail easy to overlook when focused only on the core mechanism.
  6. Testing idempotency only with sequential (not concurrent) duplicate requests. As stressed above, a sequential test can pass even with a check-then-store race condition present, since the two calls never actually overlap in time - only a genuinely concurrent test exercises the race condition the atomic-check requirement exists to prevent.
