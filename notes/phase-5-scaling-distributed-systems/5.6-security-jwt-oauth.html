5.6 Security: JWT & OAuth

Objective: implement JWT-based authentication and understand OAuth 2.0's authorization flows well enough to explain why JWT and OAuth solve different (complementary) problems.

5.6a JWT

A JWT (JSON Web Token) is a self-contained, digitally signed token encoding claims (user_id, expiration, roles) as a compact string: HEADER.PAYLOAD.SIGNATURE, each base64-encoded, with the signature computed over header+payload using a secret/private key known only to the issuer. A server can verify a JWT's authenticity and integrity without any database/session lookup, since all necessary information - and proof of authenticity - is self-contained in the token.

Plain English: traditional session-based auth stores a random session ID in a cookie, and the server must look that ID up in a DB/session store on every request. A JWT instead carries the user's identity/claims directly, cryptographically signed so the server trusts it wasn't tampered with, with no server-side lookup - attractive for stateless, horizontally-scaled systems (any server instance verifies independently, no shared session store needed). The trade-off: since nothing is looked up server-side, you can't just "delete a session" to revoke it early - the token stays valid until it naturally expires, unless a revocation/blocklist is added back in.

Analogy: a traditional session ID is a coat-check ticket - meaningless by itself; the attendant (server) looks up which coat (session data) it corresponds to every time. A JWT is a sealed, tamper-evident ID card carrying your actual info printed directly on it, with an official security seal (the signature) - anyone with the right verification tool checks the seal and reads the info off the card directly, no calling back to a central database - but revoking a lost/stolen card early needs a separate revocation list, since there's no "erasing" it directly.

import jwt
import datetime

SECRET_KEY = "your-secret-key"    # in reality: a secrets manager, not a literal

def create_token(user_id):
    payload = {
        "user_id": user_id,
        "exp": datetime.datetime.utcnow() + datetime.timedelta(hours=1)
    }
    return jwt.encode(payload, SECRET_KEY, algorithm="HS256")

def verify_token(token):
    try:
        return jwt.decode(token, SECRET_KEY, algorithms=["HS256"])
    except jwt.ExpiredSignatureError:
        raise HTTPException(status_code=401, detail="Token expired")
    except jwt.InvalidTokenError:
        raise HTTPException(status_code=401, detail="Invalid token")

Why the signature, not the base64 encoding, is what actually protects a JWT from tampering: base64 is just an encoding, not encryption or protection - anyone can decode a JWT's header and payload and read them directly (JWTs are not secret/confidential by default, only tamper-evident). The signature is what prevents a client from, say, editing the payload to change user_id or add an admin role: since the signature is computed from the original header+payload using a secret only the server knows, any modification to the payload would no longer match the signature, and jwt.decode would reject it as invalid. This distinction - "readable but not forgeable" - is the single most important thing to understand about how JWTs actually protect data.

What happens when a protected endpoint receives an expired token, step by step: (1) client sends the request with the expired JWT; (2) server calls jwt.decode(), which checks the exp claim against current time as part of validity checking; (3) since exp is in the past, decode raises ExpiredSignatureError; (4) server catches it, returns 401 (not 403 - the client isn't "forbidden," they need to re-authenticate); (5) client, seeing 401, typically attempts a refresh token flow (a separate, longer-lived token used to obtain a new short-lived access token) rather than forcing a full re-login.

Why short-lived access tokens plus a separate refresh token is the standard pattern, rather than one long-lived token: a short expiry limits how long a stolen token remains useful to an attacker (the exact same "bound the damage" logic as a TTL-based cache, 5.1b, applied to security instead of staleness) - if an access token leaks, it's only dangerous for its short window. The refresh token, used far less frequently and typically kept more securely, lets the client obtain fresh access tokens without forcing the user to fully re-authenticate every hour, balancing security (short-lived exposure window) against user experience (no constant re-login).

5.6b OAuth 2.0

OAuth 2.0 is an authorization protocol (not authentication) letting a user grant a third-party application limited access to their resources on another service, without ever sharing their password with that third-party app. The user authenticates directly with the resource owner's service (logs into Google directly, not the third-party app), which then issues a scoped access token to the third-party app.

Plain English - the key confusion: JWT is a token format (encoding and signing claims compactly). OAuth is a protocol/flow describing how an app gets permission to act on a user's behalf in the first place. Often used together (OAuth's access tokens are frequently implemented as JWTs) but they solve different problems.

Analogy: a hotel guest (the user) authorizing valet parking (a third-party app) to access their car specifically, without handing over their house keys (password) - the guest gets a limited-scope valet key from the hotel (the resource owner's service) that only starts the car and opens the trunk, nothing else, and typically only works for the length of their stay. The valet never has the house key, and its capability is deliberately restricted to exactly what's needed.

Authorization Code flow (the most common):

  1. Third-party app redirects the user to the resource owner's login page ("Login with Google").
  2. User logs in directly with Google; Google asks "grant [App] access to [specific scopes]?"
  3. User approves.
  4. Google redirects back with a short-lived authorization code.
  5. The app exchanges that code (server-to-server, using its own registered client secret) for an access token (often plus a refresh token).
  6. The app uses the access token for scoped API calls on the user's behalf - at no point does it ever see the user's actual Google password.
import requests

def exchange_code_for_token(auth_code, client_id, client_secret, redirect_uri):
    response = requests.post("https://oauth-provider.com/token", data={
        "grant_type": "authorization_code",
        "code": auth_code,
        "client_id": client_id,
        "client_secret": client_secret,
        "redirect_uri": redirect_uri,
    })
    return response.json()   # {"access_token": "...", "expires_in": 3600, "refresh_token": "..."}

Why the code-for-token exchange happens server-to-server (step 5), rather than the browser directly receiving the access token: the authorization code from step 4 is exchanged for the actual access token using the app's client_secret - a credential that must never be exposed to the browser/client-side code, since anyone who obtained it could impersonate the app itself. Routing the final token exchange through a server-to-server call (rather than returning the access token directly in the browser redirect) keeps that secret confined to a context an attacker with browser access can't reach - this is precisely why the Authorization Code flow, not a simpler "just redirect back with the token," is the standard, more secure pattern.

Why "scoped" access matters as much as "without sharing the password": even without ever seeing the user's password, an access token that grants unrestricted access to the entire account would still be a huge liability if leaked. OAuth's scope mechanism (the "grant [App] access to [specific scopes]" consent step) lets the user approve access to exactly what's needed (e.g. "read your calendar," not "do anything as you") - limiting the blast radius of what a compromised or overreaching third-party app could actually do, independent of the password-sharing protection.

Why complementary, not competing: a real system commonly uses OAuth to obtain a user's authorization for a third-party app, where the resulting access token happens to be a JWT (verifiable statelessly, per 5.6a). OAuth defines the flow of getting that token issued with the right scope/consent; JWT defines the format of the token itself once issued.

Common mistakes & misconceptions

  1. Believing base64 encoding provides confidentiality for a JWT's contents. As emphasized above, base64 is trivially decodable by anyone - a JWT's claims are readable, not secret, by default. Never put genuinely sensitive data (passwords, secrets) directly into a JWT payload expecting it to be hidden; the signature protects against tampering, not disclosure.
  2. Confusing JWT and OAuth as competing or interchangeable technologies, when they solve genuinely different problems at different layers - JWT is a token format, OAuth is an authorization flow/protocol, and they're frequently used together rather than as alternatives to each other.
  3. Believing OAuth is fundamentally about authentication ("logging the user in"), when it's specifically about authorization (granting scoped access to resources). A related but distinct protocol, OpenID Connect, is built on top of OAuth 2.0 specifically to add a standardized authentication layer - conflating the two is a very common but consequential mix-up.
  4. Issuing a single long-lived token instead of the short-lived-access-token-plus-refresh-token pattern, losing the "bound the damage window" security benefit explained above in exchange for slightly simpler implementation - a real trade-off, but one that should be made deliberately, not by default.
  5. Returning the OAuth access token directly to the browser/client-side code instead of exchanging the authorization code server-to-server. As explained above, this is precisely the security property the Authorization Code flow's extra step is designed to protect - skipping it (an "implicit flow"-style shortcut, now generally discouraged) exposes tokens to a context with a larger attack surface.
  6. Assuming a JWT is automatically invalid the instant something about the user changes (e.g. their role is revoked). Since JWT verification is entirely self-contained and stateless, a previously-issued token with the old role remains valid (and would still pass verification) until it naturally expires, unless the system specifically implements a revocation/blocklist mechanism to check against - a subtlety worth being explicit about since it's the direct trade-off for avoiding server-side session lookups in the first place.
