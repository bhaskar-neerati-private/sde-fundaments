5.4 Message Queues & Streaming

Objective: understand the difference between a message queue (RabbitMQ) and a distributed log (Kafka), and when to use each; implement a basic producer/consumer.

5.4a Message Queues (RabbitMQ)

A message queue follows a "to-do list" model - a producer publishes a message onto a queue, a consumer receives and processes it, and once acknowledged, the message is removed from the queue. Each message is intended to be consumed and handled by (typically) exactly one consumer, once, then it's gone.

Plain English: this decouples the producer from needing the consumer to be immediately available/fast - the producer drops the message and moves on; the consumer processes it whenever ready, at its own pace. Great for offloading slow/non-critical work off the main request path (e.g. "send a confirmation email" doesn't need to block the API response that created the order).

Analogy: a physical to-do whiteboard - someone writes a task up (produces a message), whoever's free crosses it off once done (consumes and acknowledges it) - once crossed off, it's gone. If multiple people watch the same board, whoever gets to a task first handles it, and it disappears for everyone else - not duplicated across workers by default.

import pika

# producer
connection = pika.BlockingConnection(pika.ConnectionParameters('localhost'))
channel = connection.channel()
channel.queue_declare(queue='email_tasks')
channel.basic_publish(exchange='', routing_key='email_tasks', body='send_confirmation:order_123')

# consumer (separate process)
def callback(ch, method, properties, body):
    send_confirmation_email(body)
    ch.basic_ack(delivery_tag=method.delivery_tag)   # acknowledge -- removes it from the queue

channel.basic_consume(queue='email_tasks', on_message_callback=callback)
channel.start_consuming()

5.4b Distributed Logs (Kafka)

A distributed log is a fundamentally different model: messages are appended to a durable, ordered log (a "topic," split into partitions) and are not removed once consumed - they persist for a configured retention period, and multiple independent consumer groups can each read (and replay) the same messages at their own pace, tracking their own read position ("offset") independently.

Plain English: RabbitMQ assumes a message is for exactly one consumer, once, then gone. Kafka is closer to a shared, append-only broadcast recording - many different downstream systems can each independently read (and replay from an earlier point) the same event stream, without affecting what any other consumer sees. Suited to "many systems need to react to the same event" (an "order placed" event triggering inventory updates and analytics and email and fraud detection, each an independent consumer on the same stream) rather than "exactly one worker handles this one task."

Analogy: RabbitMQ is a physical to-do task, erased once done. Kafka is a public, permanent broadcast recording (a podcast episode) - many listeners tune in at different times, some live, some catching up, some re-listening - the recording doesn't disappear because one listener finished it, and each tracks their own progress independently.

from kafka import KafkaProducer, KafkaConsumer

producer = KafkaProducer(bootstrap_servers='localhost:9092')
producer.send('order_events', b'order_placed:order_123')

# consumer group "inventory-service" -- tracks its OWN offset independently
consumer = KafkaConsumer('order_events', group_id='inventory-service', bootstrap_servers='localhost:9092')
for message in consumer:
    update_inventory(message.value)

# a SEPARATE consumer group "analytics-service" reads the SAME topic independently,
# at its own pace, without affecting inventory-service's progress

Choosing between them: a queue (RabbitMQ) when a task should be handled by exactly one worker, once, with no need to replay it later. Kafka when multiple independent systems need to react to the same event stream, or when replaying historical events (rebuilding a downstream system's state by re-reading the whole log) is a genuine requirement.
