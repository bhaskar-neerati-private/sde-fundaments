4.3 Creational Design Patterns

Objective: implement Singleton, Factory Method, and Builder in Python, and know when each is actually warranted vs. over-engineering.

4.3a Singleton & Factory Method

Singleton: ensures a class has exactly one instance throughout the application's lifetime, with a global access point to it. Useful when exactly one shared instance genuinely makes sense (a single config object, a connection pool) - but often overused, since it introduces global mutable state (harder testing, hidden dependencies). Consider whether plain dependency injection (4.2c) is cleaner than a global singleton.

class Singleton:
    _instance = None
    def __new__(cls, *args, **kwargs):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance

config1, config2 = Singleton(), Singleton()
assert config1 is config2

# more Pythonic alternative: a MODULE is a singleton by default in Python.
# config.py: settings = {"debug": True}
# elsewhere: from config import settings -- everyone shares the same dict object, no class needed

Factory Method: delegates object creation to a separate method, letting it decide which concrete class to instantiate based on input, without the caller needing to know the concrete class names.

Analogy: Singleton is a country having exactly one currently-serving president - a fixed global access point. Factory Method is a restaurant order window - you name the dish, the kitchen decides internally which chef/recipe produces it; you never need to know how.

class Shape:
    def draw(self): raise NotImplementedError
class Circle(Shape):
    def draw(self): return "drawing a circle"
class Square(Shape):
    def draw(self): return "drawing a square"

def shape_factory(shape_type):
    shapes = {"circle": Circle, "square": Square}
    if shape_type not in shapes:
        raise ValueError(f"unknown shape: {shape_type}")
    return shapes[shape_type]()

shape = shape_factory("circle")     # caller never references the Circle class directly

4.3b Builder

Constructs a complex object step by step, via chained method calls (a "fluent interface") each setting one piece of configuration, culminating in a build() call - used instead of a constructor with many optional parameters (the "telescoping constructor" problem).

Plain English: a constructor with 10 optional parameters becomes unreadable and error-prone at the call site. A Builder lets you set only the pieces you care about, by name, one call at a time, in any order, assembling the final object only when explicitly asked.

Analogy: ordering a custom sandwich by naming each ingredient one at a time at a deli counter ("add turkey", "hold the mayo", "done") rather than filling out one giant form with 15 boxes in a fixed order, where getting the order wrong gives you the wrong sandwich.

class HttpRequest:
    def __init__(self):
        self.url = None
        self.method = "GET"
        self.headers = {}
        self.body = None

class HttpRequestBuilder:
    def __init__(self):
        self._request = HttpRequest()

    def url(self, url):
        self._request.url = url
        return self                     # returns self -- enables chaining

    def method(self, method):
        self._request.method = method
        return self

    def header(self, key, value):
        self._request.headers[key] = value
        return self

    def body(self, body):
        self._request.body = body
        return self

    def build(self):
        return self._request

request = (HttpRequestBuilder()
    .url("https://api.example.com/users")
    .method("POST")
    .header("Content-Type", "application/json")
    .body('{"name": "Alice"}')
    .build())
