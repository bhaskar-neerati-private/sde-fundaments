4.2 SOLID Principles

Objective: identify SOLID violations in real code and fix them - not just recite the five letters.

4.2a Single Responsibility & Open/Closed

Single Responsibility Principle (SRP): a class should have only one reason to change - responsible for one part/concern of the system, not several unrelated ones bundled together.

Plain English: if a class handles pay calculation and report formatting and database persistence, a change to any of those three unrelated concerns (a tax rule, a report format, a DB switch) forces editing this one class - and each change is driven by a different stakeholder, meaning multiple reasons to change. Split each concern into its own class.

Analogy: an employee whose job description is "accountant AND graphic designer AND database administrator" - three unrelated departments can each demand changes to this one role, and a change for one risks breaking something for another, purely because they were bundled into one job that should've been three.

Open/Closed Principle (OCP): software entities should be open for extension, closed for modification - add new behavior without editing existing, already-tested code.

# violates SRP
class Employee:
    def calculate_pay(self): ...
    def format_report(self): ...
    def save_to_db(self): ...

# SRP fix
class PayCalculator:
    def calculate_pay(self, employee): ...
class ReportFormatter:
    def format_report(self, employee): ...
class EmployeeRepository:
    def save(self, employee): ...

# violates OCP -- adding a new discount type means editing this function
def calculate_discount(customer_type, amount):
    if customer_type == "regular": return amount * 0.95
    elif customer_type == "vip": return amount * 0.90
    # a new case means editing existing, already-tested code

# OCP fix -- extend via new classes, don't modify existing ones
class DiscountStrategy:
    def apply(self, amount): raise NotImplementedError
class RegularDiscount(DiscountStrategy):
    def apply(self, amount): return amount * 0.95
class VIPDiscount(DiscountStrategy):
    def apply(self, amount): return amount * 0.90
class EmployeeDiscount(DiscountStrategy):    # NEW -- added without touching existing classes
    def apply(self, amount): return amount * 0.80

Why "editing existing, already-tested code" is specifically the risk OCP targets, not just extra typing: every time working code is modified, there's a real chance of introducing a regression - even a change that looks purely additive (adding an elif branch) recompiles/re-executes the entire function, meaning existing branches are re-exposed to risk from a change that was only supposed to affect the new case. The DiscountStrategy fix eliminates this risk structurally: adding EmployeeDiscount never requires touching RegularDiscount or VIPDiscount's code at all, so there's no path by which the new addition could accidentally break the old, already-verified behavior.

4.2b Liskov Substitution & Interface Segregation

Liskov Substitution Principle (LSP): objects of a subclass must be substitutable for objects of the superclass without breaking program correctness - a subclass shouldn't strengthen preconditions, weaken postconditions, or otherwise violate behavior callers reasonably expect. This is the formal name for 4.1's Penguin/fly() problem - if code written against the parent's promised behavior breaks when handed a child instance, LSP is violated, even if it type-checks fine.

Interface Segregation Principle (ISP): clients shouldn't be forced to depend on methods they don't use - prefer several small, specific interfaces over one large, general-purpose one.

# violates LSP
class Rectangle:
    def __init__(self, w, h): self.w, self.h = w, h
    def set_width(self, w): self.w = w
    def set_height(self, h): self.h = h
    def area(self): return self.w * self.h

class Square(Rectangle):
    def set_width(self, w): self.w = self.h = w      # forces height to match --
    def set_height(self, h): self.w = self.h = h       # breaks the parent's "set independently" assumption

def resize(rect):
    rect.set_width(5); rect.set_height(4)
    assert rect.area() == 20     # passes for Rectangle, FAILS for Square (area=16) -- LSP violated

# violates ISP -- one bloated interface
class Worker:
    def work(self): ...
    def eat(self): ...
    def sleep(self): ...

class RobotWorker(Worker):
    def work(self): return "working"
    def eat(self): raise NotImplementedError("robots don't eat")     # forced, meaningless
    def sleep(self): raise NotImplementedError("robots don't sleep")

# ISP fix -- split into role-specific interfaces
class Workable:
    def work(self): ...
class Eatable:
    def eat(self): ...
class Sleepable:
    def sleep(self): ...

class RobotWorker(Workable):                 # only depends on what it needs
    def work(self): return "working"
class HumanWorker(Workable, Eatable, Sleepable):
    def work(self): return "working"
    def eat(self): return "eating"
    def sleep(self): return "sleeping"

Why the Rectangle/Square example is the canonical LSP violation, worth understanding precisely, not just memorizing: mathematically, a square genuinely is a special case of a rectangle (equal width and height) - the "is-a" relationship is true in the same sense the Penguin/Bird one was. The violation is specifically that Rectangle's interface implicitly promises "width and height can be set independently of each other," and Square cannot honor that promise without breaking its own defining constraint (width must always equal height). This is the exact same lesson as 4.1's composition discussion, restated with a formal name and a concrete, testable failure (resize breaking for Square but not Rectangle) - LSP violations are found by asking "does code written trusting the parent's contract still work correctly when handed any subclass instance," and the resize function here is precisely that kind of trust-testing code.

Why ISP is really just SRP applied to interfaces rather than classes: a bloated Worker interface forces every implementer to either genuinely support every method, or fake/raise on the ones that don't apply - the same "bundling unrelated concerns" problem SRP addresses for classes, here appearing as unrelated capabilities bundled into one interface that not every implementer actually needs.

4.2c Dependency Inversion

Dependency Inversion Principle (DIP): high-level modules should not depend on low-level modules - both should depend on abstractions; abstractions should not depend on details, details should depend on abstractions. This is the principle that makes the other four actually enforceable in practice.

Plain English: if high-level business logic directly instantiates a specific low-level implementation (a specific database class), you can't swap it without editing the high-level code (violating OCP), and can't test the high-level logic in isolation (stuck with the real database). Instead, high-level code depends on an abstract interface ("something that can save data"), and the specific implementation is plugged in from outside (dependency injection).

Analogy: a wall socket (the abstraction) vs. wiring a lamp directly into the house's wiring (a concrete dependency). Appliances don't hard-wire to one specific power plant's wiring - they plug into a standardized socket, and the power source behind it can change (generator, solar, battery) without the appliance ever needing rewiring.

# violates DIP
class MySQLDatabase:
    def save(self, data): print(f"Saving {data} to MySQL")

class OrderService:
    def __init__(self):
        self.db = MySQLDatabase()      # hard-wired to one specific implementation
    def place_order(self, order):
        self.db.save(order)

# DIP fix -- depend on an abstraction, inject the concrete implementation
class Database:                          # abstraction
    def save(self, data): raise NotImplementedError

class MySQLDatabase(Database):
    def save(self, data): print(f"Saving {data} to MySQL")
class PostgresDatabase(Database):          # swap freely -- OrderService never changes
    def save(self, data): print(f"Saving {data} to Postgres")

class OrderService:
    def __init__(self, db: Database):        # depends on the ABSTRACTION
        self.db = db
    def place_order(self, order):
        self.db.save(order)

order_service = OrderService(PostgresDatabase())    # swap without touching OrderService

Why DIP is described as "the principle that makes the other four actually enforceable": OCP asks for extension without modification - but if OrderService is hard-wired to MySQLDatabase, swapping databases requires modifying OrderService, violating OCP in practice even if nothing else about the design is wrong. DIP's "depend on abstractions" is the specific mechanical technique that makes OCP achievable for this kind of dependency, and it's also exactly what makes unit testing OrderService in isolation possible (inject a fake/mock Database instead of needing a real one).

Common mistakes & misconceptions

  1. Treating SRP as "a class should only have one method." SRP is about reasons to change (which stakeholder/concern drives modification), not method count - a class can have several closely-related methods, all serving one cohesive responsibility, and still fully satisfy SRP.
  2. "Fixing" OCP violations by adding more if/elif branches "for now" and promising to refactor later. Every new branch is itself evidence the design isn't actually open for extension - the fix (a strategy/polymorphism-based design, as shown above) should be applied as soon as the pattern of "editing this same function for every new case" becomes visible, not deferred indefinitely.
  3. Believing LSP is only about method signatures matching (which static type checkers enforce automatically). As the Rectangle/Square example shows, LSP violations can type-check perfectly fine while still breaking behavioral expectations - LSP is fundamentally a semantic/behavioral contract, not just a structural/type-signature one, and no type checker alone can catch it.
  4. Designing one large "god interface" and treating ISP violations as acceptable "because most implementers will need most methods eventually." Even a genuinely common case (most implementers need most methods) doesn't justify forcing the exceptions to fake or reject the methods they don't need - ISP specifically protects against exactly that awkward middle ground.
  5. Confusing "dependency injection" (a technique - passing dependencies in from outside) with "Dependency Inversion Principle" (a design principle - depend on abstractions, not concretions). Dependency injection is one common mechanism for satisfying DIP, but the principle itself is about the direction of the dependency (on an abstraction, not a concrete detail) - not merely about where an object gets constructed.
  6. Applying all five SOLID principles maximally everywhere, regardless of actual need. Like normalization (2.1) and DIP itself, these are tools for managing change and complexity - a small, stable script with no anticipated variation gains little from an elaborate abstraction layer, and over-applying SOLID to code that will never need that flexibility is itself a design mistake (unnecessary indirection with no corresponding benefit).
