4.9 HLD Case Studies

Objective: apply the 4.8 fundamentals to design an end-to-end system under realistic constraints - the actual shape of a system design interview.

4.9a Case Study: URL Shortener

Requirements gathering. Functional: shorten a long URL; redirect a short URL to the original; optionally custom aliases, expiration, analytics. Non-functional: high availability, low redirect latency, scale for read (redirect) volume typically >> write (shorten) volume.

Back-of-envelope estimate: e.g. 100M new URLs/month → ~40 writes/sec average; reads often 100x writes → ~4,000 reads/sec average, spikier at peak. Storage: 100M/month × ~500 bytes × 12 months (5-year retention) → tens of GB - easily fits; this is a throughput problem, not a storage-capacity one.

API design: POST /shorten {long_url} -> {short_url}; GET /{short_code} -> 302 redirect to long_url.

counter = 0   # in reality: a coordinated/pre-allocated counter, not a single in-process variable

def base62_encode(n):
    chars = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz"
    if n == 0: return chars[0]
    result = ""
    while n:
        n, rem = divmod(n, 62)
        result = chars[rem] + result
    return result

@app.post("/shorten")
def shorten(long_url: str):
    global counter
    counter += 1
    short_code = base62_encode(counter)          # e.g. 1 -> "1", 1000000 -> "4c92"
    db.save(short_code, long_url)
    return {"short_url": f"https://short.ly/{short_code}"}

@app.get("/{short_code}")
def redirect(short_code: str):
    long_url = cache.get(short_code) or db.get(short_code)   # cache-aside, per 5.1a
    if long_url is None:
        raise HTTPException(status_code=404)
    return RedirectResponse(long_url, status_code=302)

High-level architecture: client → load balancer → stateless app servers (horizontally scaled, 4.8a) → cache (hot short codes cached, since reads >> writes - foreshadowing Phase 5) → database (short_code -> long_url) + an ID-generation approach (base62-encoding an auto-incrementing counter, or a dedicated ID-generation service, to avoid collisions).

Database choice, justified: a simple key-value store fits well (DynamoDB/Redis-backed) since access is almost purely exact-key lookup, no complex relational queries needed - though a relational DB works fine at this scale too; the choice matters more at larger scale, where NoSQL's sharding-friendly horizontal scalability (4.8b) becomes the deciding factor.

Trade-off worth naming: base62-encoding a counter is simple but needs a centralized/coordinated counter - a potential bottleneck at very high write volume. Pre-generated ID pools handed to app servers in batches avoid that contention.

4.9b Case Study: Rate Limiter

Requirements: limit how many requests a client can make in a time window (e.g. 100 requests/minute per API key), reject excess (typically 429 Too Many Requests).

Algorithms - the actual LLD-relevant core:

  • Fixed window counter: count requests in a fixed time bucket, reset at each boundary. Simple, but allows bursts right at boundaries (100 requests at 11:59:59 and another 100 at 12:00:00 = 200 in 2 seconds, technically within "two windows' limits" but violating the spirit of "100/minute").
  • Sliding window log: track exact timestamps of each request, count how many fall within the last 60 seconds from now - accurate, but memory cost grows with request volume.
  • Token bucket: a bucket holds tokens, refilled at a steady rate up to a max capacity; each request consumes one token, rejected if none remain. Allows brief bursts (up to bucket capacity) while enforcing a steady average rate - a common practical middle ground.

Analogy (token bucket): a movie-ticket booth handing out a new ticket every few seconds (steady refill) into a tray holding at most 10 at once (capacity) - customers take a ticket to enter; empty tray means waiting for the next refill. This naturally allows a small burst if tickets accumulated (nobody entering for a while), while capping the long-run average rate to the refill rate.

import time

class TokenBucket:
    def __init__(self, capacity, refill_rate_per_sec):
        self.capacity = capacity
        self.tokens = capacity                 # starts full
        self.refill_rate = refill_rate_per_sec
        self.last_refill = time.monotonic()

    def _refill(self):
        now = time.monotonic()
        elapsed = now - self.last_refill
        self.tokens = min(self.capacity, self.tokens + elapsed * self.refill_rate)
        self.last_refill = now

    def allow_request(self):
        self._refill()
        if self.tokens >= 1:
            self.tokens -= 1
            return True                          # request allowed
        return False                              # 429 Too Many Requests

bucket = TokenBucket(capacity=10, refill_rate_per_sec=100/60)   # 100 requests/minute, burst up to 10
if not bucket.allow_request():
    raise HTTPException(status_code=429, detail="Rate limit exceeded")

Where rate-limit state lives: a per-server in-memory counter lets each server enforce only its own local limit, undercounting the true global rate across the fleet - so a shared, low-latency store (typically Redis - foreshadowing Phase 5's caching lessons) tracks counts/tokens centrally, checked/updated on every request.
