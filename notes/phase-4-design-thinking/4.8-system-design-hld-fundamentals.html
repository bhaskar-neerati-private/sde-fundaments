4.8 System Design / HLD Fundamentals

Objective: understand the core building blocks of scalable systems - load balancing, horizontal vs. vertical scaling, replication/sharding, CAP theorem - well enough to use them as vocabulary, not just define them.

4.8a Scaling Basics: Vertical/Horizontal & Load Balancers

Vertical scaling ("scaling up") increases a single server's capacity (more CPU/RAM/disk, same machine). Horizontal scaling ("scaling out") adds more servers running the same application, distributing load across them. A load balancer sits in front of multiple servers, distributing incoming requests (round-robin, least-connections, weighted) so no single server is overwhelmed, and routes around unhealthy servers.

Plain English: vertical scaling is simple (no architecture changes) but has a hard ceiling (there's a biggest machine you can buy) and is a single point of failure (one machine, one outage = total outage). Horizontal scaling has no theoretical ceiling and improves fault tolerance - but requires the application to actually support multiple instances (no reliance on server-local state other instances can't see) and needs a load balancer to actually spread traffic.

Analogy: vertical scaling is upgrading to a bigger cash register at one checkout counter - handles more transactions per minute, but if it breaks, the entire store's checkout stops. Horizontal scaling is opening several more independent counters - one breaking doesn't stop the others - but now someone has to direct customers to whichever line is shortest (the load balancer).

A load balancer's core job, stripped down to the actual decision it makes on every incoming request:

class RoundRobinBalancer:
    def __init__(self, servers):
        self.servers = servers
        self.next_index = 0

    def get_server(self):
        server = self.servers[self.next_index]
        self.next_index = (self.next_index + 1) % len(self.servers)   # cycle through evenly
        return server

class LeastConnectionsBalancer:
    def __init__(self, servers):
        self.active_connections = {s: 0 for s in servers}

    def get_server(self):
        return min(self.active_connections, key=self.active_connections.get)  # send to the least-busy one

Real load balancers (nginx, HAProxy, a cloud provider's managed one) do this same basic job - pick which backend gets the next request - plus health checks (stop routing to a server that's failing) and TLS termination, but the core routing decision is exactly this simple.

4.8b Replication & Sharding

Replication copies the same data across multiple nodes - for reliability (a copy survives a node failure) and read scalability (reads served from any replica). Sharding splits different portions of data across nodes by some key, because the full dataset no longer fits comfortably on one machine.

Plain English: replication answers "the same data, more copies, for safety and read speed." Sharding answers "the data itself is too big for one machine, split it into pieces on different machines." Different problems, often used together - each shard might itself be replicated.

Analogy: replication is photocopying an important document into several filing cabinets (safety if one burns, multiple readers simultaneously). Sharding is a company's records being too voluminous for one cabinet, split alphabetically across several (A–M in cabinet 1, N–Z in cabinet 2) - each holds a distinct, non-overlapping subset.

Hotspot risk (foreshadowing Phase 5): a bad shard key - e.g. sharding by signup date when most active traffic comes from recently-signed-up users - concentrates disproportionate load on one or two shards, defeating the point of splitting the data.

4.8c The CAP Theorem

A distributed data store can provide at most two of three guarantees during a network partition: Consistency (every read gets the most recent write, or an error), Availability (every request gets a non-error response, not guaranteed to be the latest data), Partition tolerance (the system keeps operating despite nodes being unable to communicate). Since partitions are a real, unavoidable possibility, partition tolerance is effectively non-negotiable - the real choice during an actual partition is Consistency vs. Availability (CP vs. AP).

Plain English: this theorem describes what happens specifically during a partition - not a general "pick 2 forever" statement. When the network is healthy, you can often have all three. When node A and node B can't talk and both get write requests, you must choose: reject requests until the partition heals (Consistency - never serve possibly-stale/conflicting data), or accept them on both sides and reconcile conflicts later (Availability - never refuse a request, risk temporary inconsistency).

Analogy: two bank branches lose connection to each other but stay open. A withdrawal at Branch A: refuse it until confirming with Branch B the account isn't being drained simultaneously (CP), or allow it based on local last-known balance, risking a conflicting withdrawal at Branch B, reconciled once communication returns (AP).

Concrete example, C over A: a financial ledger typically favors Consistency during a partition - rather reject a transaction (momentarily unavailable) than risk a double-spend (inconsistent data); correctness of money matters more than always responding.

Concrete example, A over C: a social-media "like" counter or shopping cart often favors Availability - better to let the request through (a slightly stale count, or two replicas both accepting cart updates) than refuse service during a network hiccup; eventual consistency (data converges once the partition heals) is an acceptable trade for that kind of data.

The actual branch a node has to make when it detects it can't reach its peers, in either mode:

def handle_write(data, can_reach_peers):
    if not can_reach_peers:                  # a partition is happening right now
        if mode == "CP":
            raise Unavailable("can't confirm consistency with peers -- refusing the write")
        elif mode == "AP":
            write_locally(data)                # accept it, reconcile with peers once the partition heals
            return "accepted (will sync later)"
    write_locally(data)
    replicate_to_peers(data)
    return "accepted"

This is the entire theorem in code form: the if not can_reach_peers branch is the partition; the two outcomes inside it (raise Unavailable vs. write_locally anyway) are the CP-vs-AP choice. Everything else in the function is identical either way.
