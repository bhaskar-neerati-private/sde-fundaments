4.6 UML & the LLD Process

Objective: go from a written requirements paragraph to a class diagram to code, in that order, every time - the actual skill LLD interviews test.

Low-Level Design (LLD) translates a written requirements description into a concrete class-level design (attributes, methods, relationships) before writing implementation code - typically expressed as a UML class diagram (boxes for classes with key attributes/methods, arrows showing relationships) as an intermediate artifact between requirements and code.

Plain English: the actual skill LLD interviews test isn't "do you know UML arrow notation" - it's the discipline of designing class structure and relationships first, deliberately, before getting lost in implementation details, rather than typing code and letting the design emerge accidentally (and often badly) as you go.

Key UML relationships (the essential vocabulary):

  • Association - a general "uses/knows about" relationship (a plain line).
  • Composition - a strong "owns and controls the lifetime of" relationship (filled diamond) - e.g. a House has Rooms that don't exist independently of the house.
  • Aggregation - a weaker "has, but doesn't own the lifetime of" relationship (hollow diamond) - e.g. a University has Students, but students exist independently of any one university.
  • Inheritance - "is-a" (hollow triangle arrow pointing to the parent).

Analogy: a UML diagram is an architect's blueprint drawn before construction begins - it lets you (and reviewers) catch a structural problem ("this load-bearing wall conflicts with that room's placement") cheaply, on paper, instead of discovering it after the walls are already built (i.e. after a bunch of code needs a costly rewrite).

The process, concretely:

  1. Read requirements carefully, extract the nouns (candidate classes) and verbs (candidate methods/responsibilities).
  2. Sketch relationships between those classes (who owns/uses/inherits from whom).
  3. Assign responsibilities to the right class (informed by SRP, 4.2a).
  4. Then implement, following the diagram - and if the design needs to change mid-implementation, update the diagram too, rather than letting code and diagram silently diverge.

Worked mini-example - turning a requirements sentence into a skeleton. Requirement: "A library has books. A member can borrow a book if it's available, and return it later."

  • Nouns → classes: Library, Book, Member.
  • Verbs → methods: borrow_book(), return_book().
  • Relationship: Library has many Books (composition - books don't exist independently of some library owning them); Member uses Library (association, not ownership).

Only after that sketch exists do you write:

class Book:
    def __init__(self, title):
        self.title = title
        self.is_available = True

class Member:
    def __init__(self, name):
        self.name = name

class Library:
    def __init__(self):
        self.books = []           # composition: Library owns these Book instances

    def borrow_book(self, member: Member, book: Book):
        if not book.is_available:
            raise ValueError(f"{book.title} is not available")
        book.is_available = False

    def return_book(self, book: Book):
        book.is_available = True

Notice the code is almost a direct transcription of step 1–3 above - that's the point of doing the design first: by the time you type class Library:, there's nothing left to figure out, only to translate.

Do:

  • Take a one-paragraph requirements prompt (write your own, e.g. "design a library book-lending system") and produce a class diagram BEFORE writing any code. Only then implement it.

Checkpoint:

  • Practical review - show the diagram-first artifact and the resulting code side by side; the code must match the diagram (a design change mid-coding without updating the diagram is a fail - this is about discipline in the process, not just the final code).
