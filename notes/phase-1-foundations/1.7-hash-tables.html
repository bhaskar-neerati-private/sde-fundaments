1.7 Hash Tables

Objective: understand how a hash map actually works under the hood (buckets, collision resolution, amortized O(1)) - not just dict[key] = value.

1.7a What Hashing Actually Is

A hash table maps keys to values by applying a hash function - deterministically converting a key into a fixed-size integer (hash code) - then using that integer (reduced via modulo) as an index into an array, called a bucket. Gives average-case O(1) insert/lookup/delete regardless of element count.

Plain English: searching a list checks items one at a time (O(n)). Hashing computes exactly where a key's data lives via arithmetic on the key itself - a lookup jumps straight there instead of scanning.

A good hash function is: deterministic (same key → same code, always), uniformly distributing (spreads keys evenly, minimizing collisions), and fast.

Analogy: a formula converting a name into a gym locker number. Run "Alice" through it, get locker #47 directly - no walking every row checking tags. Same input, same locker, every time.

def simple_string_hash(key, table_size):
    hash_code = 0
    for ch in key:
        hash_code = (hash_code * 31 + ord(ch)) % table_size
    return hash_code

Multiplying by a small prime per character and folding in % table_size keeps values bounded and spreads similar keys apart (this shape underlies Java's String.hashCode() and rolling-hash string algorithms). index = hash(key) % table_size squeezes an arbitrary-size hash code into the array's valid range.

Why "O(1) usually," not "always": depends on the hash function actually spreading keys out. Many keys piling into one bucket (a collision) degrades that bucket's operations toward O(n).

1.7b Collision Resolution & Building One From Scratch

Collisions are inevitable (pigeonhole principle - key space vastly exceeds bucket count). Two dominant strategies:

Separate chaining - each bucket holds a small list of every pair that hashed there. Insert always succeeds (append). Lookup: hash to find the bucket, scan its (hopefully short) list.

Analogy: an apartment mailroom where a mailbox isn't capped at one letter - colliding letters just stack together in the same box; finding one means flipping through that box's pile.

class HashMap:
    def __init__(self, capacity=8):
        self.capacity = capacity
        self.size = 0
        self.buckets = [[] for _ in range(self.capacity)]

    def _hash(self, key): return hash(key) % self.capacity

    def put(self, key, value):
        idx = self._hash(key)
        for pair in self.buckets[idx]:
            if pair[0] == key: pair[1] = value; return
        self.buckets[idx].append([key, value])
        self.size += 1
        if self.size / self.capacity > 0.75: self._resize()

    def get(self, key):
        for k, v in self.buckets[self._hash(key)]:
            if k == key: return v
        raise KeyError(key)

    def delete(self, key):
        bucket = self.buckets[self._hash(key)]
        for i, (k, v) in enumerate(bucket):
            if k == key: del bucket[i]; self.size -= 1; return
        raise KeyError(key)

    def _resize(self):
        old_buckets = self.buckets
        self.capacity *= 2
        self.buckets = [[] for _ in range(self.capacity)]
        self.size = 0
        for bucket in old_buckets:
            for k, v in bucket: self.put(k, v)   # re-hash everything into the larger table

Load factor (size / capacity, ~average items per bucket) and resizing: without resizing, chains grow unboundedly and every operation degrades toward O(n), regardless of hash quality - a good hash function controls distribution, not total volume. Doubling capacity + rehashing once load factor crosses ~0.7–0.75 keeps average chain length bounded. This is why put is amortized O(1): most inserts are cheap, occasionally one triggers an O(n) rehash, and spread across all inserts the average stays O(1) - same shape as Python's own list.append().

Open addressing - every item lives directly in the array, one per slot; on collision, probe forward per a fixed sequence until an empty slot is found.

Analogy: assigned parking by formula; if your spot's taken, you drive to the next spot in a fixed search pattern. Finding your car later follows the same pattern from your assigned spot.

class HashMapOpenAddressing:
    def __init__(self, capacity=8):
        self.capacity = capacity
        self.keys = [None] * capacity
        self.values = [None] * capacity
        self.deleted = [False] * capacity     # tombstones

    def _hash(self, key): return hash(key) % self.capacity

    def put(self, key, value):
        idx = start = self._hash(key)
        while self.keys[idx] is not None and not self.deleted[idx]:
            if self.keys[idx] == key: self.values[idx] = value; return
            idx = (idx + 1) % self.capacity     # linear probe
            if idx == start: raise Exception("full")
        self.keys[idx], self.values[idx], self.deleted[idx] = key, value, False

    def get(self, key):
        idx = start = self._hash(key)
        while self.keys[idx] is not None:
            if self.keys[idx] == key and not self.deleted[idx]: return self.values[idx]
            idx = (idx + 1) % self.capacity
            if idx == start: break
        raise KeyError(key)

Why delete needs a tombstone, not None: clearing a slot to None would break lookups for other keys whose probe chain passes through it - their get relies on "keep probing until None" to know when to give up; wiping an earlier slot would make a later lookup stop early and wrongly report "not found." A tombstone marks "empty but keep probing past me," while insertion is free to reclaim it.

Quadratic probing: step by i² instead of i (idx = (hash(key) + i²) % capacity) - spreads probes faster, reducing primary clustering (long runs from linear probing). Still suffers secondary clustering: keys sharing an initial index follow the identical subsequent sequence.

Double hashing: step size comes from a second hash function: idx = (hash1(key) + i·hash2(key)) % capacity. Keys colliding at the same initial slot almost certainly have different hash2 values, so their probe sequences diverge immediately - eliminates secondary clustering, behaves close to uniform/random probing. Requires hash2(key) != 0 and ideally coprime with capacity (commonly: prime capacity, hash2 in 1..capacity-1).

What Python's dict actually uses: open addressing (not chaining), with a custom probe sequence (not plain linear/quadratic/double hashing) designed to avoid pathological cases like keys whose hashes differ only in low bits. Roughly: j = (5*j + 1 + perturb) % table_size; perturb >>= 5, starting perturb as the full hash value - early probes are pseudo-random with respect to low bits, settling into a guaranteed-to-visit-every-slot walk once perturb bottoms out. Since 3.6/3.7, dict is actually two structures: a sparse open-addressed index array (where this probing happens) plus a dense array holding entries in insertion order - which is why dicts preserve insertion order.

Trade-offs: chaining tolerates high load factor gracefully, pays per-item pointer overhead. Open addressing is more cache-friendly/memory-efficient, needs tombstones for deletion, suffers clustering without a good probe sequence.
