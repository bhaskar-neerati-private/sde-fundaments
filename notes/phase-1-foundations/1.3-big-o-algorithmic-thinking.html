1.3 Big-O and Algorithmic Thinking

Objective: look at any snippet of code and state its time/space complexity within seconds; know when O(n log n) vs O(n²) actually matters in practice.

Big-O notation, O(f(n)), describes an asymptotic upper bound on how an algorithm's resource usage grows as input size n grows - formally, T(n) is O(f(n)) if constants c, n₀ exist such that T(n) ≤ c·f(n) for all n ≥ n₀. It ignores constant factors and lower-order terms, describing only the shape of the growth curve.

Plain English: Big-O answers "if I double the input, roughly how much more work does this do?" - a category of growth behavior, not a stopwatch reading.

Analogy - everyday growth rates:

  • O(1) constant: grabbing a book off a shelf when you know the exact spot. Same effort regardless of library size.
  • O(log n) logarithmic: finding a word in a dictionary by always opening to the middle and discarding half. Doubling the dictionary costs one more halving step.
  • O(n) linear: totaling receipts by reading every one. Twice the receipts, twice the time.
  • O(n log n) linearithmic: merge sort - repeatedly split and merge.
  • O(n²) quadratic: checking every person against every other person for a shared birthday. Double the people, ~4x the comparisons.
  • O(2ⁿ) exponential: trying every on/off combination of n switches. Each extra switch doubles the possibilities.
def get_first(arr): return arr[0]                    # O(1)

def binary_search(arr, target):                       # O(log n)
    lo, hi = 0, len(arr) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if arr[mid] == target: return mid
        elif arr[mid] < target: lo = mid + 1
        else: hi = mid - 1
    return -1

def find_max(arr):                                     # O(n)
    m = arr[0]
    for x in arr:
        if x > m: m = x
    return m

def sorted_copy(arr): return sorted(arr)                # O(n log n) - Timsort

def has_duplicate_pair(arr):                             # O(n^2)
    for i in range(len(arr)):
        for j in range(i + 1, len(arr)):
            if arr[i] == arr[j]: return True
    return False

def all_subsets(arr):                                     # O(2^n)
    if not arr: return [[]]
    first, rest = arr[0], arr[1:]
    without = all_subsets(rest)
    return without + [[first] + s for s in without]

Rules for deriving Big-O from code:

  • Sequential code → add: O(n) + O(n) = O(n) (drop the constant).
  • Nested loops → multiply: loop-in-loop over the same input = O(n²).
  • Range halves/doubles each iteration → O(log n).
  • Recursion → count branches: one call per invocation, shrinking by 1 → usually O(n). Two calls per invocation → usually O(2ⁿ).
  • Drop constants and lower-order terms: O(3n + 100) → O(n); O(n² + n log n) → O(n²).
  • Unrelated inputs get separate variables - looping over two different arrays of length a and b is O(a + b), not O(n). Collapsing two independent sizes into one variable hides real information.
  • Know built-ins' real costs: x in list → O(n); x in set/dict → O(1) average; arr[a:b] → O(k), k = slice length; sorted() → O(n log n).
  • Hidden trap: result += some_string in a loop, n times, is O(n²), not O(n) - strings are immutable, each += allocates a new string and copies everything so far. Use "".join(parts) instead (O(n)).
  • Hidden trap: a nested-looking loop where the inner loop's bound is a constant, not related to n (e.g. inner loop always runs exactly 10 times) is still O(n), not O(n²) - always check what each loop's bound is actually tied to, don't pattern-match "nested loop = quadratic."
  • Memoized recursion is not automatically exponential: naive recursive Fibonacci is O(2ⁿ), but adding a cache so each distinct subproblem is computed once (not re-derived) brings it to O(n) time, O(n) space - compare the code to what it actually recomputes, not to "recursion = exponential" by reflex.

Space complexity: extra memory used relative to input (auxiliary space, usually excluding the input itself). Recursive calls cost O(depth) stack space even without explicit allocation.

When O(n log n) vs O(n²) actually matters: Big-O is asymptotic - for small n, constant factors can dominate, making the "worse" algorithm faster in real wall-clock time (insertion sort often beats merge sort on tiny arrays; real sort implementations switch to O(n²) methods below a size threshold). At scale, though, the class is everything: n=10⁶ means ~10¹² ops for O(n²) (minutes to hours) vs. ~2×10⁷ for O(n log n) (milliseconds).
