1.2 Git & GitHub Essentials

Objective: use Git confidently for branching, merging, rebasing, and resolving conflicts - not just add/commit/push.

1.2a Commits, Branches & Merging

Commit: an immutable, content-addressed snapshot of your entire project's tracked files, identified by a SHA-1 hash computed from its contents (file tree, message, author/timestamp, and a pointer to its parent commit). Not a diff - Git stores a full snapshot per commit (deduplicated internally for unchanged files); git diff/git log -p compute the visible diff on the fly by comparing two snapshots.

Plain English: because a commit's hash is derived from its own content and its parent's hash, changing anything - even in a commit from months ago - changes that commit's hash, cascading forward through every commit after it. That's why history is tamper-evident.

Analogy: a video game checkpoint, not word-processor undo history. Undo records edits (deltas) you step backward through. A checkpoint records the entire game state - loading checkpoint 5 doesn't replay checkpoints 1–4, it just drops you into that saved state directly. Checking out a commit works the same way.

git init demo && cd demo
echo "line 1" > file.txt
git add file.txt
git commit -m "first commit"
git log --oneline

Branch: a movable, named pointer to a single commit. HEAD is a special pointer tracking which branch (or, in "detached HEAD," which specific commit) is currently checked out. Creating a branch doesn't copy files - it's one new pointer, instant regardless of repo size.

Analogy: a bookmark in a book where every page is glued to the previous one in fixed order - the bookmark holds no content, just marks which page you're on. Moving it repositions you instantly.

git branch feature-x        # create pointer, doesn't switch to it
git switch feature-x        # HEAD now points at feature-x

Merge: integrates one branch's changes into another by creating a new commit with two parents (three-way merge). If the target hasn't moved since the source diverged, Git instead fast-forwards: slides the pointer forward, no merge commit at all, since there's nothing to reconcile. Git finds the common ancestor, compares what changed on each side since then, and combines automatically if the changes touch different lines - a merge conflict occurs only when both sides changed the same lines differently.

Analogy: two people editing separate photocopies of the same document. Different pages changed → staple both sets together, no trouble. Same sentence on the same page changed differently → someone has to manually decide the final wording.

git switch main
git merge feature-x               # fast-forward if main hasn't moved
git merge --no-ff feature-x -m "merge msg"   # force a real merge commit

1.2b Rebasing & Conflict Resolution

Rebase: takes the commits unique to your branch and replays them one at a time on top of the target's current tip, creating brand-new commits (new hashes - a commit's hash includes its parent's hash, and rebase changes the parent) with the same content changes. Produces a straight-line history instead of a merge-commit bump.

Analogy: a stack of tracing-paper overlays (commits), each traced from the same base drawing. Rebasing slides a new base drawing underneath and re-traces every overlay on top of it - same content, but each is physically a new sheet.

git switch feature-x
git rebase main
#   ... conflict? fix files ...
git add <file>
git rebase --continue
# or bail out entirely:
git rebase --abort

Resolving a conflict by hand: Git writes conflict markers directly into the file at the conflicting hunk and pauses until you edit it to the correct final content and git add it.

<<<<<<< HEAD
def greet():
    return "Hello, world"
=======
def greet():
    return "Hey there!"
>>>>>>> feature-x

HEAD is "your side," the other label is the incoming side. Edit down to the correct final version, delete the markers, then git add <file> + git commit (merge) or git rebase --continue (rebase). git status at any point shows exactly which files are still unmerged.

Interactive rebase & squashing: git rebase -i <base> opens an editable todo list of commits between <base> and HEAD, each prefixed pick/squash/fixup/reword/drop/edit. Changing a commit to squash merges it into the commit directly above it in the list, prompting for a combined message.

git log --oneline
git rebase -i HEAD~3
# editor: change "pick" to "squash" for the 2nd and 3rd commits, save
# second editor opens to combine messages, save
git log --oneline    # 3 commits collapsed into 1

Merge vs. rebase - the actual rule:

  • Merge preserves true history at the cost of merge-commit bumps. Use on shared/public branches - never rewrites commits others may already have.
  • Rebase produces clean linear history by rewriting commits. Use on your own local, not-yet-pushed work before sharing it.
  • Golden rule: never rebase commits other people might already have.
