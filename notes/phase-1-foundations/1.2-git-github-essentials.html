1.2 Git & GitHub Essentials

Objective: use Git confidently for branching, merging, rebasing, and resolving conflicts - not just add/commit/push.

1.2a Commits, Branches & Merging

Commit: an immutable, content-addressed snapshot of your entire project's tracked files, identified by a SHA-1 hash computed from its contents (file tree, message, author/timestamp, and a pointer to its parent commit). Not a diff - Git stores a full snapshot per commit (deduplicated internally via a shared object store, so unchanged files across commits point at the same underlying blob rather than being duplicated); git diff/git log -p compute the visible diff on the fly by comparing two snapshots, they don't read a stored diff.

Plain English: because a commit's hash is derived from its own content and its parent's hash, changing anything - even in a commit from months ago - changes that commit's hash, which changes every commit's hash that points back to it, cascading forward through every commit after it. That's the actual mechanism behind "history is tamper-evident": you can't quietly edit an old commit in place, because doing so necessarily produces a different commit with a different hash, and every descendant commit's stored parent-hash would now point at a hash that no longer matches anything in the repository.

Analogy: a video game checkpoint, not word-processor undo history. Undo records edits (deltas) you step backward through, each one meaningless without the ones before it. A checkpoint records the entire game state - loading checkpoint 5 doesn't replay checkpoints 1-4 first, it drops you into that saved state directly, instantly, regardless of how much happened to reach it. Checking out a commit works the same way: Git doesn't replay every commit since the beginning of history to reconstruct your files, it just materializes the snapshot that commit already points to.

git init demo && cd demo
echo "line 1" > file.txt
git add file.txt
git commit -m "first commit"
git log --oneline

Branch: a movable, named pointer to a single commit - nothing more. HEAD is a special pointer tracking which branch (or, in "detached HEAD," which specific commit) is currently checked out. Creating a branch doesn't copy any files or history - it's one new 41-byte pointer file, instant regardless of repo size, which is exactly why Git branching is so cheap compared to version-control systems that model a branch as a full directory copy.

Analogy: a bookmark in a book where every page is permanently glued to the one before it in a fixed, unchangeable order - the bookmark itself holds no content, it just marks which page you're currently on. Moving a bookmark to a different page repositions you instantly; it never rewrites the book.

git branch feature-x        # create pointer, doesn't switch to it
git switch feature-x        # HEAD now points at feature-x

Merge: integrates one branch's changes into another by creating a new commit with two parents (a three-way merge). If the target branch hasn't moved since the source diverged from it, Git instead fast-forwards: it just slides the target's pointer forward to match the source's tip, with no merge commit at all, since there's nothing to reconcile - the target's history is already a strict prefix of the source's. When a real merge is needed, Git finds the common ancestor commit, compares what changed on each side since that ancestor, and combines automatically whenever the changes touch different lines of a file - a merge conflict occurs specifically when both sides changed the same lines differently, since Git has no principled way to decide which version you actually want.

Analogy: two people editing separate photocopies of the same document, starting from an identical original. If they changed different pages, you staple both sets of edits together with no trouble - nothing overlaps. If they both rewrote the exact same sentence on the exact same page, differently, someone has to manually read both versions and decide the final wording; no automated process can guess which one is "right."

git switch main
git merge feature-x               # fast-forward if main hasn't moved
git merge --no-ff feature-x -m "merge msg"   # force a real merge commit

1.2b Rebasing & Conflict Resolution

Rebase: takes the commits unique to your branch and replays them one at a time on top of the target's current tip, creating brand-new commits with the same content changes but different parent commits - and because a commit's hash is computed partly from its parent's hash, changing the parent necessarily produces a new hash for every replayed commit, even though the actual code changes are identical. The result is a straight-line history instead of a merge-commit bump.

Analogy: a stack of tracing-paper overlays (your commits), each one originally traced from the same base drawing. Rebasing slides a new base drawing underneath the stack and re-traces every overlay on top of it, one at a time, in the same order - the visible content of each overlay is unchanged, but each is now physically a different sheet of paper, sitting on a different base.

git switch feature-x
git rebase main
#   ... conflict? fix files ...
git add <file>
git rebase --continue
# or bail out entirely:
git rebase --abort

Resolving a conflict by hand: whether the conflict arose from a merge or a rebase, Git writes conflict markers directly into the affected file at the exact conflicting hunk and pauses, waiting for you to edit it down to the correct final content and git add it.

<<<<<<< HEAD
def greet():
    return "Hello, world"
=======
def greet():
    return "Hey there!"
>>>>>>> feature-x

HEAD marks "your side" of the conflict, the label after >>>>>>> marks the incoming side. The fix is always the same three steps: edit the file down to the single correct final version, delete all three marker lines (<<<<<<<, =======, >>>>>>>) entirely, then git add <file> followed by git commit (if this was a merge) or git rebase --continue (if this was a rebase). git status at any point during a stalled merge/rebase shows exactly which files still have unresolved conflicts, which is the first thing worth checking if you're unsure what state you're in.

Interactive rebase & squashing: git rebase -i <base> opens an editable todo list of every commit between <base> and HEAD, each line prefixed with an action word - pick (keep as-is), squash (merge into the commit directly above it in the list, prompting for a combined message), fixup (like squash, but silently discards this commit's message), reword (keep the commit, edit only its message), drop (delete the commit entirely). Changing the action word and saving is the entire interface - Git replays the list top to bottom, applying each instruction.

git log --oneline
git rebase -i HEAD~3
# editor: change "pick" to "squash" for the 2nd and 3rd commits, save
# second editor opens to combine messages, save
git log --oneline    # 3 commits collapsed into 1

Merge vs. rebase - the actual rule, not a matter of taste:

  • Merge preserves true history (what actually happened, including the exact order things were done) at the cost of merge-commit bumps cluttering the log. Use it on shared/public branches - it never rewrites commits other people may already have pulled.
  • Rebase produces clean, linear-looking history by rewriting commits into new ones with new hashes. Use it only on your own local, not-yet-pushed work, before anyone else has based anything on top of it.
  • Golden rule: never rebase commits other people might already have. Rebasing gives every affected commit a new hash; anyone who already has the old commits will have a diverged, seemingly-unrelated history the next time they try to pull, and reconciling that mess is far more painful than the merge-commit clutter rebase was trying to avoid in the first place.

Common mistakes & misconceptions

  1. Believing a commit stores a diff, not a snapshot. This is backwards, and it matters: because each commit is a full snapshot, checking out any commit is a single direct jump, not a replay of every diff since the beginning - and it's also why Git can detect a moved/renamed file after the fact (by comparing snapshots for similar content), rather than needing you to explicitly tell it "this was a rename."
  2. Rebasing a branch that's already been pushed and that others may have pulled. Since rebase rewrites commit hashes, anyone who already has the old commits now has history that's diverged from yours in a way that isn't a simple fast-forward - their next git pull produces a confusing merge of two "different" histories that are actually the same content under new hashes. If a rebased branch must be pushed, it requires git push --force-with-lease (never plain --force, which can silently discard someone else's work pushed in the meantime) and clear communication that it happened.
  3. Assuming git merge always creates a merge commit. It only does so when there's genuinely something to reconcile (both branches diverged); if the target simply hasn't moved, Git fast-forwards silently with no merge commit at all - a common point of confusion when someone expects to see a merge commit in the log and doesn't.
  4. Panicking mid-conflict and running git merge --abort / git rebase --abort without realizing this discards all conflict-resolution work done so far, not just "cancels the merge cleanly" - which is the right move if you genuinely want to start over, but a mistake if you'd already correctly resolved most of the conflicts and just wanted to back out one specific hunk.
  5. Leaving conflict markers (<<<<<<<, =======, >>>>>>>) in a file after "resolving" it. It's easy to fix the actual code but forget to delete the marker lines themselves - the file then contains syntactically broken code (or, worse, code that happens to still run but with nonsensical extra text) that git add will happily stage, since Git has no idea what "resolved" is supposed to look like beyond "you ran git add."
