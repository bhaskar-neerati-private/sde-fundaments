1.4 Arrays & Strings

Objective: fluently apply two-pointer, sliding-window, and prefix-sum techniques.

1.4a Two Pointers

Uses two index variables traversing a structure, moving per a problem-specific rule, so total combined work stays O(n) instead of the O(n²) from checking every pair with nested loops - typically O(1) extra space.

Plain English: brute force checks every pair (O(n²)). Two pointers exploits a structural fact (most commonly: sorted data, or a symmetric check) to move intelligently - each pointer only moves forward, so total movement across the run is bounded by n.

Two shapes: converging (start at both ends, move toward each other) and fast/slow (both start near the beginning, move at different rates/conditions).

Analogy: converging - two people at opposite ends of a size-sorted shoe rack, looking for a pair summing to a target; whoever's sum is too big/small steps inward on the appropriate side, converging in the middle, covering the whole rack once. Fast/slow - a librarian's one hand marking "last confirmed-good spot" while the other scans ahead.

def two_sum_sorted(arr, target):          # converging
    lo, hi = 0, len(arr) - 1
    while lo < hi:
        s = arr[lo] + arr[hi]
        if s == target: return (lo, hi)
        elif s < target: lo += 1
        else: hi -= 1
    return None

def is_palindrome(s):                       # converging
    lo, hi = 0, len(s) - 1
    while lo < hi:
        if s[lo] != s[hi]: return False
        lo += 1; hi -= 1
    return True

def remove_duplicates(arr):                  # fast/slow, in-place dedup
    if not arr: return 0
    slow = 0
    for fast in range(1, len(arr)):
        if arr[fast] != arr[slow]:
            slow += 1
            arr[slow] = arr[fast]
    return slow + 1

Recognize on sight: sorted array + pair/triplet sum condition → converging. Symmetric check (palindrome) → converging. In-place dedup/partition → fast/slow. Merging two sorted sequences → one pointer per sequence.

1.4b Sliding Window

Maintains a contiguous subrange ("window") bounded by two pointers, incrementally updating a running state as the window moves, instead of recomputing from scratch per window - O(n) instead of O(n·k)/O(n²).

Plain English: consecutive windows overlap heavily; recomputing each independently is wasteful. Keep a running state (sum, frequency map) and just remove what left / add what entered.

Two flavors: fixed-size (given constant k, slide one in/one out) and variable-size (expand until a condition breaks/is met, contract to restore validity, repeat).

Analogy: fixed - a cashier's running total in a fixed viewing frame on a conveyor belt; subtract what scrolled out, add what scrolled in. Variable - an accordion: pull open (expand) until a note's too loud (condition breaks), squeeze shut (contract) until quiet again, repeat across the whole piece.

def max_sum_subarray(arr, k):                  # fixed-size
    window_sum = sum(arr[:k])
    max_sum = window_sum
    for i in range(k, len(arr)):
        window_sum += arr[i] - arr[i - k]
        max_sum = max(max_sum, window_sum)
    return max_sum

def min_subarray_len(target, arr):               # variable-size
    left, total, min_len = 0, 0, float('inf')
    for right in range(len(arr)):
        total += arr[right]
        while total >= target:
            min_len = min(min_len, right - left + 1)
            total -= arr[left]
            left += 1
    return min_len if min_len != float('inf') else 0

def length_of_longest_substring(s):                # variable-size
    seen, left, max_len = {}, 0, 0
    for right, ch in enumerate(s):
        if ch in seen and seen[ch] >= left:
            left = seen[ch] + 1
        seen[ch] = right
        max_len = max(max_len, right - left + 1)
    return max_len

Why the nested-looking while in min_subarray_len is still O(n): left only ever moves forward, at most n times total across the entire run, regardless of how many times the outer loop triggers the inner while. Combined movement of both pointers ≤ 2n - O(n) amortized, not O(n²).

Recognize on sight: "contiguous subarray"/"substring" (not "subsequence" - that's non-contiguous, a different pattern) + a sum/count/length/frequency condition. Explicit fixed k → fixed window. Min/max length satisfying a condition → variable window.

1.4c Prefix Sums

A precomputed auxiliary array where index i holds the cumulative sum from the start through index i. O(n) to build, O(n) space, but then any range-sum query is O(1) via subtraction instead of O(n) per query.

Analogy: a car's odometer - doesn't reset per trip, just accumulates total mileage. Distance between mile markers A and B is just reading(B) - reading(A), no re-driving required.

def build_prefix(arr):
    prefix = [0] * (len(arr) + 1)      # prefix[i] = sum of arr[0..i-1]
    for i in range(len(arr)):
        prefix[i + 1] = prefix[i] + arr[i]
    return prefix

def range_sum(prefix, i, j):            # inclusive sum of arr[i..j]
    return prefix[j + 1] - prefix[i]

Why length n+1 with prefix[0] = 0: padding avoids a special case for i == 0 in range_sum - the leading 0 ("sum of zero elements") lets one formula work uniformly for every i. General pattern: when a formula needs a special case only at a boundary, look for a padding value that makes the boundary behave like everything else.

Boundary of the technique: only works because the combining operation has an inverse (sum ↔ subtraction; XOR ↔ itself). Does not work for range min/max - no operation "undoes" a min - those need different structures (sparse tables, segment trees).

Composes with a hash map - count subarrays summing to exactly k:

def subarray_sum_equals_k(arr, k):
    count, running_sum = 0, 0
    seen = {0: 1}                        # empty prefix (sum 0) occurred once
    for x in arr:
        running_sum += x
        count += seen.get(running_sum - k, 0)
        seen[running_sum] = seen.get(running_sum, 0) + 1
    return count

If running_sum - k was seen before as a prefix sum, the subarray between that point and now sums to exactly k. O(n) time/space.
