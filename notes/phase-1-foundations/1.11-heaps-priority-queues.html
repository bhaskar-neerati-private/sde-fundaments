1.11 Heaps & Priority Queues

Objective: know when a problem needs a heap (top-K, merge-K, running median) and use Python's heapq correctly, plus understand the underlying array-based implementation.

A (binary min-)heap is a complete binary tree satisfying the heap property: every parent's value is ≤ both of its children's values (min-heap; ≥ for max-heap). This is not a full ordering like a BST - just a parent-child relative ordering - but it's enough to guarantee the minimum is always at the root. Implemented as a flat array, no node/pointer objects needed, by exploiting the "complete tree" shape: a node at index i has children at 2i+1 and 2i+2, and parent at (i-1)//2.

Plain English: a heap doesn't fully sort everything (unlike a BST) - it only guarantees the smallest (or largest) element is instantly findable at the root, maintaining just enough loose ordering to cheaply (O(log n)) re-establish that guarantee after each insert/removal. That's why it's the right tool specifically for "repeatedly grab the min/max" workloads (top-K, merge-K sorted lists, running median, Dijkstra's algorithm) rather than "give me everything fully sorted."

Analogy: an org chart where the only guaranteed rule is "every manager earns less than their direct reports" (min-heap). It says nothing about how two employees under different managers compare - just that going up any single chain of command, values keep decreasing. That partial ordering is enough to guarantee the CEO (root) is the company minimum, without ranking everyone.

def sift_up(heap, i):
    while i > 0:
        parent = (i - 1) // 2
        if heap[i] < heap[parent]:
            heap[i], heap[parent] = heap[parent], heap[i]
            i = parent
        else:
            break

def sift_down(heap, i):
    n = len(heap)
    while True:
        left, right, smallest = 2*i + 1, 2*i + 2, i
        if left < n and heap[left] < heap[smallest]: smallest = left
        if right < n and heap[right] < heap[smallest]: smallest = right
        if smallest == i: break
        heap[i], heap[smallest] = heap[smallest], heap[i]
        i = smallest

class MinHeap:
    def __init__(self):
        self.heap = []

    def push(self, val):
        self.heap.append(val)
        sift_up(self.heap, len(self.heap) - 1)

    def pop(self):
        if not self.heap: raise IndexError("pop from empty heap")
        top = self.heap[0]
        last = self.heap.pop()
        if self.heap:
            self.heap[0] = last
            sift_down(self.heap, 0)
        return top

Why the array-index formulas (2i+1, 2i+2, (i-1)//2) work at all: they rely entirely on the tree being complete (every level fully filled except possibly the last, which fills left-to-right with no gaps) - this is what guarantees a simple arithmetic relationship between a node's position and its children's/parent's positions, with no explicit pointers needed. A tree that wasn't kept complete couldn't use this trick; heaps are specifically designed to always insert at "the next open complete-tree position" (the end of the array) precisely to preserve this property.

Why pop moves the last element to the root before sifting down, rather than just removing the root directly: removing the root would leave a hole with two orphaned children and no obvious single replacement. Moving the last element into the root's spot keeps the tree complete (the array is still one contiguous block with no gaps) and gives sift_down a single, well-defined starting point to restore the heap property from.

Why insert/extract-min are O(log n): a complete binary tree with n nodes has height O(log n) (specifically, height = floor(log₂ n)). sift_up/sift_down each move at most one level per step, so at most O(log n) swaps - a direct consequence of "height is O(log n)" plus "each step of sifting only ever moves one level."

Using Python's built-in heapq (min-heap only - negate values for a max-heap):

import heapq

arr = [5, 3, 8, 1]
heapq.heapify(arr)              # O(n), in place
heapq.heappush(arr, 2)           # O(log n)
smallest = heapq.heappop(arr)    # O(log n)

heapq.nlargest(3, arr)           # top-3, convenience helper
heapq.nsmallest(3, arr)

Why heapq.heapify is O(n), not O(n log n) - a genuinely surprising result worth knowing: it might look like heapifying should cost O(n log n) (n insertions, each O(log n)), but heapify doesn't build the heap by inserting one element at a time from an empty array - it works bottom-up, calling sift_down on every non-leaf node starting from the last one and working toward the root. Most nodes in a complete binary tree are near the bottom (close to half of all nodes are leaves, needing zero sift-down work at all), and the total work across all levels sums to O(n), not O(n log n) - the nodes that could sift down the farthest (near the root) are also the fewest in number, and this trade-off works out to a linear total.

Why negating values simulates a max-heap without a separate implementation: heapq only ever exposes min-heap behavior. Pushing -val instead of val means the smallest negated value corresponds to the largest original value - popping the min of the negated values and negating the result back gives exactly the max-heap behavior, with zero changes to the underlying algorithm.

Common mistakes & misconceptions

  1. Believing a heap keeps elements fully sorted internally. It doesn't - only the root is guaranteed to be the min (or max); the rest of the array satisfies the parent-child relative ordering but has no guarantee about ordering between siblings or across different branches. Iterating the raw internal array does not produce sorted output.
  2. Assuming heapq.heapify costs O(n log n) by pattern-matching "n insertions at O(log n) each." As explained above, the actual bottom-up algorithm achieves O(n) - worth knowing precisely because it's a common and reasonable-sounding overestimate.
  3. Forgetting heapq is min-heap only and trying to pass a custom "reverse" comparator directly. Python's heapq has no built-in max-heap mode or comparator parameter (unlike, say, some other languages' priority queue implementations) - the standard workaround is negating numeric values, or wrapping entries in a custom comparable object/tuple for more complex sort keys.
  4. Storing mutable or unstably-ordered objects directly in a heap of tuples without a tiebreaker, e.g. heapq.heappush(heap, (priority, some_object)) - if two entries have equal priority, Python falls back to comparing some_object directly, which raises TypeError if that object isn't orderable. The standard fix is inserting a unique, always-comparable tiebreaker (like an insertion counter) as the second tuple element: (priority, counter, some_object).
  5. Using a heap when the problem actually needs full sorting, or vice versa. A heap is the right tool specifically for repeatedly extracting the current min/max (top-K, running median, merge-K) without needing the rest of the data ordered - if the task genuinely needs everything sorted, a plain sorted()/.sort() call is both simpler and no worse asymptotically.
  6. Manually removing an arbitrary (non-root) element from a heap by index and expecting the heap to remain valid without re-establishing the heap property there. Removing from the middle of the array requires both a sift-up and a sift-down check at that position (the replacement element might need to move either direction), not just one or the other - heapq doesn't expose a direct "remove at index" operation for exactly this reason.
