1.8 Recursion & Backtracking

Objective: write recursive solutions without tracing through them on paper first; recognize backtracking problems (permutations, combinations, N-Queens-style) on sight.

1.8a Recursion Fundamentals

A function solves a problem by calling itself on a smaller/simpler subproblem of the same type, plus at least one base case (simple enough to answer directly, no further calls) that terminates the chain. Every recursive call must make measurable progress toward a base case.

Two required parts:

  1. Base case - simplest input, answered directly.
  2. Recursive case - express the current answer in terms of the answer to a smaller version, trusting the recursive call returns correctly, without needing to know how it computes it internally.

The core discipline - "trusting the recursion": don't mentally trace the entire call stack every time (doesn't scale past a few levels). Verify only: (a) is the base case correct? (b) assuming the recursive call on a smaller input is correct, does the combining step correctly produce the current answer? If both hold, correctness follows at every depth by induction - this is literally mathematical induction, just applied to code instead of a formula: the base case is the induction's base, and "assume the recursive call is correct" is exactly the induction hypothesis.

Analogy: asking the person behind you in line "how many people are behind you?", trusting their answer completely, adding 1. They do the same to the person behind them. Nobody sees the whole line at once - each person handles one relationship (my count = 1 + their answer) - until the last person, who directly answers "0" (base case), no further asking needed.

def factorial(n):
    if n <= 1: return 1                      # base case
    return n * factorial(n - 1)               # trust factorial(n-1)

def recursive_sum(arr):
    if not arr: return 0                       # base case
    return arr[0] + recursive_sum(arr[1:])       # trust recursive_sum(rest)

What's physically happening (useful for intuition, not required for correctness reasoning) - factorial(4):

factorial(4)
  factorial(3)
    factorial(2)
      factorial(1) -> returns 1
    factorial(2) receives 1 -> 2*1=2, returns 2
  factorial(3) receives 2 -> 3*2=6, returns 6
factorial(4) receives 6 -> 4*6=24, returns 24

Each call sits on the stack until the one below returns - O(n) space for depth-n recursion.

Python-specific gotchas:

  • RecursionError: sys.getrecursionlimit() defaults to 1000 - deep unbounded recursion raises before actually exhausting memory. Verified: count_up(2000) (simple 1 + count_up(n-1) style) raises RecursionError: maximum recursion depth exceeded.
  • No tail-call optimization, ever: writing a function "tail-recursive" style (recursive call is the very last operation, e.g. factorial_tail(n-1, acc*n) with an accumulator) gets zero special treatment in Python - every call still gets its own real stack frame, tail position or not. Verified: both a normal recursive factorial and a tail-recursive-style factorial fail identically at n=2000. Languages with TCO (Scheme, Elixir) would collapse the tail-recursive version into O(1) stack space; Python never does. The actual fix is an explicit loop - while n > 1: acc *= n; n -= 1 - which reuses one frame every iteration and handles arbitrarily large n with zero stack growth.

Termination requirements: the base case must be reachable, and every call must make strict progress toward it (shrinking n, a shorter list) - miss either and you get infinite recursion (which, in Python, actually surfaces as a RecursionError once the stack limit is hit, not a true infinite loop - the process doesn't hang forever, it errors out, though the underlying bug is the same).

1.8b Backtracking

Recursive search that incrementally builds candidate solutions and abandons ("backtracks" from) a candidate the moment it's determined that path can't lead to a valid solution, rather than building it out fully first. Doesn't change the theoretical worst case (usually still exponential) but often prunes huge fractions of the search space in practice.

Plain English: recursion + "undo the choice and try the next one." Make a tentative choice, recurse assuming it holds; if that path's invalid or exhausted, undo and try the next option at that same step. Systematic trial-and-error that only ever backs up one step, never restarts from scratch.

The choice / constraint / goal framework for any backtracking problem:

  • Choice - what are the options at this step?
  • Constraint - what makes a partial candidate invalid, prunable immediately?
  • Goal - what does a complete valid solution look like?

Analogy - a maze: hit a dead end, walk back to the last junction with an untried direction (not all the way to the entrance), try the next one. Analogy - seating guests with a rule (Alice can't sit next to Bob): seat one guest at a time; hit a violation, undo just that one seating, try the next guest for that chair, keep going. Catching a broken rule immediately - not after fully seating everyone - is what saves the wasted exploration of doomed branches.

def subsets(nums):                     # choice: include or not; every call IS a valid subset
    result, path = [], []
    def backtrack(start):
        result.append(path[:])
        for i in range(start, len(nums)):
            path.append(nums[i])        # choice
            backtrack(i + 1)
            path.pop()                   # undo
    backtrack(0)
    return result

def permutations(nums):                  # constraint: no reuse; goal: full length
    result, path = [], []
    used = [False] * len(nums)
    def backtrack():
        if len(path) == len(nums):
            result.append(path[:]); return
        for i in range(len(nums)):
            if used[i]: continue          # constraint
            path.append(nums[i]); used[i] = True
            backtrack()
            path.pop(); used[i] = False    # undo
    backtrack()
    return result

def combination_sum(candidates, target):   # constraint: arithmetic (remaining < 0), reuse allowed
    result, path = [], []
    def backtrack(start, remaining):
        if remaining == 0: result.append(path[:]); return
        if remaining < 0: return                          # prune
        for i in range(start, len(candidates)):
            path.append(candidates[i])
            backtrack(i, remaining - candidates[i])         # i, not i+1 -> allows reuse
            path.pop()
    backtrack(0, target)
    return result

Why path.append()/path.pop() is the essential mechanic: unlike recursive_sum (which builds a new smaller list each call), path here is one shared, mutable list across the whole recursion tree - every branch reads/writes the same object. After fully exploring one choice, you must manually undo it before trying the next option, or every later branch would incorrectly still contain a choice that no longer applies. This is exactly the shared-mutable-state discipline flagged in the Tries/Backtracking pairing elsewhere in this curriculum - the same path object is passed by reference into every recursive call, so mutating and un-mutating it in place (rather than passing copies) is what keeps the whole thing efficient.

i vs i+1 in the recursive call: i+1 (subsets/permutations) enforces "each element used once." i (combination_sum) deliberately allows reusing the same candidate. This is a conscious decision tied to the problem's actual rules, not boilerplate to copy blindly - get it backwards and you either miss valid results (using i+1 when reuse should be allowed) or generate impossible duplicates/infinite recursion (using i when each element should only be used once, though the remaining < 0 prune here happens to still terminate it, just producing wrong answers along the way for problems without a similarly convenient numeric bound).

Why the theoretical worst case doesn't improve, but real performance often does: backtracking still visits, in the worst case, every leaf of the same exponential search tree that pure brute force would - the remaining < 0 prune in combination_sum doesn't change the Big-O bound on adversarial input, it changes how much of that tree is actually explored on typical input by cutting off entire subtrees the moment they're provably doomed, often long before reaching a full-depth leaf.

Common mistakes & misconceptions

  1. Trying to trace the entire call stack by hand for every recursive function, instead of trusting the induction argument. This doesn't scale past 3-4 levels of depth and is a common reason recursive solutions "feel unintuitive" - the discipline described above (verify the base case, then trust the recursive call) is what actually makes recursion tractable to reason about.
  2. Believing "tail-recursive style" in Python avoids stack growth. As stated explicitly above, Python performs no tail-call optimization under any circumstances - a tail-recursive-looking function still accumulates one stack frame per call and hits the same RecursionError as a non-tail-recursive one at the same depth.
  3. Forgetting to undo a choice (path.pop(), used[i] = False) after a recursive call returns. Since path/used are shared mutable state across the whole recursion tree, skipping the undo step leaves stale state that corrupts every subsequent branch explored - this is the single most common backtracking bug, and it typically produces subtly wrong results (missing or duplicated solutions) rather than an obvious crash.
  4. Confusing i and i+1 in the recursive call's start index, as explained above - always derive this from the problem's actual reuse rules, not from memory of a similar-looking problem.
  5. Appending path directly to result instead of path[:] (a copy). Since path is the same mutable list object throughout the recursion, appending a reference to it means every entry in result ends up pointing at the same list - by the time backtracking finishes, all of them show whatever path's final state happened to be, not the value at the moment each was "recorded." This is the backtracking-specific instance of the general mutable-reference-sharing trap.
  6. Assuming backtracking changes the worst-case time complexity. It doesn't, in general - pruning reduces actual work on typical/favorable input, often dramatically, but the worst-case bound (adversarial input where little or nothing can be pruned) usually remains the same exponential bound as brute force.
