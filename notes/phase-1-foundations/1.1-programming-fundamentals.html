1.1 Programming Fundamentals (Python)

Objective: close the gap between "comfortable writing code" and actually knowing the language - OOP internals, comprehensions/generators, decorators, context managers, and exception design.

1.1a Objects, Classes & Dunder Methods

Class vs. object. A class is a blueprint defining what attributes (data) and methods (behavior) its instances will have - it holds no per-object data itself, it's a template. An object is an instance of a class, with its own copy of instance attributes. Instantiation is creating an object by calling the class, e.g. Dog('Rex', 'Lab').

Plain English: the class is the recipe, the object is the actual cake you baked from it. Every cake baked from the same recipe can have different toppings (instance attributes) even though they share the same steps (methods).

__init__ (the constructor): a special method Python calls automatically, exactly once, immediately after a new object is created, used to initialize that object's instance attributes. Mechanically, Dog('Rex', 'Lab') first calls Dog.__new__(Dog) to allocate a bare, empty object, then calls __init__(that_object, 'Rex', 'Lab') on it - __init__ never returns the object itself (it must return None), it only mutates the one already created by __new__. You almost never need to touch __new__ directly; __init__ is where per-instance setup belongs.

self: the conventional name for the first parameter of every instance method - a reference to the specific object the method was called on, letting the method read/modify that object's own attributes. dog.bark() is syntactic sugar for Dog.bark(dog) - Python automatically passes the object as the first argument whenever you call a method through an instance.

Attribute: a variable bound to an object (instance attribute, e.g. self.name, unique per object) or to the class itself (class attribute, shared by all instances).

Method: a function defined inside a class that operates on its instances (or on the class itself, for classmethod/staticmethod).

class Dog:
    species = "Canis familiaris"      # class attribute - shared by every Dog

    def __init__(self, name, breed):
        self.name = name              # instance attribute - unique per Dog
        self.breed = breed

    def bark(self):
        return f"{self.name} says woof!"

Inheritance: a mechanism where a new class (subclass) derives the attributes and methods of an existing class (superclass), enabling code reuse and modeling "is-a" relationships. super() is used inside the subclass to call the superclass's version of a method (most often __init__).

class Puppy(Dog):
    def __init__(self, name, breed, age_months):
        super().__init__(name, breed)   # reuse Dog's setup instead of duplicating it
        self.age_months = age_months

Analogy: inheritance is like a franchise restaurant - the local branch (subclass) automatically gets the parent company's recipes and processes (methods), but can add its own local specials (extra methods) or override a recipe for local taste (override a method) without changing the original company's recipe book.

Dunder ("double underscore") methods are special methods Python calls to implement built-in syntax (print(), ==, len(), +, ...). This is Python's actual mechanism for operator overloading and protocol support - a + b doesn't have hardcoded behavior per type baked into the interpreter; it's literally a.__add__(b) under the hood, which is exactly why any class can participate in + by simply defining __add__. Without dunders, your objects behave nothing like Python's built-ins:

  • __repr__ / __str__ - what's shown by print()/repr(); the default is a useless memory address like <Dog object at 0x7f...>.
  • __eq__ - defines ==; the default compares identity (same object in memory), not data. Two Dog objects with identical name/breed are != by default until you define __eq__.
  • __len__ - defines len(obj); without it, len() raises TypeError.
  • __add__ - defines +.
class Fraction:
    def __init__(self, num, den):
        self.num, self.den = num, den

    def __repr__(self):
        return f"Fraction({self.num}, {self.den})"

    def __eq__(self, other):
        if not isinstance(other, Fraction):
            return NotImplemented          # not False! see note below
        return self.num * other.den == other.num * self.den

    def __add__(self, other):
        return Fraction(self.num * other.den + other.num * self.den, self.den * other.den)

Why __eq__ should return NotImplemented, not False, for an unrecognized type: NotImplemented is a signal to Python's comparison machinery, not a final answer. When a == b runs, Python calls a.__eq__(b). If that returns NotImplemented, Python retries with b.__eq__(a) before giving up and falling back to identity comparison. Returning False directly would assert "definitely not equal" even in cases where the other object might know how to compare itself to you correctly - short-circuiting that fallback and potentially producing an asymmetric, wrong answer (a == b could then disagree with b == a).

Why defining __eq__ makes a class unhashable by default: Python protects the invariant that equal objects must have equal hashes (required for correct behavior in sets/dict keys - a hash table finds candidate matches by hash first, then confirms with ==, so if two equal objects hashed differently, one could "hide" from the other inside a set/dict and duplicate detection would silently fail). The default __hash__ (inherited from object) hashes by identity, which is consistent with the default identity-based __eq__ - but the moment you override __eq__ to be value-based, that inherited hash becomes inconsistent (two value-equal objects could hash differently). Rather than leave that landmine, Python sets __hash__ to None automatically whenever __eq__ is defined without __hash__, making the class explicitly unhashable until you provide a hash consistent with your new equality. Fix: implement __hash__ yourself, normalizing any representation quirks (e.g. sign, reduced form) so equal-by-__eq__ objects always hash equal too.

1.1b Comprehensions & Generators

Comprehension: a concise expression that builds a new collection (list/set/dict) by applying an operation to each item of an iterable, optionally filtered - evaluated eagerly: the entire collection is computed and stored in memory immediately.

Analogy: a buffet restaurant - the kitchen cooks every dish and lays it all out before a single guest walks in. All the work happens upfront, and you get a full, ready-made collection sitting in memory.

squares = [x**2 for x in range(3)]                          # list: [0, 1, 4] - all computed now
unique_lengths = {len(w) for w in ['cat', 'dog', 'bee']}     # set: {3}
word_lengths = {w: len(w) for w in ['cat', 'dog', 'bee']}    # dict: {'cat': 3, 'dog': 3, 'bee': 3}

Generator expression: written with parentheses instead of brackets, returns a generator object - a lazy iterator that computes and yields exactly one value per call to next(), on demand, rather than computing and storing the entire sequence upfront.

squares_gen = (x**2 for x in range(3))   # nothing computed yet - just a "recipe" object
next(squares_gen)   # -> compute 0**2, return 0, then PAUSE
next(squares_gen)   # -> resume, compute 1**2, return 1, PAUSE
next(squares_gen)   # -> resume, compute 2**2, return 2, PAUSE
next(squares_gen)   # -> nothing left, raises StopIteration

Concretely, on nums = list(range(100_000)), [n*n for n in nums if n%2==0] costs hundreds of KB (the whole result list exists at once), while (n*n for n in nums if n%2==0) costs a couple hundred bytes regardless of nums's size - the generator object's size never changes because it's just holding "where am I paused," not the data.

Generator function: any function containing at least one yield. Calling it does not run the body - it immediately returns a generator object. Each next() call resumes the function from exactly where it paused, runs until the next yield, returns that value, and pauses again, preserving all local variables in between calls.

Analogy: a bookmark in a book. When you stop reading (yield), you place a bookmark holding your exact position. When you pick the book back up (next()), you resume from that bookmark - not page 1 - with everything about where you were exactly as you left it.

def count_up_to(n):
    i = 1
    while i <= n:
        yield i        # pause here, hand back i, remember everything
        i += 1         # resumes here on the next next() call

counter = count_up_to(3)
next(counter)   # 1
next(counter)   # 2
next(counter)   # 3
next(counter)   # raises StopIteration

Worked scenario - why this actually matters, not just as a memory micro-optimization: imagine scanning a 50GB log file for lines containing "ERROR". [line for line in open(path) if "ERROR" in line] reads the entire file into a list before you can look at a single result - if the file doesn't fit in memory, this crashes. (line for line in open(path) if "ERROR" in line) never holds more than one line in memory at a time; you can iterate it with a for loop and start seeing results (and can even break early) without ever fully reading the file. The lazy/eager distinction stops being a style choice the moment the data doesn't comfortably fit in RAM.

1.1c Decorators

Decorator: a callable that takes a function as input and returns a new function (usually wrapping the original), used via @decorator_name syntax placed above a function definition - syntactic sugar for func = decorator_name(func).

Plain English: a decorator lets you inject behavior before and/or after a function runs - logging, timing, access control, caching - without editing the function's own body, and without every caller needing to remember to call some extra setup/teardown code themselves.

Analogy: gift wrapping. The gift (the original function) doesn't change at all - you're wrapping it in paper (extra behavior) that happens as it's handed over and unwrapped, without altering the gift itself. You can wrap the same gift in different paper (apply different decorators) without ever touching what's inside.

This relies on two foundational Python facts:

  • Functions are first-class objects - they can be passed as arguments, returned from other functions, and assigned to variables, exactly like any other value.
  • Closures - an inner function defined inside an outer function "remembers" the variables from the outer function's scope even after the outer function has finished running.
import functools

def log_calls(func):
    @functools.wraps(func)              # preserves func's __name__, docstring, etc.
    def wrapper(*args, **kwargs):
        args_repr = ", ".join(str(a) for a in args)
        print(f"Calling {func.__name__}({args_repr})")
        result = func(*args, **kwargs)
        print(f"{func.__name__} returned {result}")
        return result
    return wrapper

@log_calls
def add(a, b):
    return a + b

add(3, 5)
# Calling add(3, 5)
# add returned 8
assert add.__name__ == "add"   # true only because of functools.wraps

Line-by-line, the part that actually confuses people: log_calls(add) runs once, at definition time (the moment Python sees @log_calls above def add), and returns wrapper. From that point on, the name add in this module refers to wrapper, not to the original function. Every subsequent call add(3, 5) is really wrapper(3, 5), which - via the closure - still has access to the original func (the real add) that it wraps, calls it, and returns its result. The original function object still exists in memory (referenced by the closure), it's just no longer reachable under the name add.

Why functools.wraps matters: without it, add.__name__ would be "wrapper" and add.__doc__ would be wrapper's (empty) docstring - the decorator would silently erase the original function's identity, breaking introspection tools, debuggers, and anything else that inspects __name__/__doc__. functools.wraps(func) copies that metadata from the original onto the wrapper.

Decorators with arguments (a decorator factory - a function that returns a decorator):

def repeat(times):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            for _ in range(times):
                result = func(*args, **kwargs)
            return result
        return wrapper
    return decorator

@repeat(times=3)
def greet(name):
    print(f"Hello, {name}")

greet("Alice")   # prints "Hello, Alice" three times

@repeat(times=3) first calls repeat(3), which returns the actual decorator function, which is then applied to greet - one extra layer of function-returning-a-function versus a plain decorator. It's worth explicitly tracing the call order here since it's the single most common source of confusion: repeat(3) runs immediately at decoration time and returns decorator; decorator(greet) then runs (also at decoration time) and returns wrapper; only later, when greet("Alice") is actually called, does wrapper's body run.

1.1d Context Managers & Custom Exceptions

Context manager: an object implementing __enter__(self) and __exit__(self, exc_type, exc_val, exc_tb), used via with to guarantee setup/teardown code runs regardless of whether the block completes normally or raises.

Analogy: a gym locker with an automatic-locking wristband. Tap in (__enter__) - the locker opens. No matter what happens during your workout (the with block), tapping out (__exit__) always locks the locker - even if your workout ended badly (an exception).

class Timer:
    def __enter__(self):
        import time
        self.start = time.perf_counter()
        return self

    def __exit__(self, exc_type, exc_val, exc_tb):
        import time
        elapsed = time.perf_counter() - self.start
        print(f"Elapsed: {elapsed:.4f}s")
        return False   # False/None = don't suppress the exception; True = swallow it

with Timer():
    raise ValueError("test")
# prints "Elapsed: ..." FIRST, then the ValueError still propagates

__exit__'s three parameters are None, None, None if the block exited normally, or filled in if an exception occurred - that's how __exit__ knows something went wrong. Its return value controls suppression: True swallows the exception, False/None (the default) lets it re-raise. An accidental return True deep in cleanup logic silently eats every exception ever raised inside that block - a genuinely nasty bug class, since the program keeps running as if nothing went wrong, with no traceback and no error, while whatever the exception was warning about (a failed write, a broken connection) goes completely unnoticed.

Function-based, via @contextmanager:

from contextlib import contextmanager
import time

@contextmanager
def timer():
    start = time.perf_counter()
    try:
        yield                     # code inside "with" runs here
    finally:
        print(f"Elapsed: {time.perf_counter() - start:.4f}s")

Everything before yield is __enter__; everything after, inside finally, is __exit__. Omit the try/finally and an exception inside the block skips the code after yield entirely - defeating the guarantee.

Suppressing exceptions with @contextmanager: there's no return True here - control comes from ordinary exception handling around yield, because contextlib calls gen.throw(...) to re-raise the exception at the yield point:

  • try: yield / finally: ... -> not suppressed (finally doesn't catch, just guarantees cleanup runs on the way past).
  • try: yield / except SomeError: ... (no re-raise, function returns normally) -> suppressed - equivalent to __exit__ returning True.
  • Catch one exception, raise NewError(...) from e -> translates the exception into a different, more meaningful one.

Class-based vs. @contextmanager - when to pick which: class-based when you need the object reusable across multiple with blocks (a generator is exhausted after one use - reusing the same generator object a second time raises an error), need extra attributes readable after the block ends (e.g. timer.elapsed), or want subclassing. Otherwise, default to @contextmanager - less boilerplate for the same guarantee.

Custom exceptions. A custom exception is a user-defined class inheriting from Exception (or a built-in subclass), representing a specific, named error condition. Since except matches a class and its subclasses, a hierarchy lets you catch broadly or narrowly.

class StackError(Exception):
    """Base class for all Stack-related errors."""

class EmptyStackError(StackError):
    def __init__(self, message="pop from an empty stack"):
        super().__init__(message)

class Stack:
    def __init__(self):
        self._items = []
    def push(self, item):
        self._items.append(item)
    def pop(self):
        if not self._items:
            raise EmptyStackError()
        return self._items.pop()

s = Stack()
try:
    s.pop()
except EmptyStackError as e:      # specific catch
    print(f"Specific: {e}")
try:
    s.pop()
except StackError as e:            # general catch - still works, EmptyStackError IS-A StackError
    print(f"General: {e}")

Analogy: hospital alarm codes - "Code Blue," "Code Red," "Code Silver" are all "emergencies" (the base class), but specific enough that the right team responds without everyone converging on every alarm.

Why a shared base pays off concretely: generic call sites (logging/retry wrappers) that want "catch anything in this family" write except StackError: once, and it automatically covers subclasses added later - no need to hunt down and update a tuple of exception types every time a new one is added. This mirrors Python's own built-ins: IndexError and KeyError both inherit from LookupError, so except LookupError: catches "couldn't find it by key/index" generically.

Exception chaining - raise ... from ...: preserves why a new exception happened.

try:
    int("not_a_number")
except ValueError as e:
    raise ConfigError("bad config value") from e
  • Just raise NewError(...) inside an except block -> Python automatically records the original as __context__ (implicit chaining) - traceback says "During handling of the above exception, another exception occurred." This happens whether you want it or not, as long as the raise happens while still inside the except block.
  • raise NewError(...) from e -> sets __cause__ explicitly, traceback says "The above exception was the direct cause of the following exception." - you're asserting the causal link, not just noting coincidence.
  • raise NewError(...) from None -> suppresses all trace of the original. Use only when the original is genuinely irrelevant - almost always, keep it, since it's often the real debugging clue.

Common mistakes & misconceptions

  1. Mutable default arguments. def f(items=[]): creates the list once, at function-definition time, not fresh on every call - every call that doesn't pass its own items shares and mutates the same list, so appended values silently accumulate across unrelated calls. Fix: default to None, then items = items if items is not None else [] inside the body.
  2. Believing __eq__ alone is enough for a class to work correctly in a set or as a dict key. Overriding __eq__ without also overriding __hash__ doesn't just leave the old hash behavior - Python sets __hash__ to None, making the object outright unhashable, which raises TypeError the moment you try to put it in a set. This is enforcing the equal-objects-must-hash-equal invariant, not an arbitrary restriction.
  3. Treating a generator as reusable. A generator is a one-shot iterator - once exhausted (or even partially consumed), calling list(gen) again returns an empty list, not the remaining or full sequence. If you need to iterate the same data multiple times, materialize it into a list, or re-call the generator function to get a fresh generator object.
  4. Forgetting functools.wraps and being confused later when help(func) or a debugger shows the wrong name/docstring, or when something that relies on introspecting __name__ (some frameworks route by function name) mysteriously breaks after adding a decorator.
  5. Writing except Exception: pass (or worse, except: with no type at all) to "handle" an error. A bare except: catches everything, including KeyboardInterrupt and SystemExit, silently swallowing a user's Ctrl+C or the program's own intentional exit signal - catch the specific exception type you actually expect and know how to handle.
  6. Assuming __exit__ returning None suppresses the exception, because None is falsy. It doesn't suppress it - only an explicit truthy return value (typically True) suppresses. None/False both mean "let it propagate," which is also the safer default, since silently swallowing exceptions is rarely what you actually want.
