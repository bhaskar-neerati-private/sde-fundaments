1.6 Stacks & Queues

Objective: know when a problem is secretly a stack or queue problem and implement both from scratch.

1.6a Stacks & the Monotonic Stack Pattern

Stack: strict Last-In-First-Out (LIFO) - push (add to top) and pop (remove top), both O(1). Most recently added is always removed first.

Analogy: a stack of cafeteria trays - only the top tray is accessible; a new clean tray goes on top too.

class Stack:
    def __init__(self): self._items = []
    def push(self, item): self._items.append(item)     # O(1) amortized
    def pop(self):
        if not self._items: raise IndexError("pop from empty stack")
        return self._items.pop()                        # O(1)
    def peek(self): return self._items[-1]
    def is_empty(self): return len(self._items) == 0

Valid parentheses (why a stack specifically fits): nested structures need "most recently opened must be first closed" - exactly LIFO.

def is_valid_parens(s):
    pairs = {')': '(', ']': '[', '}': '{'}
    stack = []
    for ch in s:
        if ch in '([{': stack.append(ch)
        elif ch in ')]}':
            if not stack or stack.pop() != pairs[ch]: return False
    return not stack

The final return not stack matters as much as the loop itself: a string like "((" never triggers the return False path (every closer it does see matches correctly), but leaves unclosed openers sitting on the stack - only checking that the stack is empty at the very end catches this "everything matched but nothing was ever closed" case.

Monotonic stack: a stack kept strictly increasing (or decreasing) bottom-to-top. When a new element would violate that order, pop elements off - each pop resolving something - until order is restored, then push. Answers "next greater/smaller element" queries in O(n) total, since each element is pushed once, popped at most once.

Analogy: a line of people of different heights; walking down the line looking for each person's next-taller person. When someone tall shows up, every shorter person still "waiting" gets resolved on the spot.

def daily_temperatures(temps):
    n = len(temps)
    result = [0] * n
    stack = []                     # indices of days still waiting for a warmer day
    for i, t in enumerate(temps):
        while stack and temps[stack[-1]] < t:
            j = stack.pop()
            result[j] = i - j
        stack.append(i)
    return result

On [73,74,75,71,69,72,76,73] -> [1,1,4,2,1,1,0,0] (indices 6,7 never resolve, stay 0).

Why O(n) despite the nested-looking while inside for: each index is pushed exactly once and popped at most once across the whole run - total push+pop ≤ 2n, not n². This is the exact same amortized-cost argument used for the sliding window's inner while loop in 1.4b - whenever you see a while nested inside a for and worry about O(n²), the first question to ask is "does each element get processed by the inner loop only a bounded number of times in total across the whole run," not "how many times could the inner loop run on a single outer iteration."

1.6b Queues & BFS Ordering

Queue: strict First-In-First-Out (FIFO) - enqueue (add to back), dequeue (remove from front), O(1) each. Earliest-added is always removed first.

Analogy: a coffee-shop line - first in line, first served; new arrivals join the back.

from collections import deque

class Queue:
    def __init__(self): self._items = deque()
    def enqueue(self, item): self._items.append(item)   # O(1)
    def dequeue(self):
        if not self._items: raise IndexError("dequeue from empty queue")
        return self._items.popleft()                     # O(1)

Why deque and not a plain list: a list is implemented as a contiguous, resizable array - removing from the front (list.pop(0)) requires shifting every remaining element one position left, an O(n) operation. deque (double-ended queue) is implemented internally as a doubly linked structure of fixed-size blocks, giving true O(1) operations at both ends - this is precisely why Python's standard library ships a separate type for this instead of just using list everywhere.

Trap: using a plain list and list.pop(0) for dequeue is O(n) - every remaining element shifts left. deque gives O(1) at both ends; list is only O(1) at the end.

Why BFS specifically needs a queue: BFS visits all nodes at distance 1 before any at distance 2, by enqueuing the source, then repeatedly dequeuing a node and enqueuing its unvisited neighbors - guaranteeing processing order matches discovery order. That's exactly FIFO. Swap the queue for a stack in the same code and you get DFS instead - tunneling deep down one path before returning to the others.

Analogy: ripples from a stone in water - BFS finishes "ripple ring 1" before starting "ripple ring 2," matching FIFO's "whoever arrived first gets served first." A stack would instead chase the most recent ripple, tunneling outward along one direction.

def bfs_levels(graph, start):
    visited = {start}
    queue = deque([(start, 0)])
    distances = {}
    while queue:
        node, dist = queue.popleft()
        distances[node] = dist
        for neighbor in graph[node]:
            if neighbor not in visited:
                visited.add(neighbor)
                queue.append((neighbor, dist + 1))
    return distances

This is the standard tool for shortest-path-in-an-unweighted-graph, precisely because of the discovery-order guarantee - all of a node's direct neighbors resolve fully (including discovering their own neighbors) before any of those grandchildren nodes are dequeued and processed themselves. Note also visited.add(neighbor) happens at enqueue time, not dequeue time - marking a node visited only when it's finally dequeued would let the same neighbor be enqueued multiple times by different in-progress nodes before any of them dequeue it, wasting work (though not breaking correctness, since re-processing an already-visited node would just be redundant, not wrong).

Common mistakes & misconceptions

  1. Checking stack.pop() != pairs[ch] without first checking not stack. Popping from an empty stack raises IndexError - the not stack or short-circuit in is_valid_parens is load-bearing, not defensive boilerplate; removing it crashes on any string with an unmatched closing bracket.
  2. Forgetting the final return not stack check, as explained above - a string of only unclosed openers passes every check inside the loop and needs this final verification to be correctly rejected.
  3. Using list.pop(0) for a queue "because it works," without registering that it's O(n) per call - this is one of the most common accidental performance bugs in interview code, since the list-based queue looks correct and passes small test cases, only revealing its O(n²) total cost on larger inputs.
  4. Believing a monotonic stack needs to check every existing stack element against the new one. It doesn't - the while loop only ever needs to compare the new element against the current top, because by the stack's maintained invariant (strictly increasing/decreasing), if the new element beats the top, it necessarily also beats whatever's now newly exposed as the top after that pop, and so on - each comparison is O(1), and the loop's total iterations are bounded by the total number of pushes, per the amortized argument above.
  5. Swapping a queue for a stack (or vice versa) without realizing this changes the traversal order entirely, particularly when adapting BFS code into what's meant to be DFS or vice versa - the data structure choice is the algorithm's defining characteristic here, not an implementation detail that can be swapped freely.
  6. Assuming deque is only useful for queues. It supports O(1) append/pop at both ends, so it's equally the right choice for a stack that also occasionally needs front access, a sliding-window's underlying storage, or any structure needing efficient operations at both ends simultaneously - not exclusively a "queue data structure."
