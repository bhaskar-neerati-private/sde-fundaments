2.1 Relational DB Design & Normalization

Objective: design a normalized relational schema from requirements, and explain why each normal form matters - not just recite 1NF/2NF/3NF.

2.1a Why Normalize? 1NF & 2NF

Normalization organizes relational data to eliminate redundancy and prevent update/insert/delete anomalies, by decomposing tables through a series of increasingly strict normal forms, each eliminating a specific category of redundancy-induced problem.

Un-normalized data often duplicates information across rows (e.g. every order row repeating the customer's full address). This wastes space, but the real problem is anomalies:

  • Update anomaly - change the customer's address, and you must remember to update every row that duplicated it, or the data becomes inconsistent.
  • Insert anomaly - can't record a new customer until they place an order, if customer info only lives inside the orders table.
  • Delete anomaly - deleting someone's only order accidentally deletes their customer info entirely.

1NF (First Normal Form): every column holds atomic (indivisible) values - no repeating groups, no lists crammed into one cell.

2NF: the table is in 1NF, and every non-key column depends on the entire primary key, not just part of it (only relevant for composite/multi-column keys) - eliminates partial dependency.

Analogy: 1NF is a form insisting each field has exactly one answer, not a "list all that apply" essay crammed into one box. 2NF is a two-part membership form (member ID + activity ID) where "activity description" depends only on which activity, not on who signed up - writing it on every member's registration is redundant; it belongs on a separate activities sheet, referenced by ID.

-- violates 1NF: items crammed into one field
CREATE TABLE orders_bad (
    order_id INT, customer_name TEXT, items TEXT  -- "Widget x2, Gadget x1"
);

-- 1NF fix
CREATE TABLE orders (order_id INT, customer_name TEXT);
CREATE TABLE order_items (order_id INT, item_name TEXT, quantity INT);

-- violates 2NF: course_name depends only on course_id, not the full (student_id, course_id) key
CREATE TABLE enrollments_bad (
    student_id INT, course_id INT, course_name TEXT, grade TEXT,
    PRIMARY KEY (student_id, course_id)
);

-- 2NF fix: split out the partial dependency
CREATE TABLE courses (course_id INT PRIMARY KEY, course_name TEXT);
CREATE TABLE enrollments (
    student_id INT, course_id INT REFERENCES courses(course_id), grade TEXT,
    PRIMARY KEY (student_id, course_id)
);

2.1b 3NF & Designing a Real Schema

3NF: the table is in 2NF, and no non-key column depends on another non-key column - eliminates transitive dependency. Every non-key column must depend on the key, the whole key, and nothing but the key.

Plain English: 2NF handles dependency on part of a composite key; 3NF handles a non-key column depending on another non-key column instead of the key directly. An employees table with employee_id (key), department_id, and department_name - department_name depends on department_id, not directly on employee_id (a transitive chain: employee_id → department_id → department_name), so it gets duplicated across every employee in the department, with the same update-anomaly risk if the department is renamed.

Analogy: a company directory listing every employee's department name directly on their record - rename "Sales" to "Revenue" and you must hunt down and fix every employee's record mentioning it, instead of updating one row in a separate departments table that everyone points to by ID.

-- violates 3NF: department_name transitively depends on employee_id via department_id
CREATE TABLE employees_bad (
    employee_id INT PRIMARY KEY, name TEXT, department_id INT, department_name TEXT
);

-- 3NF fix
CREATE TABLE departments (department_id INT PRIMARY KEY, department_name TEXT);
CREATE TABLE employees (
    employee_id INT PRIMARY KEY, name TEXT,
    department_id INT REFERENCES departments(department_id)
);

A full schema to 3NF - small e-commerce system:

CREATE TABLE users (user_id INT PRIMARY KEY, name TEXT, email TEXT UNIQUE);
CREATE TABLE products (product_id INT PRIMARY KEY, name TEXT, price DECIMAL);
CREATE TABLE orders (order_id INT PRIMARY KEY, user_id INT REFERENCES users(user_id), order_date DATE);
CREATE TABLE order_items (
    order_id INT REFERENCES orders(order_id),
    product_id INT REFERENCES products(product_id),
    quantity INT,
    PRIMARY KEY (order_id, product_id)
);
CREATE TABLE inventory (product_id INT PRIMARY KEY REFERENCES products(product_id), stock_quantity INT);

Every non-key column depends only on its own table's key - no customer info duplicated in orders, no product info duplicated in order_items (just a reference + quantity, since quantity is specific to that order-product pairing, not derivable from either alone).

Worth knowing: in practice, denormalization is sometimes deliberately applied for read-performance reasons (a trade-off, foreshadowing Phase 5's caching material) - but understand proper normalization first before intentionally breaking it.
