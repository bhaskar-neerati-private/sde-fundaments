2.2 SQL Querying

Objective: write joins, aggregations, subqueries, and window functions fluently without looking up syntax.

2.2a Joins & Aggregations

A JOIN combines rows from two or more tables based on a related column. INNER JOIN returns only rows matching in both tables. LEFT JOIN returns all rows from the left table plus matches from the right (NULL where no match). GROUP BY groups rows sharing a value so aggregate functions (COUNT, SUM, AVG, MAX, MIN) compute per-group instead of over the whole table. HAVING filters groups after aggregation - unlike WHERE, which filters rows before aggregation (and so can't reference an aggregate value that doesn't exist yet at that stage).

Plain English: joins reassemble data that normalization deliberately split across tables (2.1) back together for querying. GROUP BY + aggregates answer "what's true about each group" (total spent per customer) instead of "what's true about each row."

Analogy: JOIN is matching socks from two baskets by a shared tag (customer_id) - INNER JOIN keeps only matched pairs; LEFT JOIN keeps every left sock even with no match (an empty partner). GROUP BY is sorting a pile of receipts into per-customer stacks, then summing each stack separately instead of one giant total.

SELECT o.order_id, u.name
FROM orders o
INNER JOIN users u ON o.user_id = u.user_id;

SELECT u.name, COUNT(o.order_id) AS order_count
FROM users u
LEFT JOIN orders o ON u.user_id = o.user_id
GROUP BY u.name;
-- LEFT JOIN keeps users with ZERO orders (order_count = 0) -- INNER JOIN would exclude them entirely

SELECT user_id, SUM(quantity * price) AS total_spent
FROM order_items oi
JOIN products p ON oi.product_id = p.product_id
JOIN orders o ON oi.order_id = o.order_id
GROUP BY user_id
HAVING SUM(quantity * price) > 100;    -- filters GROUPS, not individual rows

Why WHERE can't do what HAVING does: SQL conceptually evaluates WHERE before grouping/aggregation happens - at that stage, aggregate values like SUM(quantity * price) simply don't exist yet, since no grouping has occurred. HAVING runs after GROUP BY has produced its per-group aggregate values, which is the only point at which "keep only groups where the total exceeds 100" is even a meaningful question to ask.

Why COUNT(o.order_id) and not COUNT(*) in the LEFT JOIN example: for a user with zero orders, the LEFT JOIN produces one row with every orders-table column as NULL, including order_id. COUNT(column) only counts non-NULL values, correctly giving 0 for that user; COUNT(*) counts rows regardless of NULLs, which would incorrectly report 1 (since the LEFT JOIN still produced exactly one output row for that user, just with all-NULL order columns).

2.2b Subqueries & Window Functions

A subquery is a query nested inside another, used as a value/table/condition. A correlated subquery references a column from the outer query, so it's conceptually re-evaluated once per outer row. A window function computes a value across a set of rows related to the current row (a "window," defined by OVER (...)) without collapsing rows into one output row per group - unlike GROUP BY, which does collapse.

Plain English: a correlated subquery is "for each row, ask this same question again, scoped to this row." Window functions solve what GROUP BY can't: "rank each order among that customer's orders, but keep every order as its own row" - GROUP BY would collapse everything into one row per customer, losing individual orders.

Analogy: correlated subquery - "for each student, what's the highest score in their own class" - "their own class" changes per student, so the question is re-asked per student. Window function - handing every student their personal class rank on their own report card, without a separate summary page hiding everyone's individual data.

-- subquery as a filter
SELECT name FROM products WHERE price > (SELECT AVG(price) FROM products);

-- correlated subquery: was this order above THAT customer's own average?
SELECT o.order_id, o.user_id
FROM orders o
WHERE o.total > (SELECT AVG(o2.total) FROM orders o2 WHERE o2.user_id = o.user_id);

-- window function: rank each order within its own customer's orders, rows NOT collapsed
SELECT order_id, user_id, total,
       RANK() OVER (PARTITION BY user_id ORDER BY total DESC) AS rank_within_customer
FROM orders;

-- top 3 orders per customer by value
SELECT * FROM (
    SELECT order_id, user_id, total,
           ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY total DESC) AS rn
    FROM orders
) ranked
WHERE rn <= 3;

PARTITION BY vs GROUP BY: PARTITION BY (inside OVER()) divides rows into groups for the calculation only - every original row still appears in the output, just with an extra computed column. GROUP BY actually collapses multiple rows into one per group. This is the single most important distinction in this lesson: reaching for GROUP BY when the actual requirement is "keep every row, but annotate it with something computed relative to its group" produces the wrong shape of result entirely (fewer rows than needed), no matter how correct the aggregate math itself is.

RANK() vs ROW_NUMBER(): RANK() gives ties the same rank and skips subsequent numbers (1,1,3). ROW_NUMBER() always gives distinct sequential numbers even on ties (1,2,3) - useful specifically for "give me exactly top-3," since ties under RANK() could otherwise produce more than 3 rows (e.g. two orders tied for 2nd place both get rank 2, and a naive WHERE rank <= 3 would then return 4 rows total, not 3).

Why the outer WHERE rn <= 3 needs to wrap the window-function query in a subquery, rather than filtering directly: window functions are computed as part of the SELECT list, conceptually after WHERE would have already run - so a query can't filter on a window function's result in the same SELECT's WHERE clause (this is the same "not computed yet at that stage" issue that makes WHERE unable to filter on aggregates, applied to window functions instead). Wrapping the window-function query as a subquery/CTE and filtering the outer query is the standard workaround.

Common mistakes & misconceptions

  1. Using WHERE to try to filter on an aggregate value. As explained above, this is a category error given SQL's logical evaluation order - WHERE runs before aggregation exists; HAVING is the only clause that can reference aggregate results.
  2. Using COUNT(*) when COUNT(column) is actually needed (or vice versa) in a query involving a LEFT JOIN - as shown above, this is a common, easy-to-miss source of subtly wrong counts specifically when some rows have NULL in the counted column.
  3. Confusing INNER JOIN and LEFT JOIN and silently dropping rows. A LEFT JOIN preserves every row from the left table even without a match; swapping in an INNER JOIN by habit silently excludes those unmatched rows - a common source of "my report is missing some customers" bugs that produce no error, just quietly wrong (incomplete) results.
  4. Trying to filter directly on a window function's output in the same query's WHERE clause. As explained above, this requires wrapping the windowed query as a subquery/CTE and filtering in the outer query instead - window functions and WHERE operate at different logical stages of query evaluation.
  5. Reaching for RANK() when ROW_NUMBER() is what's actually needed for a strict "give me exactly N rows" requirement, or vice versa when ties genuinely should share a rank (e.g. a leaderboard where tied scores should display the same position) - the right choice depends on whether ties in the underlying data should be collapsed to the same output value or forced into an arbitrary distinct order.
  6. Writing a correlated subquery that re-scans a large table once per outer row without considering the performance cost. Correlated subqueries are conceptually (and, depending on the query planner, sometimes literally) re-evaluated per outer row - on a large table this can be dramatically slower than an equivalent join or window-function formulation; it's worth knowing multiple ways to express the same logical question, since they're not always equally efficient even when they return identical results (a theme 2.3's indexing material develops further).
