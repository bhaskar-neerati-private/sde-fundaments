2.2 SQL Querying

Objective: write joins, aggregations, subqueries, and window functions fluently without looking up syntax.

2.2a Joins & Aggregations

A JOIN combines rows from two or more tables based on a related column. INNER JOIN returns only rows matching in both tables. LEFT JOIN returns all rows from the left table plus matches from the right (NULL where no match). GROUP BY groups rows sharing a value so aggregate functions (COUNT, SUM, AVG, MAX, MIN) compute per-group instead of over the whole table. HAVING filters groups after aggregation - unlike WHERE, which filters rows before aggregation (and so can't reference an aggregate value that doesn't exist yet at that stage).

Plain English: joins reassemble data that normalization deliberately split across tables (2.1) back together for querying. GROUP BY + aggregates answer "what's true about each group" (total spent per customer) instead of "what's true about each row."

Analogy: JOIN is matching socks from two baskets by a shared tag (customer_id) - INNER JOIN keeps only matched pairs; LEFT JOIN keeps every left sock even with no match (an empty partner). GROUP BY is sorting a pile of receipts into per-customer stacks, then summing each stack separately instead of one giant total.

SELECT o.order_id, u.name
FROM orders o
INNER JOIN users u ON o.user_id = u.user_id;

SELECT u.name, COUNT(o.order_id) AS order_count
FROM users u
LEFT JOIN orders o ON u.user_id = o.user_id
GROUP BY u.name;
-- LEFT JOIN keeps users with ZERO orders (order_count = 0) -- INNER JOIN would exclude them entirely

SELECT user_id, SUM(quantity * price) AS total_spent
FROM order_items oi
JOIN products p ON oi.product_id = p.product_id
JOIN orders o ON oi.order_id = o.order_id
GROUP BY user_id
HAVING SUM(quantity * price) > 100;    -- filters GROUPS, not individual rows

2.2b Subqueries & Window Functions

A subquery is a query nested inside another, used as a value/table/condition. A correlated subquery references a column from the outer query, so it's conceptually re-evaluated once per outer row. A window function computes a value across a set of rows related to the current row (a "window," defined by OVER (...)) without collapsing rows into one output row per group - unlike GROUP BY, which does collapse.

Plain English: a correlated subquery is "for each row, ask this same question again, scoped to this row." Window functions solve what GROUP BY can't: "rank each order among that customer's orders, but keep every order as its own row" - GROUP BY would collapse everything into one row per customer, losing individual orders.

Analogy: correlated subquery - "for each student, what's the highest score in their own class" - "their own class" changes per student, so the question is re-asked per student. Window function - handing every student their personal class rank on their own report card, without a separate summary page hiding everyone's individual data.

-- subquery as a filter
SELECT name FROM products WHERE price > (SELECT AVG(price) FROM products);

-- correlated subquery: was this order above THAT customer's own average?
SELECT o.order_id, o.user_id
FROM orders o
WHERE o.total > (SELECT AVG(o2.total) FROM orders o2 WHERE o2.user_id = o.user_id);

-- window function: rank each order within its own customer's orders, rows NOT collapsed
SELECT order_id, user_id, total,
       RANK() OVER (PARTITION BY user_id ORDER BY total DESC) AS rank_within_customer
FROM orders;

-- top 3 orders per customer by value
SELECT * FROM (
    SELECT order_id, user_id, total,
           ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY total DESC) AS rn
    FROM orders
) ranked
WHERE rn <= 3;

PARTITION BY vs GROUP BY: PARTITION BY (inside OVER()) divides rows into groups for the calculation only - every original row still appears in the output, just with an extra computed column. GROUP BY actually collapses multiple rows into one per group.

RANK() vs ROW_NUMBER(): RANK() gives ties the same rank and skips subsequent numbers (1,1,3). ROW_NUMBER() always gives distinct sequential numbers even on ties (1,2,3) - useful specifically for "give me exactly top-3," since ties under RANK() could otherwise produce more than 3 rows.
