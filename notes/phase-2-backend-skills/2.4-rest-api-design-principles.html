2.4 REST API Design Principles

Objective: design a REST API's resources, HTTP methods, status codes, and versioning strategy correctly - before writing a line of implementation code.

REST (REpresentational State Transfer) is an architectural style organizing APIs around resources (nouns, e.g. /users, /orders) manipulated via a small, standard set of HTTP methods (verbs: GET, POST, PUT, PATCH, DELETE) mapping to CRUD-like operations, using HTTP status codes to communicate outcome, with each request stateless - the server holds no memory of prior requests; all necessary context travels with each request.

Plain English: instead of inventing custom action-named endpoints for everything (/getUserById, /createNewOrder - "RPC-style"), REST organizes around resources: the same URL (/users/42) means different things depending on which HTTP verb is used (GET = fetch, PUT/PATCH = update, DELETE = remove). A small, predictable, reusable vocabulary instead of an ever-growing list of bespoke endpoint names.

Analogy: resources are shelf locations in a warehouse; HTTP verbs are a small fixed set of actions a forklift operator can perform at any shelf (pick up = GET, place a new item = POST, replace what's there = PUT, remove it = DELETE) - no unique tool needed per shelf, because the action is decoupled from which shelf you're at.

Resource naming: plural nouns for collections (/users, not /getUsers); nested resources for relationships (/users/42/orders); avoid verbs in URLs where possible - model actions as state changes instead (PATCH /orders/42 with {"status": "cancelled"} rather than /orders/42/cancel, though the latter is borderline-acceptable for actions that don't map cleanly to CRUD).

HTTP methods:

Method Meaning
GET /users list (safe, no side effects, cacheable)
GET /users/42 fetch one
POST /users create new (server assigns the ID)
PUT /users/42 replace entirely
PATCH /users/42 partial update
DELETE /users/42 remove

Status codes:

Code Meaning
200 OK success (GET, successful PUT/PATCH)
201 Created successful POST that created a resource
204 No Content success, nothing to return (e.g. DELETE)
400 Bad Request malformed request
401 Unauthorized missing/invalid authentication
403 Forbidden authenticated but not allowed
404 Not Found resource doesn't exist
422 Unprocessable Entity well-formed request, validation failed
500 Internal Server Error server's fault

Versioning: URL versioning (/v1/users - simplest, most visible) vs. header versioning (Accept: application/vnd.myapi.v1+json - cleaner URLs, less discoverable). URL versioning is the more common default in practice.

Pagination: offset/limit (?offset=20&limit=10 - simple, but can skip/duplicate items if data changes mid-pagination) vs. cursor-based (?cursor=abc123 - stable under concurrent inserts/deletes, preferred for large or frequently-changing datasets).

Putting it together - what actual requests/responses look like:

POST /users HTTP/1.1
Content-Type: application/json

{"name": "Alice", "email": "alice@example.com"}

HTTP/1.1 201 Created
Location: /users/42
Content-Type: application/json

{"id": 42, "name": "Alice", "email": "alice@example.com"}

GET /users?limit=10&offset=20 HTTP/1.1

HTTP/1.1 200 OK
Content-Type: application/json

{
  "items": [{"id": 21, "name": "..."}, ...],
  "limit": 10,
  "offset": 20,
  "total": 143
}

GET /users/999 HTTP/1.1

HTTP/1.1 404 Not Found
Content-Type: application/json

{"error": "User 999 not found"}

Three separate requests to the same general shape of URL (/users), each producing a different, predictable status code and body - this predictability, not any specific framework, is what "RESTful" actually buys you.
