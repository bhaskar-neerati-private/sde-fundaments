2.4 REST API Design Principles

Objective: design a REST API's resources, HTTP methods, status codes, and versioning strategy correctly - before writing a line of implementation code.

REST (REpresentational State Transfer) is an architectural style organizing APIs around resources (nouns, e.g. /users, /orders) manipulated via a small, standard set of HTTP methods (verbs: GET, POST, PUT, PATCH, DELETE) mapping to CRUD-like operations, using HTTP status codes to communicate outcome, with each request stateless - the server holds no memory of prior requests; all necessary context travels with each request.

Plain English: instead of inventing custom action-named endpoints for everything (/getUserById, /createNewOrder - "RPC-style"), REST organizes around resources: the same URL (/users/42) means different things depending on which HTTP verb is used (GET = fetch, PUT/PATCH = update, DELETE = remove). A small, predictable, reusable vocabulary instead of an ever-growing list of bespoke endpoint names.

Analogy: resources are shelf locations in a warehouse; HTTP verbs are a small fixed set of actions a forklift operator can perform at any shelf (pick up = GET, place a new item = POST, replace what's there = PUT, remove it = DELETE) - no unique tool needed per shelf, because the action is decoupled from which shelf you're at.

Why statelessness specifically matters, not just as a style preference: if the server held per-client session state in memory, that client's requests would need to always reach the same server instance, complicating load balancing and making horizontal scaling (adding more server instances) much harder - a crashed server would also silently lose that client's context. Statelessness means any server instance can handle any request as long as it has access to the same backing data store, which is exactly what makes REST APIs straightforward to scale horizontally.

Resource naming: plural nouns for collections (/users, not /getUsers); nested resources for relationships (/users/42/orders); avoid verbs in URLs where possible - model actions as state changes instead (PATCH /orders/42 with {"status": "cancelled"} rather than /orders/42/cancel, though the latter is borderline-acceptable for actions that don't map cleanly to CRUD).

HTTP methods:

Method Meaning
GET /users list (safe, no side effects, cacheable)
GET /users/42 fetch one
POST /users create new (server assigns the ID)
PUT /users/42 replace entirely
PATCH /users/42 partial update
DELETE /users/42 remove

Why PUT and PATCH are genuinely different, not interchangeable: PUT means "replace this resource entirely with what I'm sending" - any field omitted from the request body is conceptually treated as absent/reset in the new version. PATCH means "apply only these specific changes" - omitted fields stay untouched. Sending a partial payload to a PUT endpoint can silently wipe out fields the client didn't intend to touch, which is exactly the failure mode PATCH exists to avoid.

Status codes:

Code Meaning
200 OK success (GET, successful PUT/PATCH)
201 Created successful POST that created a resource
204 No Content success, nothing to return (e.g. DELETE)
400 Bad Request malformed request
401 Unauthorized missing/invalid authentication
403 Forbidden authenticated but not allowed
404 Not Found resource doesn't exist
422 Unprocessable Entity well-formed request, validation failed
500 Internal Server Error server's fault

Why 401 and 403 are distinct, not synonyms for "access denied": 401 means the server doesn't know who's asking (missing or invalid credentials - the fix is to authenticate). 403 means the server does know who's asking, and that identity is specifically not allowed to do this (the fix is not "log in differently," it's "this account genuinely lacks permission"). Conflating them gives clients misleading signals about what action would actually resolve the error.

Why 400 and 422 are distinct: 400 means the request itself is malformed at a structural level (invalid JSON, missing required headers) - the server can't even meaningfully parse what was sent. 422 means the request was well-formed and parseable, but the content fails validation rules (e.g. an email field containing a syntactically valid JSON string that isn't a valid email address). This distinction lets clients tell "I sent garbage" apart from "I sent a well-structured but invalid value."

Versioning: URL versioning (/v1/users - simplest, most visible) vs. header versioning (Accept: application/vnd.myapi.v1+json - cleaner URLs, less discoverable). URL versioning is the more common default in practice.

Pagination: offset/limit (?offset=20&limit=10 - simple, but can skip/duplicate items if data changes mid-pagination) vs. cursor-based (?cursor=abc123 - stable under concurrent inserts/deletes, preferred for large or frequently-changing datasets).

Why offset/limit pagination can skip or duplicate items concretely: if a new row is inserted before the current page's offset while a client is paging through results, every subsequent page's offset now points one row later than intended relative to the original ordering - the row that would have been at position 20 shifts to position 21, causing the client's next offset=20 request to either re-show a row already seen (duplicate) or skip one entirely, depending on the direction of the shift. Cursor-based pagination avoids this by anchoring to a specific row's identity/position (e.g. "everything after row with ID X") rather than a numeric position that shifts as the underlying data changes.

Putting it together - what actual requests/responses look like:

POST /users HTTP/1.1
Content-Type: application/json

{"name": "Alice", "email": "alice@example.com"}

HTTP/1.1 201 Created
Location: /users/42
Content-Type: application/json

{"id": 42, "name": "Alice", "email": "alice@example.com"}

GET /users?limit=10&offset=20 HTTP/1.1

HTTP/1.1 200 OK
Content-Type: application/json

{
  "items": [{"id": 21, "name": "..."}, ...],
  "limit": 10,
  "offset": 20,
  "total": 143
}

GET /users/999 HTTP/1.1

HTTP/1.1 404 Not Found
Content-Type: application/json

{"error": "User 999 not found"}

Three separate requests to the same general shape of URL (/users), each producing a different, predictable status code and body - this predictability, not any specific framework, is what "RESTful" actually buys you.

Common mistakes & misconceptions

  1. Using verbs in URLs out of habit from RPC-style API design (/getUser, /createOrder), instead of modeling the action as an HTTP verb applied to a resource noun. This isn't just a style preference - it defeats the predictable, reusable vocabulary that makes REST APIs learnable at a glance, forcing clients to learn a bespoke endpoint name per action instead of a small fixed set of verbs.
  2. Using PUT for a partial update. As explained above, PUT semantically means full replacement - sending only the changed fields to a PUT endpoint can silently null out or reset every omitted field, a genuinely dangerous and easy-to-miss bug.
  3. Returning 200 OK for every response regardless of what actually happened, including error cases communicated only via a body field like {"success": false}. This defeats the purpose of HTTP status codes (which let clients, proxies, caches, and monitoring tools react correctly without parsing the response body) and is a common anti-pattern in APIs that don't fully embrace REST conventions.
  4. Conflating 401 and 403, or 400 and 422, as interchangeable "something went wrong" codes. As explained above, each pair signals a meaningfully different required fix, and collapsing the distinction gives API consumers less actionable information.
  5. Using offset/limit pagination for a large, frequently-changing dataset without considering the skip/duplicate risk explained above - cursor-based pagination is the standard fix specifically for this failure mode, not just a marginal optimization.
  6. Assuming REST requires JSON, or requires resource URLs to exactly mirror the database schema. Neither is true - REST is an architectural style about resources/verbs/statelessness/status codes, not a specific data format or a mandate that every API resource map 1:1 to a database table; a resource can be a computed/aggregated view that has no single corresponding table at all.
