2.3 Indexing & Query Performance

Objective: explain how a B-tree index speeds up lookups, when an index helps vs. hurts, and read a query plan (EXPLAIN) to diagnose a slow query.

A database index is a separate, auxiliary data structure (most commonly a B-tree) storing a sorted mapping from a column's values to the physical location of matching rows - letting the database find matches via O(log n) lookups instead of an O(n) full table scan. An index speeds up reads that filter/sort/join on the indexed column(s), but slows down writes (INSERT/UPDATE/DELETE), since the index itself must also be updated on every write, and it consumes extra disk space.

Plain English: without an index, finding matching rows means checking every row (a "full table scan," O(n)) - like flipping through every page of a book to find a topic. An index is the book's index page: sorted, pointing directly to the right page, O(log n) via a B-tree's balanced structure (same complexity story as 1.10's balanced BST - a B-tree is a wider, shallower generalization tuned for disk access). Writes get slower because every write touching an indexed column must also update the index's own sorted structure (rebalance the B-tree) - more indexes means more work per write, not just more disk space.

Analogy: an index is a library's card catalog - instead of walking every aisle checking every spine (full scan), look up the topic in the catalog and go straight to the shelf. But every new book arriving also requires updating the catalog - that's the write cost of maintaining it; skip that step and the catalog goes stale.

CREATE INDEX idx_orders_user_id ON orders(user_id);

EXPLAIN SELECT * FROM orders WHERE user_id = 42;
-- before index: "Seq Scan on orders"                        (full table scan, O(n))
-- after index:  "Index Scan using idx_orders_user_id"        (O(log n) + retrieval)

Why a B-tree specifically, not the plain BST from 1.10: a BST is tuned for in-memory access, where following a pointer to any node costs roughly the same regardless of where it lives. Disk access is drastically different - reading anything from disk incurs a large fixed latency per read, so the goal shifts from "minimize comparisons" to "minimize the number of disk reads (tree levels)." A B-tree achieves this by making each node hold many keys and children (not just 2), keeping the tree very wide and shallow - a B-tree indexing millions of rows might only be 3-4 levels deep, meaning a lookup costs only 3-4 disk reads, versus the many more levels a binary-branching tree would need for the same number of entries.

When an index actually hurts: on a column with low cardinality (few distinct values, e.g. a boolean is_active), an index often isn't worth it - the query planner may skip it anyway, since filtering on a near-50/50 split doesn't narrow things down much (matching roughly half the table via an index, then fetching each matching row individually, can actually be slower than just scanning the whole table sequentially), yet the index still pays its full write-maintenance cost on every insert/update. Same logic for columns rarely queried, or on a write-heavy, rarely-read table - you're trading write speed for a read benefit that's rarely cashed in.

Reading EXPLAIN output, concretely: Seq Scan means the planner is reading every row in table order - expected and fine for small tables or queries that genuinely need most of the rows, but a red flag on a large table with a highly selective filter. Index Scan means the planner is using an index to jump directly to matching rows. Between these, Bitmap Index Scan/Bitmap Heap Scan is a hybrid the planner uses when a filter matches enough rows that jumping to each individually (via a plain Index Scan) would cost more random disk access than worth it, but few enough that a full sequential scan is still wasteful - it builds an in-memory bitmap of matching row locations from the index, then reads those in an efficient, mostly-sequential order.

Common mistakes & misconceptions

  1. Believing "add an index" is always a safe, free performance win. As explained above, every index adds real write overhead and disk space cost on every table modification - indexing every column "just in case" is a common anti-pattern that can make write-heavy workloads meaningfully slower without a corresponding read benefit.
  2. Adding an index on a low-cardinality column expecting it to help. As explained above, a near-uniform boolean or few-value column often doesn't narrow the search enough to justify the index - the query planner may ignore such an index entirely and fall back to a sequential scan, making the index pure overhead.
  3. Assuming a query is automatically using an available index. The query planner decides based on estimated cost, table statistics, and data distribution - it's entirely possible for an index to exist and still not be used for a specific query (e.g. if the planner estimates a sequential scan is actually cheaper for that particular filter). Always verify with EXPLAIN rather than assuming.
  4. Confusing "index exists" with "index is being used for this specific query." A composite index on (a, b) can typically be used for queries filtering on a alone, but usually cannot be used efficiently for queries filtering on b alone (without a) - index usability depends heavily on how the query's filter conditions align with the index's actual column order.
  5. Not distinguishing between a full table scan being a problem versus being the correct plan. For a small table, or a query that's genuinely expected to return most of the table's rows, a sequential scan can be the fastest available option - reflexively treating every Seq Scan in an EXPLAIN output as a bug to fix, without considering the table size and selectivity, is a common overcorrection.
