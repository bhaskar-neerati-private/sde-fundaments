2.3 Indexing & Query Performance

Objective: explain how a B-tree index speeds up lookups, when an index helps vs. hurts, and read a query plan (EXPLAIN) to diagnose a slow query.

A database index is a separate, auxiliary data structure (most commonly a B-tree) storing a sorted mapping from a column's values to the physical location of matching rows - letting the database find matches via O(log n) lookups instead of an O(n) full table scan. An index speeds up reads that filter/sort/join on the indexed column(s), but slows down writes (INSERT/UPDATE/DELETE), since the index itself must also be updated on every write, and it consumes extra disk space.

Plain English: without an index, finding matching rows means checking every row (a "full table scan," O(n)) - like flipping through every page of a book to find a topic. An index is the book's index page: sorted, pointing directly to the right page, O(log n) via a B-tree's balanced structure (same complexity story as 1.10's balanced BST - a B-tree is a wider, shallower generalization tuned for disk access). Writes get slower because every write touching an indexed column must also update the index's own sorted structure (rebalance the B-tree) - more indexes means more work per write, not just more disk space.

Analogy: an index is a library's card catalog - instead of walking every aisle checking every spine (full scan), look up the topic in the catalog and go straight to the shelf. But every new book arriving also requires updating the catalog - that's the write cost of maintaining it; skip that step and the catalog goes stale.

CREATE INDEX idx_orders_user_id ON orders(user_id);

EXPLAIN SELECT * FROM orders WHERE user_id = 42;
-- before index: "Seq Scan on orders"                        (full table scan, O(n))
-- after index:  "Index Scan using idx_orders_user_id"        (O(log n) + retrieval)

When an index actually hurts: on a column with low cardinality (few distinct values, e.g. a boolean is_active), an index often isn't worth it - the query planner may skip it anyway, since filtering on a near-50/50 split doesn't narrow things down much, yet the index still pays its full write-maintenance cost on every insert/update. Same logic for columns rarely queried, or on a write-heavy, rarely-read table - you're trading write speed for a read benefit that's rarely cashed in.
