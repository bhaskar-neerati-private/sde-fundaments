2.6 Debugging Techniques & Tools

Objective: debug systematically (reproduce → isolate → hypothesize → verify) using a real debugger instead of scattering print() statements.

Systematic debugging follows a repeatable cycle: Reproduce (get a reliable, minimal way to trigger the bug) → Isolate (narrow down where the problem originates, often via bisection) → Hypothesize (form a specific, falsifiable guess about the root cause) → Verify (test the hypothesis directly, e.g. by inspecting state at the suspected point) - repeating until the actual root cause is found and confirmed, instead of randomly changing code and hoping ("print-and-pray" debugging).

Plain English: print() debugging means guessing where to look and re-running the whole program every time you want to check a new spot - you have to predict every piece of state you'll want to see, in advance. A real debugger (pdb) lets you pause execution at an exact point (a breakpoint) and interactively inspect/modify any variable, step line by line, or jump to the next breakpoint - you explore state live instead of guessing upfront.

Analogy: print() debugging is drilling a bunch of holes in a wall in advance based on guesses, then checking each hole one at a time. Using a real debugger is being able to pause time and walk through the walls freely, inspecting anywhere, exactly when needed - not committing to guesses in advance.

import pdb

def calculate_total(items):
    total = 0
    for item in items:
        pdb.set_trace()          # execution pauses here, drops into an interactive prompt
        total += item['price'] * item['quantity']
    return total

# breakpoint() is the Python 3.7+ shortcut, same effect as pdb.set_trace()

# pdb commands once paused:
#   n  - next line (step OVER function calls)
#   s  - step INTO a function call
#   c  - continue until next breakpoint
#   p item  - print the value of `item` right now
#   l  - list surrounding source code
#   q  - quit debugging

The method, applied: reproduce the bug with a minimal failing case first (don't debug against a huge, noisy scenario) → isolate by bisecting the code (breakpoint at progressively narrower regions until the exact failing line is found) → hypothesize a specific cause ("I think item['price'] is a string here, not a number") → verify by inspecting that exact variable at that exact point with the debugger, confirming or refuting the hypothesis before making any code changes. Changing code before confirming the hypothesis is exactly the "print-and-pray" failure mode this method exists to avoid.
