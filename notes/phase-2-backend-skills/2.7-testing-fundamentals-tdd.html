2.7 Testing Fundamentals & TDD

Objective: write unit and integration tests with pytest, and practice red-green-refactor TDD for at least one feature.

2.7a pytest Fundamentals

pytest discovers and runs test functions (prefixed test_, in files prefixed test_ or suffixed _test.py) using plain assert statements (no special assertX methods needed), and uses fixtures (@pytest.fixture) to provide reusable setup/teardown state via dependency injection - a test function simply declares a fixture as a parameter name, and pytest supplies it automatically.

Plain English: plain assert value == expected gives clear, readable failure output showing exactly what was and what was expected, with no assertEqual(a, b) boilerplate. Fixtures solve "every test needs fresh, isolated setup (a test DB, a sample object) and cleanup afterward" without copy-pasting that setup into every test - same spirit as 1.1d's context managers avoiding duplicated try/finally cleanup.

Analogy: a fixture is a stagehand setting up the exact same props before every scene (test) that needs them, and clearing the stage after - each scene starts from a known clean state without actors (test functions) setting up their own props by hand.

import pytest

def add(a, b): return a + b

def test_add_positive_numbers():
    assert add(2, 3) == 5

@pytest.fixture
def sample_client():
    client = TestClient(app)      # setup: runs before the test using it
    yield client                   # test runs here
    # cleanup would go here, after yield -- same shape as @contextmanager (1.1d)

def test_get_user(sample_client):
    response = sample_client.get("/users/1")
    assert response.status_code == 200
    assert response.json()["name"] == "Alice"

@pytest.mark.parametrize("a,b,expected", [(1, 1, 2), (2, 3, 5), (-1, 1, 0)])
def test_add_parametrized(a, b, expected):
    assert add(a, b) == expected     # runs 3 times, once per tuple

Why pytest needs no special assertion methods, unlike unittest's assertEqual/assertTrue/etc.: pytest rewrites the bytecode of plain assert statements at test-collection time to capture the actual values of each subexpression, so a failure can report exactly what add(2, 3) evaluated to and what it was compared against - without this introspection, a bare assert failure would only say "assertion failed," with no detail about why. This is what lets pytest offer both the readability of plain assert and the informative failure output that unittest's special methods were originally designed to provide.

Why @pytest.fixture uses yield instead of return: exactly the same @contextmanager shape from 1.1d - everything before yield is setup that runs before the test, everything after yield is cleanup guaranteed to run after the test finishes, regardless of whether it passed or failed. A fixture using return instead of yield has no way to express "and afterward, clean this up."

2.7b The TDD Workflow

Test-Driven Development (TDD) follows Red-Green-Refactor: (1) Red - write a test for not-yet-implemented behavior, confirm it fails (proving the test actually exercises something real); (2) Green - write the minimum code to make it pass, no over-engineering; (3) Refactor - clean up the implementation (and/or test) while keeping all tests passing, now that a safety net proves correctness at every step.

Plain English: writing the test first forces you to think about expected behavior before being biased by an existing implementation. "Confirm it fails first" catches a common mistake - a test that always passes regardless of correctness (a typo in the assertion, testing the wrong thing) - invisible if you write the implementation first and the test just happens to pass immediately.

Analogy: a locksmith who, before building a new lock, first builds a duplicate key to a lock that doesn't exist yet and tries it (Red - confirms nothing currently satisfies it), then builds the simplest lock the key actually opens (Green), and only afterward reinforces/polishes the construction (Refactor) - always keeping the working key nearby to confirm the lock still opens after every adjustment.

# RED - write the test first, watch it fail (endpoint doesn't exist yet)
def test_mark_task_complete(sample_client):
    response = sample_client.patch("/tasks/1/complete")
    assert response.status_code == 200
    assert response.json()["completed"] is True
# running now: fails with 404 -- confirms the test is real

# GREEN - minimum code to pass
@app.patch("/tasks/{task_id}/complete")
def complete_task(task_id: int, db: Session = Depends(get_db)):
    task = db.query(Task).filter(Task.id == task_id).first()
    task.completed = True
    db.commit()
    return task
# running now: passes

# REFACTOR - add the 404-if-missing case, re-run ALL tests after, not just the new one
@app.patch("/tasks/{task_id}/complete")
def complete_task(task_id: int, db: Session = Depends(get_db)):
    task = db.query(Task).filter(Task.id == task_id).first()
    if task is None:
        raise HTTPException(status_code=404, detail="Task not found")
    task.completed = True
    db.commit()
    db.refresh(task)
    return task

Why the order matters: implementation-first, tests-after tends to produce tests shaped around "what the code happens to do" rather than "what the code is supposed to do" - TDD's ordering keeps the test honest and requirement-driven, not implementation-driven. Writing the assertion first also forces a concrete, specific definition of "done" before any implementation exists, which is often harder to pin down accurately in hindsight, after an implementation is already shaping how you think about the feature.

Why the "Refactor" step re-runs all tests, not just the one just added: the safety net TDD builds up is cumulative - every previously-green test is a guarantee that a specific piece of behavior still works. Refactoring without re-running the full suite risks silently breaking something the new test doesn't cover, defeating the entire purpose of having a growing regression-catching test suite in the first place.

Common mistakes & misconceptions

  1. Skipping the "confirm it fails" step of Red, jumping straight to writing the implementation and the test together. As explained above, this is exactly how a broken test (one that would pass regardless of whether the feature actually works, due to a typo or wrong assertion) slips through unnoticed - watching it fail first is the only way to confirm the test genuinely exercises the intended behavior.
  2. Over-implementing during Green, writing more functionality than the current failing test actually requires. This works against TDD's incremental discipline - each cycle should add just enough code to pass the current test, with additional behavior driven by additional tests, not anticipated in advance.
  3. Using return instead of yield in a fixture that needs cleanup, losing the guaranteed teardown that yield combined with pytest's fixture lifecycle provides - any resource opened in a return-based fixture has no reliable mechanism to ensure it's released after the test.
  4. Writing tests that depend on execution order or shared mutable state between tests, rather than using fixtures to provide fresh, isolated state per test. Tests that pass or fail depending on what ran before them are a common and frustrating source of flaky, hard-to-debug test suites.
  5. Confusing unit tests (isolated, fast, testing one piece of logic) with integration tests (exercising multiple components together, e.g. a full API request through to the database). Both have their place, but conflating them - or only writing one kind - leaves gaps: unit tests alone can miss real integration bugs (like a wrong SQL join), while integration tests alone are slower and make it harder to pinpoint exactly which piece of logic broke when something fails.
  6. Treating "the test suite is green" as proof of correctness rather than proof of coverage. A passing suite only guarantees the behaviors that were actually tested work as asserted - it says nothing about untested edge cases or requirements the tests never captured in the first place.
