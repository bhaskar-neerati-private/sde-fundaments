3.4 Multiprocessing & Asyncio

Objective: choose correctly between threading, multiprocessing, and asyncio for a given workload, and implement a basic solution with each.

3.4a Multiprocessing

The multiprocessing module achieves true parallelism for CPU-bound work by running code in separate OS processes, each with its own independent Python interpreter and its own GIL. Since the GIL only prevents multiple threads within a single process from running bytecode simultaneously, multiple processes - each with their own GIL - genuinely execute bytecode in parallel across CPU cores. Cost: each process has its own memory space (no sharing by default - data must be explicitly serialized/copied, e.g. via pickling, when passed between processes), heavier startup, higher baseline memory.

Plain English: multiprocessing doesn't "get around" the GIL's restriction - it's just not subject to it, because the restriction is "one GIL per process," and now there are multiple processes, each with its own. Trade-off: threads within one process share memory freely (part of why the GIL exists - to protect that shared memory); separate processes share nothing by default, so passing data between them costs real serialization overhead.

Analogy: multithreading is several workers sharing one office with one filing cabinet (memory) - efficient for passing notes, but needing the one-desk rule (GIL) to avoid chaos. Multiprocessing is opening several entirely separate offices, each with its own staff and cabinet - genuine parallel work, no shared-desk bottleneck, but if one office needs info from another, someone has to photocopy and mail the documents over (serialization cost) instead of walking to a shared cabinet.

from multiprocessing import Pool

def cpu_bound_task(n):
    total = 0
    for i in range(n): total += i * i
    return total

if __name__ == "__main__":
    with Pool(processes=4) as pool:
        results = pool.map(cpu_bound_task, [10_000_000] * 4)
    # DOES show real speedup roughly proportional to CPU cores used --
    # each process has its own GIL, unlike the threading version in 3.3

3.4b Asyncio

asyncio provides cooperative concurrency within a single thread - an async function voluntarily yields control at each await point back to an event loop, which runs some other pending task while the first waits (e.g. on I/O), resuming the original once its awaited operation completes. Best for high-volume I/O-bound work (many concurrent network calls, DB queries) where managing many OS threads/processes would itself become the bottleneck.

Plain English: both asyncio and threading help I/O-bound work by not blocking on individual waits, but differently. Threading relies on the OS juggling real threads, each with real (if lightweight) per-thread overhead. Asyncio does the juggling itself, in Python, within a single thread, using await as an explicit "I'm about to wait, run something else now" handoff - dramatically cheaper for thousands of concurrent I/O-waiting tasks than thousands of actual OS threads would be.

Analogy: one waiter handling many tables by never standing idle at one waiting for food - takes an order (starts a task), immediately moves to another table while it cooks (an await point hands control back), returns to serve that table once ready (the awaited operation completes), repeats across many tables. One person, handling many things "concurrently," by never blocking idly on any single one - vs. threading, which is like hiring a separate waiter per table (each can genuinely stand and wait, but hiring/managing many waiters has its own overhead).

import asyncio

async def io_bound_task(task_id):
    print(f"Task {task_id} starting")
    await asyncio.sleep(1)     # yields control back to the event loop during this "wait"
    print(f"Task {task_id} done")
    return task_id

async def main():
    return await asyncio.gather(*[io_bound_task(i) for i in range(4)])

asyncio.run(main())
# all 4 tasks' 1-second sleeps overlap -- total runtime ~1s, not ~4s, with ONE thread

Choosing between them - the actual interview-relevant skill:

Workload Choice
CPU-bound (e.g. image processing, heavy computation) multiprocessing - true parallelism, bypasses the GIL
I/O-bound, moderate concurrency, or needs non-async-aware libraries threading
I/O-bound, high volume (thousands of concurrent connections) asyncio - cheapest per-task overhead

Using multiprocessing for I/O-bound work wastes heavy process overhead on work that was never CPU-limited. Using threading for CPU-bound work doesn't help at all - still bottlenecked by the single GIL.
