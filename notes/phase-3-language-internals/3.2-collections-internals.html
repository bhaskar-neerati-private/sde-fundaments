3.2 Collections Internals

Objective: understand how dict and list are actually implemented well enough to reason about their performance characteristics.

3.2a How Python Lists Work

Python's list is a dynamic array (not a linked list) - a contiguous block of memory holding pointers to the actual objects, over-allocated with extra capacity beyond the current length, so append() is usually O(1) (writes into already-reserved space, increments a length counter). When reserved capacity runs out, Python allocates a new, larger block, copies all pointers over, and frees the old block - this occasional O(n) resize, spread across many cheap O(1) appends, is why append() is amortized O(1), not always-O(1).

Plain English: the exact same "occasionally expensive, usually cheap" resizing story as 1.7b's hash-map resizing. insert(0, x) (front insert) is a completely different story: every existing element must physically shift over by one slot - O(n), always, no amortization helps, because unlike the reserved space at the end, there's no slack at the front to grow into.

Analogy: a row of parking spaces with a few extra reserved spots beyond your current cars (over-allocation) - parking in the next reserved space is instant (O(1) append). Squeezing a car in at the very front means physically pushing every other car back one space first (O(n) insert-at-front) - no amount of extra space further down helps with that.

def bench_append(n):
    lst = []
    for i in range(n):
        lst.append(i)              # total cost across n appends: O(n) -- O(1) each, amortized

def bench_insert_front(n):
    lst = []
    for i in range(n):
        lst.insert(0, i)            # total cost across n inserts: O(n^2) -- O(n) EACH

Why append stays amortized O(1) as size grows: the over-allocation factor means the total cost of all resize-copies across the list's entire growth history sums to O(n) overall, not O(n²) - spread across n appends, that's O(1) each on average, even though any individual append occasionally costs O(n) for that one resize.

3.2b How Python Dicts Work

The collision-resolution mechanics (why average lookup stays O(1) as a dict grows) are exactly 1.7b's content - CPython's dict uses open addressing with a custom pseudo-random probe sequence, not plain linear/quadratic probing.

What's new here: since 3.6 as an implementation detail (3.7 as a guaranteed language behavior), dict is actually two structures: a sparse, open-addressed array of indices (where the hash-collision machinery from 1.7b operates), plus a separate dense array holding the actual entries in the order they were inserted. Lookups go through the sparse index array to find which slot in the dense array holds a key. Iteration just walks the dense array directly - completely unaffected by however scrambled the sparse index array's internal layout is. That's why dict iteration order is insertion order.

Analogy: a nightclub with a bouncer's lookup sheet (the sparse hash-indexed array, deliberately scrambled for fast lookup) plus a separate plain guest logbook recording "who walked in, in order" (the dense array). Checking "is so-and-so inside" uses the scrambled lookup sheet for speed; reading "who came through the door, in order" just reads the logbook directly.

The practical payoff, benchmarked conceptually:

data_list = [(i, f"value{i}") for i in range(100_000)]
data_dict = dict(data_list)

def find_in_list(key):                # O(n) -- must scan
    for k, v in data_list:
        if k == key: return v
    return None

def find_in_dict(key):                  # O(1) average -- direct hash-based lookup
    return data_dict.get(key)

As size grows from 100 → 10k → 1M, find_in_list's time grows linearly; find_in_dict's time stays roughly flat - the concrete, measurable payoff of average O(1) vs. O(n).
