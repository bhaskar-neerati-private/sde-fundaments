3.1 Python Object Model & Memory Management

Objective: explain reference counting, garbage collection, mutability vs. immutability, and is vs. == correctly - including where they cause real bugs.

3.1a Mutability, is vs ==, and References

In Python, a variable is not a box holding a value - it's a name bound to an object living in memory. Assignment binds a name to an object reference; it doesn't copy the object. Multiple names can bind to the same object (aliasing). is checks whether two references point to the exact same object (identity, via id()). == checks whether two objects compare equal by value (calls __eq__, see 1.1a). Mutable objects (list, dict, set) can change contents after creation while identity stays the same; immutable objects (int, str, tuple, frozenset) can never change - any "modification" creates a brand-new object.

Plain English: a variable name is a sticky-note label on a box (the object), not the box itself. x = [1,2,3] creates a list and labels it "x". y = x sticks a second label on the same box - no copy. y.append(4) changes that shared box's contents, and since x labels the same box, x shows the change too.

Analogy: two roommates sharing one refrigerator, each holding a key (a variable name) to the same fridge. One puts milk in - the other's key opens the same fridge, milk's there too, because there's only one fridge, two keys. Compare that to each roommate having their own separate fridge that happens to currently hold identical contents - changing one wouldn't affect the other, even though you couldn't tell the difference just by looking inside.

x = [1, 2, 3]
y = x                    # y is ANOTHER LABEL on the SAME object, not a copy
y.append(4)
print(x)                  # [1, 2, 3, 4] -- x and y are literally the same object
print(x is y)               # True -- same object
print(x == y)                # True -- same contents

a = [1, 2, 3]
b = [1, 2, 3]                  # a genuinely separate object, equal contents
print(a is b)                    # False
print(a == b)                     # True

c = x.copy()                        # or list(x), or x[:] -- an actual new object
c.append(99)
print(x)                              # unaffected

The mutable-default-argument gotcha:

def append_item(item, lst=[]):      # DANGER
    lst.append(item)
    return lst

append_item(1)    # [1]
append_item(2)     # [1, 2]  <- SURPRISE: same default list object reused across calls

Default argument values are evaluated once, when def runs - not fresh per call. A mutable default becomes a single shared object silently reused (and mutated) across every call that doesn't pass its own. This is exactly the same object-identity/aliasing concept from above, just triggered by a much less obvious mechanism (a default argument expression, evaluated once at function-definition time and then reused as the same object on every subsequent call). Fix:

def append_item(item, lst=None):
    if lst is None:
        lst = []
    lst.append(item)
    return lst

is/== on small ints and strings: CPython caches small integers (-5 to 256) and sometimes interns short strings, so is can appear to work for equality on small values - purely an implementation detail, not a language guarantee.

x, y = 5, 5
print(x is y)       # True -- small-int cache, NOT guaranteed behavior

x, y = 1000, 1000
print(x is y)         # often False -- not cached, genuinely different objects (implementation-dependent)

Rule: always use == for value comparison; reserve is for identity comparison (is None, is True/False, or deliberately checking "is this the exact same object"). The small-int cache is specifically dangerous because it makes buggy code (if x is 5) appear to work correctly during casual testing on small values, then fail unpredictably once the same code encounters a larger int - relying on is for value comparison is a latent bug waiting for the right input, not a style nitpick.

3.1b Reference Counting & Garbage Collection

CPython manages memory primarily via reference counting: every object tracks how many references point to it; the count increments on new references, decrements when references are deleted/go out of scope/reassigned; at zero, the object is deallocated immediately. This fails for circular references - two (or more) objects referencing each other with no reference reaching in from outside - refcounting alone never reaches zero for such a cycle, even though nothing external can reach it. Python's supplementary cycle-detecting garbage collector (gc module) periodically scans for and cleans up unreachable cycles.

Plain English: refcounting is fast and immediate - deallocation happens the instant the last reference vanishes, no GC-pause waiting. But a circular reference is two people each holding an IOU promising to pay the other back - from outside, nobody owes either of them anything (no external references), but internally they're still "holding onto" each other, so pure counting never hits zero for either.

Analogy: refcounting is a library destroying a book the instant its last active checkout expires. A circular reference is two patrons each holding a "hold" on the book the other currently has - each book has a permanently nonzero hold count, even though neither patron is reachable from the library's active-readers list. The periodic cycle-collector is a librarian specifically checking "is anyone outside this closed loop still connected to it?" and clearing it if not.

import sys

x = []
sys.getrefcount(x)      # baseline (includes a temporary reference from the call itself)
y = x
sys.getrefcount(x)        # increased -- y also references the same object
del y
sys.getrefcount(x)          # decreased back

class Node:
    def __init__(self): self.other = None

a, b = Node(), Node()
a.other = b                  # a references b
b.other = a                    # b references a -- a cycle
del a
del b
# a and b are now unreachable from any code, but still reference EACH OTHER --
# pure refcounting would never free them; gc handles this case
import gc
gc.collect()                    # manually trigger a pass (also runs automatically, periodically)

Why del a; del b doesn't immediately free either Node, mechanically: del a only removes the name a from the local namespace - it decrements the refcount of whatever a pointed to, but doesn't necessarily bring it to zero. At that point, the object formerly named a still has one incoming reference: b.other. Symmetrically, the object formerly named b still has one incoming reference: a.other (now unreachable via any name, but still a live reference internally). Both objects' refcounts are stuck at 1, permanently, from pure refcounting's perspective - neither will ever hit zero on its own, which is precisely the scenario the cycle-detecting collector exists to find and resolve.

id(): returns a unique integer identifying an object for its lifetime (in CPython, literally its memory address). Two different objects can share the same id() value if their lifetimes never overlap - one deallocated before the other's id() happens to reuse that address. Can surprise you if you print id() on short-lived objects and see a value repeat - this isn't a bug or a coincidence, it's the direct, expected consequence of id() being tied to a memory address that gets reclaimed and reused once its previous occupant is deallocated.

Common mistakes & misconceptions

  1. Assuming y = x copies a mutable object. As emphasized above, it creates a second name bound to the exact same object - mutating through either name affects both, since there's genuinely only one object. Copying requires an explicit .copy(), list(x), x[:], or copy.deepcopy() for nested structures.
  2. Using a mutable default argument without realizing it's evaluated once at function-definition time, not fresh per call - see the append_item example above, a genuinely common and consequential real-world bug, not just an interview trivia question.
  3. Using is for value comparison, especially relying on the small-int/short-string caching behavior working "by accident" on small test values, then hitting confusing failures once real data includes larger numbers or longer strings where CPython's caching no longer applies.
  4. Believing Python has no garbage collector because it uses reference counting. Both mechanisms coexist - refcounting handles the common case immediately and cheaply, while the supplementary cycle-detecting gc module specifically handles the cases (circular references) that pure refcounting structurally cannot resolve on its own.
  5. Assuming id() values are permanently unique identifiers safe to store and compare later. They're only guaranteed unique among objects that are alive simultaneously - a deallocated object's id() can be reused by an entirely unrelated later object, making stored id() values potentially misleading once the original object's lifetime has ended.
  6. Confusing "immutable" with "can't be reassigned." A variable bound to an immutable object can still be reassigned to point at a different object (x = 5; x = 6 is perfectly legal) - immutability is a property of the object itself (it can never change in place), not a restriction on what a variable name can point to over time.
