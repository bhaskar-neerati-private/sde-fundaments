3.3 The GIL & Multithreading

Objective: explain what the GIL actually protects, why CPU-bound multithreading in CPython doesn't give a speedup, and when threading still helps (I/O-bound work). This is the single most commonly botched Python interview answer - get the wording precise, not approximate.

The GIL (Global Interpreter Lock) is a mutex in CPython allowing only one thread to execute Python bytecode at a time, even on a multi-core machine - it exists to protect CPython's internal data structures (like the reference counts from 3.1b) from race conditions without fine-grained locking everywhere. Consequence: CPU-bound multithreaded Python gets no speedup from more threads (only one thread ever executes bytecode at any instant - more threads just means more context-switching overhead). I/O-bound multithreaded code does benefit, because the GIL is released during blocking I/O (network calls, file reads, time.sleep), letting other threads run bytecode while one waits.

Plain English, precisely: the GIL locks bytecode execution, not "the whole thread," and not "I/O." A thread blocked on a network response isn't executing bytecode at that moment, so it releases the GIL while waiting, letting another thread run. A thread doing pure CPU computation (a tight math loop) is constantly executing bytecode, holding the GIL nearly continuously - adding more such threads doesn't add parallelism, just more threads competing for one lock, with switching overhead as a net negative.

Analogy: one office with a single desk holding the only copy of sensitive shared paperwork (Python's internal object state) - only one worker (thread) may sit and actively work at that desk at any instant. A worker on hold with a phone call (I/O) steps away from the desk while waiting, letting someone else use it - phone-call-heavy work (I/O-bound) still gets done efficiently with many workers around. A worker doing pure heads-down calculation at the desk occupies it continuously - adding more such workers doesn't speed up the calculation; there's still one desk, just more people waiting their turn.

import threading, time

def cpu_bound_task(n):
    total = 0
    for i in range(n): total += i * i
    return total
# single-threaded vs. 4 threads each doing n//4: NOT meaningfully faster,
# often slightly SLOWER (GIL contention + context-switch overhead)

def io_bound_task():
    time.sleep(1)          # simulates a network call -- GIL RELEASED during this wait
# single-threaded: 4 sequential calls -> ~4s total
# 4 threads concurrently: -> ~1s total -- meaningfully faster,
# because while one thread sleeps (GIL released), others run

Caveat worth knowing: CPython 3.13+ has an experimental free-threaded (no-GIL) build. Mention this as a caveat when discussing the GIL in interviews - the classic "no CPU speedup from threading" story is specifically about the traditional GIL-enabled build, still the default as of this writing.
