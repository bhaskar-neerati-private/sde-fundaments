# 10. 3Sum

**LeetCode:** [#15 - 3Sum](https://leetcode.com/problems/3sum/) · **Topic:** [Two Pointers](../topics/02-two-pointers.md) · **Difficulty:** Medium

## Problem statement

Given an integer array `nums`, return all the **unique** triplets `[nums[i], nums[j], nums[k]]` (distinct indices `i, j, k`) such that `nums[i] + nums[j] + nums[k] == 0`. The result must not contain duplicate triplets.

**Example:**
```
Input: nums = [-1,0,1,2,-1,-4]
Output: [[-1,-1,2],[-1,0,1]]
```

## Applicable approaches

- **Brute Force** — check every triplet with three nested loops.
- **Better — Hash Set** — fix two numbers, use a hash set to find the third in O(1).
- **Optimal — Sort + Two Pointers** — the standard, expected solution.

## Approach 1: Brute Force

### Intuition

The most literal interpretation of "find all triplets summing to zero": try every possible combination of 3 numbers and check whether they sum to zero. This is correct by exhaustion — every possible triplet genuinely gets examined — but the real difficulty in this problem isn't finding *a* correct approach, it's finding triplets *efficiently* and *without duplicates*, both of which this approach handles clumsily (duplicates require an extra set-based cleanup step, shown below, which is itself a sign the core algorithm isn't naturally duplicate-aware).

### Algorithm

1. Three nested loops over distinct indices `i < j < k`.
2. If `nums[i] + nums[j] + nums[k] == 0`, record that triplet (as a sorted tuple, to make de-duplication possible).
3. Use a `set` of these sorted tuples to automatically avoid duplicate triplets in the output.

### Python code
```python
def threeSum(nums):
    n = len(nums)
    result = set()
    for i in range(n):
        for j in range(i + 1, n):
            for k in range(j + 1, n):
                if nums[i] + nums[j] + nums[k] == 0:
                    triplet = tuple(sorted([nums[i], nums[j], nums[k]]))
                    result.add(triplet)
    return [list(t) for t in result]
```

### Line-by-line explanation

- Three nested loops generate every combination of 3 distinct indices without repeats (`j` starts after `i`, `k` starts after `j`) — this is the direct 3-dimensional generalization of the pair-generating double loop seen in Two Sum.
- `tuple(sorted([nums[i], nums[j], nums[k]]))` — sorting the triplet's *values* (not the array) means the same set of 3 values always produces the same tuple regardless of which index-order they were found in — this is what makes de-duplication via a `set` possible at all; without sorting first, `(-1, 2, -1)` and `(-1, -1, 2)` would be treated as different tuples despite representing the same triplet.
- `[list(t) for t in result]` — convert the set of tuples back to the list-of-lists format the problem expects.

### Time & space complexity

- **Time: O(n³)** for the triple-nested loop — this dominates over the set operations, since generating every combination of 3 indices out of n inherently requires examining `C(n,3)` combinations.
- **Space: O(n)** for the result set in the worst case (though bounded by the number of *distinct* valid triplets, which in practice is much smaller than n³).

## Approach 2: Better — Fix Two, Hash Set for the Third

### Intuition

The brute force's waste is trying every combination of *three* independently-chosen indices, when really only two of them need to vary freely — once two numbers are fixed, the third is completely determined (it must equal `-(a+b)`), which turns "check every triplet" into "for every pair, check one O(1) hash lookup instead of a third loop." This is a direct generalization of Two Sum's core trick, applied one level deeper: 3Sum reduces to "for each fixed first number, run Two Sum on the rest of the array with a target of `-nums[i]`."

*(This is a reasonable intermediate step conceptually, but in practice the sort + two-pointer approach below is what's expected in interviews for this exact problem, partly because it makes de-duplication far cleaner. This hash-set version is shown mainly to make explicit that the "fix some elements, hash-search for the rest" idea from 2Sum generalizes upward — not because it's the version you should default to writing.)*

### Algorithm

1. Sort the array first (makes de-duplication of the *first* number easy).
2. For each index `i` (skipping duplicate values of `nums[i]`), use a hash set to find pairs `(nums[j], nums[k])` with `j > i` such that `nums[j] + nums[k] == -nums[i]`, using the classic single-pass Two Sum hash trick restricted to the subarray after `i`.
3. Skip duplicate values carefully at each level to avoid duplicate triplets in the output.

### Python code
```python
def threeSum(nums):
    nums.sort()
    n = len(nums)
    result = []

    for i in range(n):
        if i > 0 and nums[i] == nums[i - 1]:
            continue  # skip duplicate first numbers
        if nums[i] > 0:
            break  # smallest number is positive, no triplet can sum to 0 anymore

        seen = set()
        for j in range(i + 1, n):
            complement = -nums[i] - nums[j]
            if complement in seen:
                triplet = [nums[i], nums[j], complement]
                if not result or result[-1] != sorted(triplet):
                    result.append(sorted(triplet))
            seen.add(nums[j])

    return result
```

*(Note: this version's duplicate-avoidance via `result[-1] != sorted(triplet)` is a simplification and isn't fully robust against all duplicate patterns spread non-adjacently in the result — the sort + two-pointer approach below handles duplicates far more cleanly, which is the main practical reason it's preferred over this one.)*

### Time & space complexity

- **Time: O(n²)** — the outer loop is O(n), and for each outer iteration, the inner hash-set pass is O(n) — this is strictly better than the brute force's O(n³) precisely because the innermost "search for the third number" step went from an O(n) *loop* (brute force's third nested loop) to an O(1) *lookup* (hash set membership check), the same speedup mechanism as Two Sum applied one level up.
- **Space: O(n)** for the `seen` set (recreated per outer iteration) plus the output.

## Approach 3: Optimal — Sort + Two Pointers

### Intuition

This is 3Sum built directly on top of the sorted-array Two Pointers pattern from the topic overview: **fix one number, then use two pointers to find the other two**, turning the "find a pair summing to X" sub-problem into the classic opposite-direction two-pointer scan (rather than a hash-set lookup). The reason this beats Approach 2 isn't asymptotic time (both are O(n²)) — it's that sorting also makes **skipping duplicate values trivial**, since equal values become adjacent after sorting, which is exactly what the hash-set version above struggled to handle cleanly.

**Why moving a pointer is provably safe here** (the core justification the topic overview insists on): once `nums[i]` is fixed and the array is sorted, we're solving "find `left, right` with `left < right` such that `nums[left] + nums[right] == -nums[i]`" — exactly the sorted-array pair-sum pattern. If the current sum is too small, only increasing `nums[left]` (by moving `left` right) can fix it, since the array is sorted ascending; moving `right` left could only decrease the sum further, which can't help when the sum is already too small. That's the same provably-safe-move argument from Two Sum II in the topic overview, applied here.

### Algorithm

1. Sort `nums`.
2. For each index `i` from 0 to n-1 (this will be the "fixed" first number of the triplet):
   - Skip if `nums[i]` is the same as the previous `nums[i-1]` (avoids duplicate triplets starting with the same value).
   - Since the array is sorted, if `nums[i] > 0`, no triplet starting here (or later) can ever sum to 0 — the smallest possible sum of three numbers from this point on is already positive, since every remaining number is ≥ `nums[i]` > 0 — break out of the loop entirely.
   - Set `left = i + 1`, `right = n - 1`. This is now a **Two Sum on a sorted subarray** problem: find `left, right` such that `nums[left] + nums[right] == -nums[i]`.
   - While `left < right`: compute `current_sum = nums[i] + nums[left] + nums[right]`.
     - If `current_sum < 0`: the sum is too small, move `left` right to increase it.
     - If `current_sum > 0`: the sum is too large, move `right` left to decrease it.
     - If `current_sum == 0`: found a valid triplet! Record it, then move **both** pointers inward, and additionally skip past any duplicate values at the new `left`/`right` positions to avoid duplicate triplets.

### Python code
```python
def threeSum(nums):
    nums.sort()
    n = len(nums)
    result = []

    for i in range(n):
        if i > 0 and nums[i] == nums[i - 1]:
            continue
        if nums[i] > 0:
            break

        left, right = i + 1, n - 1
        while left < right:
            current_sum = nums[i] + nums[left] + nums[right]
            if current_sum < 0:
                left += 1
            elif current_sum > 0:
                right -= 1
            else:
                result.append([nums[i], nums[left], nums[right]])
                left += 1
                right -= 1
                while left < right and nums[left] == nums[left - 1]:
                    left += 1
                while left < right and nums[right] == nums[right + 1]:
                    right -= 1

    return result
```

### Line-by-line explanation

- `nums.sort()` — essential setup; enables both the two-pointer scan and easy duplicate-skipping.
- `if i > 0 and nums[i] == nums[i - 1]: continue` — if this is the same value as the previous outer-loop number, any triplets we'd find starting here were already found starting from the previous (identical) `nums[i]`, since the *rest* of the array (from `i+1` onward) hasn't changed — skip to avoid duplicate output.
- `if nums[i] > 0: break` — since the array is sorted ascending, once `nums[i]` is positive, `nums[left]` and `nums[right]` (both to its right, so also ≥ `nums[i]` > 0) can only make the sum even larger — no triplet from here onward can ever reach 0. This is a `break`, not a `continue`, because once this becomes true for one `i`, it's true for every larger `i` too (sorted ascending).
- `left, right = i + 1, n - 1` — the two-pointer search range, always to the right of `i`.
- `current_sum = nums[i] + nums[left] + nums[right]` — the sum of the current triplet candidate.
- `if current_sum < 0: left += 1` — too small; since the array is sorted, moving `left` rightward strictly increases `nums[left]`, which increases the sum — this is the "provably safe move" from the intuition section, made concrete.
- `elif current_sum > 0: right -= 1` — too large; moving `right` leftward strictly decreases `nums[right]`, decreasing the sum.
- `else:` (sum is exactly 0) — record the triplet, then move **both** pointers inward (a match uses up both current values, and we need fresh candidates for the next search).
- `while left < right and nums[left] == nums[left - 1]: left += 1` — after finding a match, skip past any further duplicate values at the new `left` position, so we don't record the same triplet again with a merely-shifted duplicate. **This is the exact mechanism the hash-set approach lacked a clean equivalent for.**
- Same idea for `right` on the other side.

### Dry run

`nums = [-1,0,1,2,-1,-4]` → sorted: `[-4,-1,-1,0,1,2]`

**i = 0, nums[i] = -4:** `left=1, right=5` (`-1` and `2`). sum = -4-1+2 = -3 < 0 → left+=1. `left=2,right=5` (`-1`,`2`): sum=-4-1+2=-3<0→left+=1. `left=3,right=5` (`0`,`2`): sum=-4+0+2=-2<0→left+=1. `left=4,right=5` (`1`,`2`): sum=-4+1+2=-1<0→left+=1. Now `left=5=right`, loop ends. No triplet found starting with -4.

**i = 1, nums[i] = -1:** (not equal to `nums[0]=-4`, proceed) `left=2, right=5` (`-1`, `2`): sum = -1-1+2 = 0 ✅ → record `[-1,-1,2]`. Move `left→3`, `right→4`. Check duplicate-skip: `nums[3]=0 != nums[2]=-1` no skip; `nums[4]=1`, no skip needed against `right+1=nums[5]=2`. Now `left=3, right=4` (`0`,`1`): sum = -1+0+1 = 0 ✅ → record `[-1,0,1]`. Move `left→4, right→3`. Now `left(4) < right(3)` is False, loop ends.

**i = 2, nums[i] = -1:** equal to `nums[1] = -1` → skip (duplicate first number) — this is exactly the case the skip check exists for; without it, this iteration would re-discover `[-1,-1,2]` and `[-1,0,1]` a second time.

**i = 3, nums[i] = 0:** `left=4, right=5` (`1`,`2`): sum = 0+1+2 = 3 > 0 → right -=1. `left=4=right`, loop ends.

**i = 4:** `nums[i] > 0`? `nums[4] = 1 > 0` → break entirely.

Final result: `[[-1,-1,2], [-1,0,1]]` ✅ matches expected output exactly, with no duplicates — and notice duplicates were avoided by two *different* mechanisms working together: the outer-loop skip (for `i`) and the inner-loop skip (for `left`/`right`), each guarding a different position in the triplet.

### Time & space complexity

- **Time: O(n²)** — the outer loop is O(n), and for each outer iteration, the two-pointer inner scan is O(n) (each of `left`/`right` moves at most n times total within that inner loop, by the same monotonic-movement argument from the topic overview). Sorting is O(n log n), dominated by the O(n²) main work. This matches Approach 2's complexity — the win here isn't speed, it's **cleaner, more reliable duplicate handling**.
- **Space: O(1)** extra (not counting the output list, and not counting the space used by the sort itself, which is typically O(log n) to O(n) depending on the sort implementation) — a genuine improvement over Approach 2's O(n) `seen` set.

## Common mistakes & misconceptions

1. **Forgetting the outer-loop duplicate skip (`if i > 0 and nums[i] == nums[i-1]`).** Without it, the exact same set of triplets gets rediscovered every time a duplicate first-number appears — the algorithm stays correct in the sense of finding all valid *sums*, but violates the "no duplicate triplets" requirement.
2. **Forgetting the inner-loop duplicate skips after a match.** This is a *different* bug from the above — even with the outer skip in place, a single fixed `i` can still produce duplicate triplets internally if `left`/`right` land on repeated values right after a match; both skip mechanisms are needed, and they guard different things.
3. **Using `if nums[i] > 0: continue` instead of `break`.** `continue` would keep checking later (even larger, sorted-ascending) values of `i`, wasting O(n) iterations that are all guaranteed to fail for the same reason — `break` is not just a minor optimization here, it correctly reflects that *no* later `i` can possibly work either.
4. **Assuming this is "just Two Sum three times."** It's specifically "fix one number, reduce to Two Sum on the remainder" — a single reduction, not three independent applications. Confusing this can lead to accidentally re-introducing a third nested loop, undoing the whole point of the reduction.
5. **Not sorting, and trying to deduplicate via a hash set of frozensets/tuples instead.** This works (as shown in Approach 1) but is asymptotically worse and doesn't scale the same reduction insight upward to 4Sum and beyond the way the sorted two-pointer version does.

## Summary

| Approach | Time | Space | Notes |
|---|---|---|---|
| Brute Force | O(n³) | O(n) | Way too slow for realistic input sizes; duplicate handling is a bolted-on afterthought. |
| Fix two + hash set | O(n²) | O(n) | Works, generalizes Two Sum's trick correctly, but duplicate handling gets messy. |
| Sort + Two Pointers | O(n²) | O(1) extra | The standard, expected, cleanest solution — same time as Approach 2, better space and far cleaner duplicate handling. |

**Key takeaway:** 3Sum is really "fix one number, then solve 2Sum on what's left" — and once the array is sorted, 2Sum-on-a-sorted-array is best solved with opposite-direction Two Pointers rather than a hash map, both because it avoids extra space and because sortedness makes skipping duplicates a natural, local check rather than a separate bookkeeping structure. This "reduce N-Sum to (N-1)-Sum" idea generalizes directly to 4Sum and beyond.
