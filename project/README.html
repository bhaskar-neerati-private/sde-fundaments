SDE Fundamentals Calude Notes - Tutoring Curriculum

Source roadmap: roadmap.txt

Profile this plan is built for

  • Stack: Python (Phase 3 and code examples throughout use it)
  • Level: comfortable writing code, gaps are in CS fundamentals - Phase 1 still opens with a Programming Fundamentals lesson, but it's framed as a rigorous audit (surface gaps, don't teach from zero) rather than a beginner crawl, before moving into Git, algorithmic thinking, and DS&A
  • Time budget: 15–20 hrs/week → phase durations below are compressed from the original roadmap's 1–2 month estimates
  • Output: this folder, one markdown file per phase, checked off as you go

Total timeline: ~16–20 weeks (~4–5 months) at 15–20 hrs/week

Why this order hasn't changed from the source roadmap: you can't design good systems without understanding data structures and how APIs/DBs actually work first; SOLID/patterns come before system design because design work assumes you already think in those terms; distributed systems concepts only make sense once you've built a few "boring" single-server APIs; DevOps comes last because it's about deploying things you already know how to build well.

How this tutor works - read this before starting Lesson 1.1

This isn't a reading list. Passive video-watching is the default failure mode for self-study: it feels like progress and isn't. Every lesson below follows the same structure and the same rule:

You do not move to the next lesson until you pass its checkpoint. No exceptions, no "I basically get it."

  1. Watch/Read - the assigned resource, in full, without skipping around. In practice, the phase files also break each lesson into ~40-minute teaching sessions (e.g. 1.4a, 1.4b, 1.4c) that I teach live in chat, in plain English with everyday analogies and code examples, before you touch the Watch/Read material - see "How live teaching sessions work" below.
  2. Do - a hands-on task. Code, not notes. If a lesson doesn't produce working code or a written artifact, it isn't done.
  3. Checkpoint - a gate, not a self-assessment. It's usually one of:
    - Closed-book explanation - explain the concept out loud or in writing with no notes and no video paused on screen. If you can't, you don't know it yet. Rewatch and retry - don't just reread your notes.
    - Build from scratch, unaided - implement the data structure/algorithm/pattern without looking at reference code. Compare against a reference only after you've committed to an answer.
    - Timed problem set - a fixed number of problems in a fixed time window, closed-book.
    - Review by me (Claude), in this project - paste your code or design and ask me to review it against a lesson's checkpoint (e.g. "quiz me on lesson 1.5" or "review my LRU cache against the checkpoint for lesson 1.7"). I will critique it like a strict reviewer: point out what's wrong, ask you to justify decisions, and won't say "looks good" unless it actually is. If you ask me to quiz you, I will actually interrogate you - follow-up questions, no partial credit for hand-waving - not just answer whatever you ask.
  4. If you fail a checkpoint - don't push forward. Identify the specific gap, redo the relevant part of the lesson, retry the checkpoint. Moving on with a shaky foundation is how Phase 4 (design) and Phase 5 (distributed systems) become incomprehensible later - they assume Phases 1–3 are solid.

How live teaching sessions work

Each lesson in the phase files is broken into ~40-minute teaching sessions (labeled 1.1a, 1.1b, ... - a lesson with no letter suffix is already small enough to cover in one sitting). For each session:

  1. I teach it, in chat, in this fixed order: Technical Definition → Plain-English Breakdown → Analogy → Code. The precise, correct definition (proper terminology, never skipped or assumed-known) always comes first - then it's immediately unpacked in simple, jargon-free English so nothing is left resting on a term you had to already know. Then a day-to-day analogy (a fresh one each time, not the same one reused for everything). Then code examples wherever the topic is code-related. This is also the order to use when phrasing answers in an actual interview: technical definition first (establishes correctness), plain explanation and analogy second (shows depth and communication skill), example third.
  2. You ask doubts as they come up. This isn't a monologue - interrupt whenever something's unclear, and I answer before continuing.
  3. No mind maps. (Dropped by request - was adding overhead without enough value.)
  4. The Watch/Read material in the lesson stays as backup/reference and homework - useful for a second pass or filling in more depth, but the live explanation is the primary teaching, not the video.

Checkpoints must be specific, not generic

A checkpoint like "write a script demonstrating X, Y, and Z" is too vague to actually fail anyone - it's easy to satisfy shallowly. Every checkpoint (whether pre-written in a phase file or one I give live at the end of a teaching session) must instead be a small number of concrete, individually-specified problems - exact inputs/outputs, exact behavior required, edge cases named - so it's actually possible to get one wrong and know precisely which part broke. When a phase file's checkpoint reads as generic, replace it with specific problems like this before using it.

Spaced review

Each phase ends with a capstone that forces you to combine everything in that phase into one project or mock assessment. This is deliberate interleaving, not busywork - don't skip a capstone even if every individual lesson checkpoint passed. Integration is a different skill from recall.

Keep a mistakes log

Keep mistakes-log.md in this folder up to date. Every time you fail a checkpoint or get a problem wrong, add one line: what you got wrong, why, and the correct approach. Reread it before starting each new phase. This is the single highest-leverage habit for retention - don't skip it.
