Phase 4: Design Thinking

  • Duration: 3–4 weeks at 15–20 hrs/week (~45–70 hrs total)
  • Builds on: Phase 1's data structures (patterns and LLD are built from them) and Phase 2's API-building experience (you'll design systems you already know how to implement).
  • Unlocks: Phase 5's distributed-systems design work assumes you can already produce a clean class design and a defensible high-level architecture for a single-server system.

How to read this file: each numbered lesson has its own Watch/Read/Do/Checkpoint - that's the gate. "Teaching sessions" underneath breaks it into the ~40-minute chunks taught live in chat.

4.1 OOP Foundations Refresher

Objective: Reason precisely about encapsulation, inheritance vs. composition, and interfaces - the vocabulary every later lesson in this phase depends on.

Teaching sessions (~40 min): one sitting - this is a focused refresher, not new ground.

  • Read: awesome-low-level-design (ashishps1) - OOP fundamentals section
  • Do: Take a class hierarchy you'd naturally reach for (e.g. Animal → Dog, Cat) and deliberately show where inheritance breaks down (a Penguin that can't fly()), then refactor it to use composition instead.

Checkpoint: Closed-book - explain "favor composition over inheritance" with a concrete example of where inheritance creates a fragile hierarchy, not just the slogan.

4.2 SOLID Principles

Objective: Identify SOLID violations in real code and fix them - not just recite the five letters.

Teaching sessions (~40 min each):

  • 4.2a Single Responsibility & Open/Closed - a class should have one reason to change, and you should be able to extend behavior without editing existing code.
  • 4.2b Liskov Substitution & Interface Segregation - a subclass shouldn't break its parent's promises, and interfaces shouldn't force clients to depend on methods they don't use.

  • 4.2c Dependency Inversion - depend on abstractions, not concrete implementations - the principle that makes the other four actually enforceable in practice.

  • Watch: Uncle Bob's SOLID Principles Made Easy - In Python! and SOLID Principles Explained | Python Example

  • Read: awesome-low-level-design (ashishps1)
  • Do: Take the FastAPI service from Phase 2 (or any code you've written) and find at least 3 real SOLID violations in it. Refactor each, one principle at a time, committing separately so the before/after is visible.

Checkpoint: Closed-book - given an unseen 30-line class that violates 2–3 SOLID principles, identify every violation and explain the concrete failure mode each one causes (not just name the letter).

4.3 Creational Design Patterns

Objective: Implement Singleton, Factory Method, and Builder in Python, and know when each is actually warranted vs. over-engineering.

Teaching sessions (~40 min each):

  • 4.3a Singleton & Factory Method - ensuring exactly one instance exists, and delegating object creation instead of calling constructors directly.

  • 4.3b Builder - constructing a complex object step by step instead of a constructor with 10 optional parameters.

  • Watch: the Creational Patterns entries in Design Patterns in Object Oriented Programming - Christopher Okhravi

  • Read: Creational Patterns catalog - Refactoring Guru
  • Do: Implement Singleton (using a Pythonic approach, not just translating Java), Factory Method, and Builder from scratch, each solving a real small problem you invent (e.g. Builder for constructing a complex HttpRequest object).

Checkpoint: Closed-book - for each pattern, state the problem it solves and one real scenario where using it would be over-engineering. If you can't articulate the "don't use this" case, you don't understand the pattern yet.

4.4 Structural Design Patterns

Objective: Implement Adapter, Decorator, and Facade; distinguish them from each other precisely (they're commonly confused).

Teaching sessions (~40 min each):

  • 4.4a Adapter & Decorator - making incompatible interfaces work together, vs. adding behavior to an object without changing its interface.

  • 4.4b Facade - a simple front door hiding a messy subsystem behind it.

  • Watch: the Structural Patterns entries in Design Patterns in Object Oriented Programming - Christopher Okhravi

  • Read: Structural Patterns catalog - Refactoring Guru
  • Do: Implement all three solving distinct problems (Adapter to wrap an incompatible third-party API, Decorator to add logging/caching to a function without modifying it, Facade to simplify a multi-step subsystem like your Phase 2 API's request pipeline).

Checkpoint: Closed-book - given three short scenarios, correctly match each to Adapter, Decorator, or Facade and explain what would go wrong if you used the wrong one.

4.5 Behavioral Design Patterns

Objective: Implement Strategy, Observer, and Command; recognize these patterns hiding inside requirements before being told to use them.

Teaching sessions (~40 min each):

  • 4.5a Strategy & Observer - swapping algorithms interchangeably, vs. notifying a list of subscribers when something happens.

  • 4.5b Command - turning an action into an object, so it can be queued, logged, or undone.

  • Watch: the Behavioral Patterns entries in Design Patterns in Object Oriented Programming - Christopher Okhravi

  • Read: Behavioral Patterns catalog - Refactoring Guru
  • Do: Implement Strategy (interchangeable sorting/pricing algorithms), Observer (an event system, e.g. notify subscribers on order status change), and Command (undoable operations, e.g. a text editor's undo stack).

Checkpoint: Closed-book - given an unseen requirements paragraph (e.g. "notify multiple systems when a payment succeeds, and allow undoing a discount application"), identify which behavioral pattern(s) apply before writing any code.

4.6 UML & the LLD Process

Objective: Go from a written requirements paragraph to a class diagram to code, in that order, every time - this is the actual skill LLD interviews test.

Teaching sessions (~40 min): one sitting - this lesson is about a process/discipline, not a pile of new concepts.

  • Watch: How to crack LLD (Low Level Design) Interview? | OOD & Design Patterns - GeeksforGeeks
  • Read: awesome-low-level-design (ashishps1) - process and UML notes
  • Do: Take a one-paragraph requirements prompt (write your own, e.g. "design a library book-lending system") and produce a class diagram (boxes and arrows, on paper or a tool) BEFORE writing any code. Only then implement it.

Checkpoint: Practical review - show the diagram-first artifact and the resulting code side by side; the code must match the diagram (if you changed the design mid-coding without updating the diagram, that's a fail - the point is discipline in the process, not just the final code).

4.7 LLD Practice Problems

Objective: Do the process from 4.6 repeatedly, unaided, on the classic interview problem set, until it's fast and automatic.

Teaching sessions (~40 min): one sitting, where I walk you through one full example problem end to end - the rest of this lesson is your independent practice, not more teaching.

  • Read: awesome-low-level-design (ashishps1) - problems directory
  • Do: Design and implement, diagram-first, at least 4 of: Parking Lot, Elevator System, Tic-Tac-Toe, Vending Machine, Rate Limiter, Chess. For each, deliberately apply at least one SOLID principle and one pattern from 4.3–4.5, and name which ones you used and why.

Checkpoint: Timed - given an unseen 5th problem from the same list, produce a class diagram in 15 minutes and a working skeleton implementation in 45 minutes, closed-book. If you blank on where to start, that's a signal to redo 4.6, not just try again.

4.8 System Design / HLD Fundamentals

Objective: Understand the core building blocks of scalable systems - load balancing, horizontal vs. vertical scaling, database replication/sharding, CAP theorem - well enough to use them as a vocabulary, not just define them.

Teaching sessions (~40 min each):

  • 4.8a Scaling Basics: Vertical/Horizontal & Load Balancers - buying a bigger machine vs. buying more machines, and how a load balancer spreads traffic across them.
  • 4.8b Replication & Sharding - copying data for reliability/read-speed, vs. splitting data across machines because it no longer fits on one.

  • 4.8c The CAP Theorem - why you can't have consistency, availability, and partition tolerance all at once, and what that means when a network actually splits.

  • Watch: System Design for Beginners Course - Gaurav Sen (freeCodeCamp) (~1.5 hrs)

  • Read: system-design-primer (donnemartin) - read through the core concepts sections (scalability, CAP theorem, load balancers, caching, databases) before jumping to case studies
  • Do: Summarize each core concept (load balancer, replication, sharding, CAP theorem) in your own words in 2–3 sentences each, with one concrete example of when you'd reach for it.

Checkpoint: Closed-book - explain the CAP theorem with a concrete example of a system choosing C over A (or vice versa) during a network partition, and explain the difference between horizontal and vertical scaling with a real trade-off for each.

4.9 HLD Case Studies

Objective: Apply the fundamentals from 4.8 to design an end-to-end system under realistic constraints (requirements, scale estimates, trade-offs) - the actual shape of a system design interview.

Teaching sessions (~40 min each):

  • 4.9a Case Study: URL Shortener - the "hello world" of system design interviews, walked through end to end.

  • 4.9b Case Study: Rate Limiter or News Feed - a second full walkthrough, to prove the first one wasn't a fluke.

  • Watch: System Design: Design a URL Shortener like TinyURL - Code Tour and browse ByteByteGo's YouTube channel for 2–3 more case studies (e.g. rate limiter, news feed)

  • Read: the solved case studies in system-design-primer (donnemartin) - Pastebin and one more of your choice
  • Do: Design your own HLD for a URL shortener from scratch (without rewatching the video) - requirements gathering, back-of-envelope capacity estimates, API design, high-level architecture diagram, database choice with justification, then compare against the video/primer solution and note every gap.

Checkpoint: Practical, timed - design a second, unseen system (e.g. a rate limiter or a notification service) end-to-end in 60 minutes: requirements → estimates → architecture → key trade-offs, defended under questioning.

4.10 Phase Capstone

Objective: Produce one complete design artifact spanning LLD and HLD for a single system, showing the full pipeline this phase taught.

Teaching sessions: none - this is an assessment, not a taught lesson.

Do: Pick a moderately complex system (e.g. "a ride-sharing dispatch system" or "an online bookstore with inventory"). Produce: (1) an HLD document - requirements, scale estimates, architecture diagram, database and caching choices, trade-offs; (2) an LLD for its core subsystem - class diagram and working code implementing at least 2 design patterns and demonstrably following SOLID.

Checkpoint: Full design review - defend every major decision (why this database, why this pattern, why this scaling approach) under questioning. Any decision you can't justify beyond "that's what the tutorial did" fails the checkpoint - go research the alternative and explain why you didn't choose it. Log the gaps in mistakes-log.md before starting Phase 5.
