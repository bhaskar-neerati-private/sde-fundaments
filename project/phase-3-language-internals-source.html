Phase 3: Language Internals (Python)

  • Duration: 1–1.5 weeks at 15–20 hrs/week (~15–25 hrs total)
  • Builds on: Phase 1's data structures (you'll now see how Python's own list/dict are implemented) and Phase 2's API work (you'll use it as the concurrency testbed).
  • Unlocks: Phase 5's distributed-systems lessons assume you understand concurrency trade-offs (thread vs. process vs. async) at the single-machine level first.

Note from the source roadmap: this phase "matters most for languages with heavy concurrency/collections concepts like Java - skip or lighten it for lighter-weight stacks." You're on Python, which is lighter-weight than Java here, so this phase is intentionally short - but the GIL and async model are still common interview/production topics for Python backend roles, so it isn't skipped entirely.

How to read this file: each numbered lesson has its own Watch/Read/Do/Checkpoint - that's the gate. "Teaching sessions" underneath breaks it into the ~40-minute chunks taught live in chat.

3.1 Python Object Model & Memory Management

Objective: Explain reference counting, garbage collection, mutability vs. immutability, and is vs. == correctly - including where they cause real bugs.

Teaching sessions (~40 min each):

  • 3.1a Mutability, is vs ==, and References - what a variable actually is in Python (a label, not a box), and why two variables can secretly point at the same object.

  • 3.1b Reference Counting & Garbage Collection - how Python knows when to free memory, and the circular-reference case where refcounting alone isn't enough.

  • Read: Python Data Model - official docs (focus on the object/reference sections) and Python behind the scenes #13: the GIL and its effects on Python multithreading (read for the memory-model background even though the title is GIL-focused)

  • Do: Write 5 short scripts that each demonstrate a classic Python memory/mutability gotcha (mutable default argument, shared reference vs. copy, is vs == on small ints/strings, circular references and the GC, id() behavior). Predict the output before running each.

Checkpoint: Closed-book - explain what happens to an object's reference count across 4 unseen code snippets, and correctly predict which produce surprising behavior and why.

3.2 Collections Internals

Objective: Understand how dict and list are actually implemented (hash table with open addressing + compact ordering for dict; dynamic array with amortized-O(1) append for list) well enough to reason about their performance characteristics.

Teaching sessions (~40 min each):

  • 3.2a How Python Lists Work - dynamic arrays, over-allocation, and why append is usually O(1) but insert(0, x) isn't.

  • 3.2b How Python Dicts Work - hash tables, open addressing, and why iteration order is insertion order (since 3.7).

  • Watch: Modern Dictionaries - Raymond Hettinger (SF Python) - the earlier meetup version of his well-known PyCon 2017 talk; same speaker, same core content

  • Read: Python behind the scenes - tenthousandmeters.com blog series (browse the series index for the dict/list internals entries)
  • Do: Benchmark (using timeit) list append vs. insert-at-front, and dict lookup vs. linear search through a list of tuples, at increasing sizes (100, 10k, 1M elements). Explain the resulting curves in terms of the underlying implementation.

Checkpoint: Closed-book - explain why list.insert(0, x) is O(n) but list.append(x) is amortized O(1), and why average-case dict lookup stays O(1) as size grows, tying the answer back to the actual data structure (not just "because Big-O says so").

3.3 The GIL & Multithreading

Objective: Explain what the GIL actually protects, why CPU-bound multithreading in CPython doesn't give you a speedup, and when threading still helps (I/O-bound work).

Teaching sessions (~40 min): one sitting - this is a single narrative (what the GIL locks, and why that means different things for CPU-bound vs I/O-bound work) that holds together better taught in one go.

  • Watch: Understanding the Python GIL - David Beazley, PyCon 2010 (the classic explanation - foundational, still conceptually accurate) and Python Threading Tutorial: Run Code Concurrently Using the Threading Module - Corey Schafer
  • Read: Python behind the scenes #13: the GIL and its effects on Python multithreading - note in your own words that CPython 3.13+ has an experimental free-threaded (no-GIL) build; mention this as a caveat when discussing the GIL in interviews.
  • Do: Write two benchmarks: (1) a CPU-bound task (e.g. summing primes) run single-threaded vs. multi-threaded - confirm threading does NOT speed it up; (2) an I/O-bound task (e.g. multiple simulated network calls with time.sleep) run single-threaded vs. multi-threaded - confirm threading DOES help here.

Checkpoint: Closed-book - explain why your two benchmarks produced different results, in terms of what the GIL actually locks (bytecode execution, not I/O waits). This is the single most commonly botched Python interview answer - don't move on until the explanation is precise.

3.4 Multiprocessing & Asyncio

Objective: Choose correctly between threading, multiprocessing, and asyncio for a given workload, and implement a basic solution with each.

Teaching sessions (~40 min each):

  • 3.4a Multiprocessing - separate processes, separate GILs, real parallelism for CPU-bound work - at the cost of heavier memory and slower startup.

  • 3.4b Asyncio - a single thread cooperatively juggling many I/O waits via async/await, and why that beats threading for high-volume I/O.

  • Watch: Python Multiprocessing Tutorial: Run Code in Parallel Using the Multiprocessing Module - Corey Schafer

  • Read: Python's asyncio: A Hands-On Walkthrough - Real Python and Speed Up Your Python Program With Concurrency - Real Python
  • Do: Reimplement the CPU-bound benchmark from 3.3 using multiprocessing and confirm it DOES speed up (bypasses the GIL via separate processes). Reimplement the I/O-bound benchmark using asyncio/aiohttp-style async calls and compare to the threaded version.

Checkpoint: Closed-book - given 4 unseen workload descriptions (e.g. "parsing 10k large CSV files," "calling 100 external APIs," "a CPU-heavy image resize pipeline," "a web server handling many slow DB queries"), correctly choose threading, multiprocessing, or asyncio for each and justify the choice in one sentence.

3.5 Phase Capstone

Objective: Demonstrate the internals knowledge is usable, not just recitable.

Teaching sessions: none - this is an assessment, not a taught lesson.

Do: Take the FastAPI service from Phase 2 and add one CPU-bound endpoint and one I/O-bound endpoint. Implement the CPU-bound one using multiprocessing (or a process pool) and the I/O-bound one using async, and load-test both to show the expected behavior (CPU-bound scales with processes; I/O-bound scales with concurrency, not threads).

Checkpoint: Explain, under questioning, why each endpoint uses the concurrency model it does, and what would break if you swapped them (e.g. multiprocessing for the I/O-bound endpoint - explain why that's wasteful; threading for the CPU-bound one - explain why it wouldn't help). Log any shaky answers in mistakes-log.md before moving to Phase 4.
