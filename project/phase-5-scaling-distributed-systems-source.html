Phase 5: Scaling & Distributed Systems

  • Duration: 3–4 weeks at 15–20 hrs/week (~45–70 hrs total)
  • Builds on: Phase 2's working API (you'll add caching, queues, and security to it) and Phase 4's HLD fundamentals (CAP theorem, replication) - this phase goes deeper into each.
  • Unlocks: Phase 6 assumes you have a real multi-component service (API + cache + queue) worth containerizing and deploying.

How to read this file: each numbered lesson has its own Watch/Read/Do/Checkpoint - that's the gate. "Teaching sessions" underneath breaks it into the ~40-minute chunks taught live in chat.

5.1 Caching Strategies & Redis

Objective: Choose the right caching strategy (cache-aside, write-through, write-behind) for a given access pattern, and use Redis correctly, including cache invalidation.

Teaching sessions (~40 min each):

  • 5.1a Caching Strategies - cache-aside, write-through, write-behind, and the trade-offs between them.

  • 5.1b Redis Basics & Cache Invalidation - using Redis as that cache, and why "invalidating" it correctly is the actually hard part.

  • Watch: Redis Explained: In-Memory Caching for Distributed Systems

  • Read: Redis official documentation
  • Do: Add a Redis cache-aside layer in front of the slowest query in your Phase 2 API. Measure latency before/after. Then deliberately create a stale-cache bug (update the DB without invalidating the cache) and fix it.

Checkpoint: Closed-book - explain cache-aside vs. write-through vs. write-behind, when you'd pick each, and walk through exactly how you'd invalidate this specific cache on a write, and why a naive TTL-only approach isn't always enough.

5.2 Distributed Systems Fundamentals

Objective: Understand replication, sharding, consensus, and the CAP theorem deeply enough to reason about failure scenarios, not just define the terms (this extends the HLD-fundamentals lesson from Phase 4 into the failure-mode details).

Teaching sessions (~40 min each):

  • 5.2a Replication & Consensus - leader-based vs. leaderless replication, and how nodes agree on "what really happened" during a failure.

  • 5.2b Sharding & Hotspots - splitting data across machines by key, and what happens when you pick a bad key.

  • Watch: MIT 6.824 Distributed Systems - Lecture 1: Introduction (optional: continue with more lectures from the MIT 6.824 channel if you want to go deeper than this roadmap requires)

  • Read: the "Distributed Systems" reading list in system-design-primer (donnemartin)
  • Do: Write out, in your own words, what happens to reads and writes in a 3-node replicated database during a network partition under (a) a CP configuration and (b) an AP configuration. Draw the timeline.

Checkpoint: Closed-book - explain the difference between leader-based and leaderless replication, and describe a concrete scenario (not the textbook one) where sharding by the wrong key creates a hotspot.

5.3 Idempotency & Reliable APIs

Objective: Design and implement idempotent API endpoints that behave correctly under retries and duplicate requests.

Teaching sessions (~40 min): one sitting - a single focused idea (repeating a request shouldn't repeat its side effect) with one worked implementation.

  • Read: Idempotency - What is an Idempotent REST API? - restfulapi.net
  • Do: Take a "charge payment" or "create order" endpoint in your Phase 2 API and make it idempotent using an idempotency-key pattern (client sends a key, server deduplicates). Write a test that fires the same request twice concurrently and asserts only one side effect occurs.

Checkpoint: Closed-book - explain which HTTP methods are idempotent by definition (and why POST isn't), and walk through exactly how your idempotency-key implementation prevents a double-charge under a network retry.

5.4 Message Queues & Streaming

Objective: Understand the difference between a message queue (RabbitMQ) and a distributed log (Kafka), and when to use each; implement a basic producer/consumer.

Teaching sessions (~40 min each):

  • 5.4a Message Queues (RabbitMQ) - a message is delivered, processed, and removed - the classic "to-do list" model.

  • 5.4b Distributed Logs (Kafka) - messages stay on the log and can be replayed by multiple independent consumers - a very different mental model from a queue.

  • Watch: Apache Kafka Crash Course - KodeKloud and RabbitMQ Crash Course

  • Read: Apache Kafka documentation and RabbitMQ Tutorials
  • Do: Take an operation from your Phase 2 API that doesn't need to be synchronous (e.g. "send confirmation email on order creation") and move it to an async worker via RabbitMQ or Kafka - producer publishes on the API request, a separate consumer process handles it.

Checkpoint: Closed-book - explain the difference between Kafka (log-based, consumer groups replay-capable) and RabbitMQ (queue-based, message removed on ack), and justify which one you chose for your exercise and why the other would've been a worse fit.

5.5 Security: SSL/TLS

Objective: Explain the TLS handshake and why HTTPS provides confidentiality, integrity, and (server) authenticity.

Teaching sessions (~40 min): one sitting - the handshake is one linear sequence of steps, best taught as a single walkthrough.

  • Watch: TLS Handshake Explained - Computerphile
  • Read: What Happens in a TLS Handshake? - Cloudflare Learning Center
  • Do: Generate a self-signed certificate and serve your Phase 2 API over HTTPS locally. Use a tool (browser dev tools or openssl s_client) to inspect the actual handshake and certificate.

Checkpoint: Closed-book - explain, in order, the steps of a TLS handshake (ClientHello through session key establishment) and why asymmetric crypto is used to establish the connection but symmetric crypto is used for the actual data transfer.

5.6 Security: JWT & OAuth

Objective: Implement JWT-based authentication and understand the OAuth 2.0 authorization flows well enough to explain why JWT and OAuth solve different (complementary) problems.

Teaching sessions (~40 min each):

  • 5.6a JWT - a self-contained, signed token that proves "who you are" without a server-side session lookup.

  • 5.6b OAuth 2.0 - letting one app grant another app limited access to your account, without ever handing over your password.

  • Watch: OAuth 2 Explained In Simple Terms - ByteByteGo and JWT Authentication Explained

  • Read: JWT.IO - Introduction to JSON Web Tokens
  • Do: Add JWT-based authentication to your Phase 2 API (login issues a token, protected endpoints require and validate it). Include token expiry and a refresh-token flow.

Checkpoint: Closed-book - explain why JWT is an authentication/claims format while OAuth is an authorization protocol (they're often confused), and walk through what happens, step by step, when your protected endpoint receives an expired token.

5.7 Phase Capstone

Objective: Combine caching, async messaging, idempotency, and security into one coherent, defensible service.

Teaching sessions: none - this is an assessment, not a taught lesson.

Do: Extend your Phase 2 API into a small production-shaped service: Redis cache-aside on the hot read path, an idempotent write endpoint, an async worker via a message queue for at least one operation, HTTPS locally, and JWT auth on protected routes.

Checkpoint: Design review - walk through the full request path for one write operation end-to-end (auth check → idempotency check → DB write → cache invalidation → async event published) and defend every component under questioning, including "what happens if the message queue is down right now" and "what happens if two identical requests arrive within 1ms of each other." Log any gaps in mistakes-log.md before starting Phase 6.
