Phase 6: Production & Operations

  • Duration: 1.5–2 weeks at 15–20 hrs/week (~25–35 hrs total)
  • Builds on: the service you've been building since Phase 2 and hardening through Phase 5 - this phase is about deploying and operating it properly, not building something new.
  • Unlocks: nothing further in this roadmap - this is the capstone phase. It's deliberately last because deployment tooling is only valuable once you have something worth deploying well.

How to read this file: each numbered lesson has its own Watch/Read/Do/Checkpoint - that's the gate. "Teaching sessions" underneath breaks it into the ~40-minute chunks taught live in chat.

6.1 Docker Fundamentals

Objective: Containerize a real application correctly - a minimal, layered, non-root, production-sane Dockerfile, not just "it runs."

Teaching sessions (~40 min each):

  • 6.1a Images & Containers - what an image actually is (layers), what a container is (a running instance of one), and writing a basic Dockerfile.

  • 6.1b Multi-Stage Builds & Docker Compose - trimming the image down for production, and orchestrating multiple containers together with Compose.

  • Watch: Docker Tutorial for Beginners [Full Course in 3 Hours]

  • Read: Docker Docs - Get Started
  • Do: Write a Dockerfile for your Phase 5 API. Get it working first, then optimize: multi-stage build, minimal base image, .dockerignore, non-root user, layer-caching ordered correctly (dependencies before source code). Add a docker-compose.yml that brings up the API, Redis, and your message broker together.

Checkpoint: Closed-book - explain why layer order in a Dockerfile matters for build caching, and walk through what would break (or become insecure) if you skipped the non-root user or the multi-stage build. docker compose up must bring up the full stack from a clean clone with no manual steps.

6.2 Kubernetes Fundamentals

Objective: Deploy the containerized service to a local Kubernetes cluster and understand what Pods, Deployments, Services, and ConfigMaps actually do (not just copy-paste YAML).

Teaching sessions (~40 min each):

  • 6.2a Pods & Deployments - the smallest deployable unit, and the controller that keeps N copies of it running and handles rollouts.

  • 6.2b Services, ConfigMaps/Secrets & Rolling Updates - giving Pods a stable network address, externalizing config, and updating a live Deployment with zero downtime.

  • Watch: Kubernetes Crash Course for Absolute Beginners - TechWorld with Nana

  • Read: Kubernetes official documentation - Concepts
  • Do: Using Minikube (or kind), deploy your API as a Deployment with a Service in front of it, move config (DB URL, etc.) into a ConfigMap and secrets into a Secret, and scale the Deployment to 3 replicas.

Checkpoint: Closed-book - explain the difference between a Pod and a Deployment, and between a ClusterIP and a NodePort/LoadBalancer Service, then demonstrate a rolling update (change the image tag, kubectl apply, and show zero-downtime rollout) and explain what Kubernetes is doing during it.

6.3 CI/CD with GitHub Actions

Objective: Build a pipeline that runs tests and lints on every push, and only builds/pushes a Docker image on merge to main - the actual point of CI/CD, not just "a YAML file exists."

Teaching sessions (~40 min): one sitting - a CI/CD pipeline is one linear story (trigger → test → conditionally build/deploy) best taught as a single walkthrough.

  • Watch: GitHub Actions Tutorial for Beginners – CI/CD Pipeline from Scratch (2026)
  • Read: GitHub Actions documentation
  • Do: Write a workflow that: runs your Phase 2/5 pytest suite on every push and PR, fails the build on test failure, and - only on merge to main - builds the Docker image from 6.1 and pushes it to a registry (GitHub Container Registry is fine).

Checkpoint: Practical - deliberately break a test, push, and show the pipeline correctly fails and blocks; fix it, push, and show it passes and the image builds only then. Explain why you'd never want the image-push step to run on every PR branch, not just on merge.

6.4 Monitoring & Logging

Objective: Instrument the service with structured logging and basic metrics, and read a dashboard to diagnose a problem - not just "add print statements to production."

Teaching sessions (~40 min each):

  • 6.4a Logs vs. Metrics vs. Traces - three different tools for three different questions ("what exactly happened," "how is the system doing overall," "where did this one request spend its time"), and structured (JSON) logging.

  • 6.4b Prometheus & Grafana Hands-On - exposing metrics, scraping them, and building a dashboard you can actually diagnose a problem from.

  • Watch: Monitoring Made EASY with Grafana and Prometheus!

  • Read: Prometheus - Overview and Grafana tutorials
  • Do: Add structured (JSON) logging to your API with request IDs threaded through. Expose a /metrics endpoint (request count, latency, error rate) and wire up Prometheus + Grafana via docker-compose to scrape and visualize it. Deliberately generate some errors/slow requests and find them on the dashboard.

Checkpoint: Closed-book - explain the difference between a log, a metric, and a trace, and when you'd reach for each. Practical: given an injected bug that causes elevated latency on one endpoint, find it using only the Grafana dashboard (no code reading) within 10 minutes.

6.5 Phase Capstone

Objective: Ship the whole thing as one coherent, observable, automatically-tested and deployed system - the integration of everything built across all 6 phases.

Teaching sessions: none - this is an assessment, not a taught lesson.

Do: From a clean clone of your repo: docker compose up brings up the full stack (API, DB, Redis, message broker, Prometheus, Grafana) with one command; a GitHub Actions pipeline tests every push and builds/pushes an image on merge; the service is deployed to a local Kubernetes cluster with a rolling-update-capable Deployment; a Grafana dashboard shows live request metrics.

Checkpoint: Full system walkthrough, under questioning, end to end: a code change goes from commit → CI tests → merge → image build → Kubernetes rollout → visible in the dashboard, and you can explain every step and what happens if any single step fails (tests fail, image build fails, rollout fails). This is the final gate of the whole roadmap - if you can defend this walkthrough without hand-waving, the fundamentals are solid. Log any remaining gaps in mistakes-log.md, and go fix them before calling this roadmap done.
