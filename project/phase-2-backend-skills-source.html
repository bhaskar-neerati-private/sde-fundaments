Phase 2: Core Backend Skills

  • Duration: 2–3 weeks at 15–20 hrs/week (~30–50 hrs total)
  • Builds on: nothing from Phase 1 directly, but the discipline of "build it from scratch, then verify" carries over.
  • Unlocks: Phase 4's HLD lessons assume you already know what an API and a database actually do under load; Phase 5's caching/messaging lessons assume you can build a working backend service.

How to read this file: each numbered lesson has its own Watch/Read/Do/Checkpoint - that's the gate. "Teaching sessions" underneath breaks it into the ~40-minute chunks taught live in chat, one sitting at a time.

2.1 Relational DB Design & Normalization

Objective: Design a normalized relational schema from a set of requirements, and explain why each normal form matters (not just recite 1NF/2NF/3NF definitions).

Teaching sessions (~40 min each):

  • 2.1a Why Normalize? 1NF & 2NF - what goes wrong when data is duplicated across rows, and the first two fixes.

  • 2.1b 3NF & Designing a Real Schema - removing indirect dependencies, then applying all three forms to an actual e-commerce schema.

  • Watch: the schema-design portion of SQL Tutorial – Full Database Course for Beginners (freeCodeCamp)

  • Read: PostgreSQL Tutorial - official docs (sections on tables/relations) and freeCodeCamp's SQL handbook
  • Do: Design a normalized schema (to 3NF) for a small e-commerce system (users, orders, products, inventory) from scratch on paper/diagram, then implement it as CREATE TABLE statements.

Checkpoint: Closed-book - given an unseen denormalized table, identify the normal-form violations and redesign it to 3NF, explaining the anomaly (update/insert/delete) each fix prevents.

2.2 SQL Querying

Objective: Write joins, aggregations, subqueries, and window functions fluently without looking up syntax.

Teaching sessions (~40 min each):

  • 2.2a Joins & Aggregations - inner/left/right joins, GROUP BY, HAVING.

  • 2.2b Subqueries & Window Functions - nesting queries, correlated subqueries, and RANK()/ROW_NUMBER()-style running calculations.

  • Watch: SQL Tutorial – Full Database Course for Beginners (freeCodeCamp) (~4.5 hrs) - the querying sections

  • Read: PostgreSQL Tutorial - official docs, Queries chapter
  • Do: Using the schema from 2.1, write: an inner join across 3 tables, a GROUP BY with HAVING, a correlated subquery, and a window function (RANK() or ROW_NUMBER()) solving a real question (e.g. "top 3 orders per customer by value").

Checkpoint: Timed, closed-book - given 5 unseen query requirements against a schema you haven't seen before, write correct SQL for at least 4/5 in 45 minutes.

2.3 Indexing & Query Performance

Objective: Explain how a B-tree index speeds up lookups, when an index helps vs. hurts, and read a query plan (EXPLAIN) to diagnose a slow query.

Teaching sessions (~40 min): one sitting - the index/B-tree/EXPLAIN story is one coherent narrative; no split needed.

  • Read: PostgreSQL Tutorial - official docs plus the EXPLAIN documentation (search "Using EXPLAIN" in the same docs)
  • Do: Load a table with 100k+ synthetic rows, run a query without an index, note the plan and timing, add an index on the filtered column, rerun, and compare. Do this for at least 2 different query patterns (equality filter, range filter).

Checkpoint: Closed-book explanation - walk through what happens internally when you add an index (B-tree structure, why lookups go from O(n) to O(log n)), and explain a scenario where adding an index would make writes worse without helping reads.

2.4 REST API Design Principles

Objective: Design a REST API's resources, HTTP methods, status codes, and versioning strategy correctly - before writing a line of implementation code.

Teaching sessions (~40 min): one sitting - this is a design/vocabulary lesson (resources, verbs, status codes), not implementation; fits in one sitting.

  • Watch: FastAPI Intro – Full CRUD REST API Tutorial (~1 hr, watch for the design/conventions parts, you'll build in 2.5)
  • Read: restfulapi.net - REST API design guide
  • Do: On paper, design the resource model, endpoints, and status codes for a "task management" API (users, projects, tasks) before writing code - get the nouns/verbs/status-codes right first.

Checkpoint: Closed-book - given an unseen set of requirements, design correct REST endpoints (resource naming, HTTP verbs, status codes for success/error cases, pagination approach) in 20 minutes.

2.5 Building APIs with FastAPI

Objective: Implement a working REST API with request validation, error handling, and database integration.

Teaching sessions (~40 min each):

  • 2.5a FastAPI Basics & Request Validation - routing, path/query params, and Pydantic models for validating input.

  • 2.5b Database Integration & Error Handling - wiring up the DB from 2.1, and returning the right status codes for the right failures.

  • Watch: FastAPI Intro – Full CRUD REST API Tutorial and Python FastAPI Tutorial (Part 1): Getting Started

  • Read: A Close Look at a FastAPI Example Application - Real Python
  • Do: Implement the task-management API you designed in 2.4 with FastAPI, backed by the SQL schema from 2.1 (SQLite or Postgres), including request validation (Pydantic models) and correct error responses (404, 422, etc.).

Checkpoint: Practical review - the API must handle at least: create/read/update/delete for one resource, a validation error case, and a not-found case, all returning correct status codes. Walk through your error-handling logic and justify each status code choice.

2.6 Debugging Techniques & Tools

Objective: Debug systematically (reproduce → isolate → hypothesize → verify) using a real debugger instead of scattering print() statements.

Teaching sessions (~40 min): one sitting - the debugging method plus pdb basics is one focused skill; no split needed.

  • Watch: How to Debug Your Python Code with the Python Debugger (pdb) - ProgrammingKnowledge
  • Read: Python Debugging With Pdb - Real Python
  • Do: Take a deliberately buggy version of your FastAPI app (introduce 3 subtle bugs: an off-by-one, a mutable-default-argument bug, and a logic error in a query) and find all 3 using pdb/breakpoints only - no adding print statements.

Checkpoint: Practical, observed - narrate your debugging process out loud while fixing an unseen bug I (or a peer) inject into your code. You must use breakpoints/step-through, not print-and-guess, and articulate your hypothesis before each step.

2.7 Testing Fundamentals & TDD

Objective: Write unit and integration tests with pytest, and practice red-green-refactor TDD for at least one feature.

Teaching sessions (~40 min each):

  • 2.7a pytest Fundamentals - writing test functions, fixtures, and assertions.

  • 2.7b The TDD Workflow - red (failing test) → green (minimum code to pass) → refactor, and why the order matters.

  • Watch: Pytest Tutorial: Complete Pytest Crash Course in Under 6 Hours and TDD Full Course (Learn Test-Driven Development with Python)

  • Read: pytest Tutorial: Effective Python Testing - Real Python
  • Do: Write a full pytest suite for the task-management API (fixtures for test DB/client, unit tests for business logic, integration tests for endpoints). Then add ONE new feature (e.g. "mark task complete") strictly test-first: write the failing test, watch it fail, write minimum code to pass, refactor.

Checkpoint: Your test suite must cover at least one success case and one failure case per endpoint, and you must be able to show the red→green→refactor commits/diffs for the TDD feature, not just the final code.

2.8 Phase Capstone

Objective: Prove the backend skills work together as a coherent, defensible service - not just as isolated exercises.

Teaching sessions: none - this is an assessment, not a taught lesson.

Do: Take the task-management API from 2.4–2.7 and harden it: add indexes where they matter (justify each one from EXPLAIN output), ensure every endpoint has tests, and write a short README documenting the schema, endpoints, and known trade-offs.

Checkpoint: Design review - walk through the schema, the endpoint design, and one query's execution plan, defending every decision under questioning ("why this normal form," "why this status code," "why this index"). Any answer that's "it just seemed right" fails the checkpoint - go back and actually justify it, or fix it. Log any gaps in mistakes-log.md before moving to Phase 3.
